# LLM gotchas — the full entries

Moved verbatim from `bristlenose/llm/CLAUDE.md` on 5 Nov 2026 to cut what every session in `bristlenose/llm/` loads on every turn (the file was 48 KB): the whole § Gotchas, and the any-llm bullet list. `bristlenose/llm/CLAUDE.md` keeps an index of every Gotchas entry's rule and tell, grouped as below, and a one-paragraph pointer for any-llm. **Read the theme's section before working in that area.** Add a new gotcha here under its theme, and add its one-line headline to the index in `bristlenose/llm/CLAUDE.md`. ## Cost estimate and shipped baselines

- **A data file shipped EMPTY is a feature that never runs — and `cohort-baselines.json` was empty for five months.** `estimate_pipeline_cost` resolves local JSONL → shipped baselines → `None`. A *new* user has no local JSONL by definition, so the shipped baseline is the only step that can ever answer them, and Slice C shipped it as `{"cohorts": []}` with the populate step deferred out of band (2026-04-28 → 2026-09-21). The pre-run cost forecast — the thing that answers "what will this study cost me on my own key" — therefore returned `None` for every user on every model, and the CLI simply printed nothing where the estimate goes. **An absent line is the worst possible symptom: there is no error to grep for and nothing looks broken.** Three further defects each independently returned `None`, so populating the file alone would not have fixed it: `_LOCAL_N_THRESHOLD = 3` was applied to `s10`/`s11`, which issue exactly one call per run by construction (and an under-sampled bucket vetoed the *whole* forecast, so a single-run project could never use its own data no matter how many sessions it had); baseline lookup was exact-match on `(family, major)`, so `claude-sonnet-5` found nothing while `claude-sonnet-4` rows sat in the same file, and `gpt-5.6-terra` / `gemini-3.8-flash` — two current provider defaults — normalise to a family with no rows at all; and `cost_usd_actual_estimate` / `cost_usd_predicted` were declared on `LLMCallEvent` in Slice A and written by nothing, so no row in any `llm-calls.jsonl` in the tree carried a cost. **Tell:** a forecast, estimate or badge that is simply *absent* rather than wrong — check whether the data file behind it has any rows, with `python -c "import json;print(len(json.load(open(...))['cohorts']))"`, before reading a line of the resolution logic. Regenerate with `.venv/bin/python scripts/regenerate-cohort-baselines.py trial-runs/`; re-run it after any `prompt_version` bump, because the medians are calibrated against the wording and **no gate enforces that coupling** despite `docs/design-llm-call-telemetry.md` claiming one.

- **…and the suite could not see any of it, because every fixture stubbed the file it was meant to test.** All of `TestEstimatePipelineCost` monkeypatched `_load_baselines` with synthetic cohorts and used one or two stages — never the real file, never the per-session + per-run mix a real log has. So the tests proved the resolution logic composes correctly over data that does not exist, while the shipped path returned `None` throughout. One test was worse than useless: `test_returns_none_when_no_data_anywhere` read the *real* baselines and asserted `cost is None`, so it was **pinning the defect** and went red the moment the file was populated — the "a test can pin a lie" shape, where the fix reads as the regression. **Rule: a test for a shipped data file must read the shipped data file.** `TestShippedBaselinesServeNewUsers` is the pattern — real `cohort-baselines.json`, a `run_dir` asserted empty with `assert not list(tmp_path.iterdir())`, and parameterisation driven from `PRICING` itself so a model added to the rate table without baseline coverage fails there instead of shipping a silently absent forecast. Each of those tests was proved red against the pre-fix tree before being kept; a regression test that passes on arrival has demonstrated nothing.

## Provider registry and model defaults

- **Provider registry** — `bristlenose/providers.py` is the single source of truth for provider metadata (names, aliases, default models, SDK modules). `resolve_provider()` handles alias normalisation (claude→anthropic, azure-openai→azure, ollama→local). `load_settings()` in `config.py` calls the registry to normalise aliases

- **`--llm <provider>` fills that provider's default model (CLI).** Selecting a provider without a model — there is no `--model` flag, and no `BRISTLENOSE_LLM_MODEL` set — used to leave `llm_model` at the Anthropic code-default, which 404'd `model_not_found` on a non-Anthropic endpoint (surfacing confusingly as `PipelineAbandonedError` at s08 topic segmentation). `_fill_provider_default_model()` in `config.py` now snaps `llm_model` to `PROVIDERS[provider].default_model` in exactly that case, emitting a `step=3-provider-default` line in the `llm_resolve` ledger. **Gated on the model VALUE, not the `_src` source label** — `_src` reports `"dotenv-file"` whenever a `.env` merely *exists* (file-presence, not field-presence), so a user with provider+key in `.env` but no model line would be mislabelled and still 404; the gate instead compares against `BristlenoseSettings.model_fields["llm_model"].default`. Rule 1 (explicit `BRISTLENOSE_LLM_MODEL` / a future `--model`) always wins. CLI-only: a `hosted_by_desktop()` no-op keeps all desktop model coherence in `_guard_orphan_desktop_model` (the Swift host injects an explicit model). Azure (`default_model == ""`) is skipped; `local` snaps *cosmetically* (Ollama reads `local_model`, not `llm_model`). A drift guard (`test_anthropic_default_matches_field_default`) pins `config.py` field-default ≡ `providers.py` anthropic `default_model`, since the value gate depends on the two staying byte-identical

- **A model-default value is hardcoded in ~40 places — a bump is never a one-line change.** Despite `providers.py` being the documented SSOT, the dated model ID is duplicated across `config.py` field-default, `llm/pricing.py`, `pipeline_view/catalogue.py` (ModelOptions **and** the `QualityRating` tuple-keys), both Swift files (`LLMProvider.swift` default+picker, `LLMSettingsView.swift` `@AppStorage`), the man page, `cli.py` help, ~15 test files, and the 100+-entry `tests/fixtures/pipeline-view-contract.json` golden fixture. Only `config.py`↔`providers.py` is drift-guarded — the rest drift silently. **`rg <dated-id>` the whole repo before declaring a bump done.** Worked example: `claude-sonnet-4-20250514` (Anthropic retired it 15 Jun 2026 → 404 on every default Claude run) was un-rotted **run-path-only** in `f159fec` (providers/config/pricing/Swift/tests → `claude-sonnet-4-6` / `claude-opus-4-8`, keep `claude-haiku-4-5-20251001`); pipeline-view catalogue, man page, docs, and the golden fixture were deliberately left for the durable follow-up — bind catalogue + Swift to `providers.py` via sync tests, add a `doctor` liveness check + a monthly EOL-watch — parked as `model-eol-resilience` (handoff + 100days + memory `project_model_default_resilience`). Anthropic dateless aliases (`claude-sonnet-4-6`) are NOT evergreen: pinned snapshots that retire (there is no `-latest`); pin + monitor the deprecation pages (Anthropic commits ~60 days notice, Gemini none). **Partly closed 4–5 Sep 2026:** `config.py` derives its default from `PROVIDERS`; `tests/test_llm_sampling_params.py` parses `LLMProvider.swift` and asserts every provider default agrees with Python and every offered model has a pricing row; `scripts/check-providers-live.py` makes one real call per offered model (release-gated — CI has no keys). **`pipeline_view/catalogue.py` bound 5 Sep 2026** — it had offered retired `gemini-2.5-pro` as Gemini's default; `tests/pipeline_view/test_models.py` now asserts every catalogued cloud id is one `providers.py` or the Swift picker ships, and that the flagged default is the registry's. **Two sites in that list remain unbound and are known-stale:** the man page, and `tests/fixtures/pipeline-view-contract.json`, whose ~120 old-id occurrences are frozen *scenario* data — the fixture round-trips against itself to pin the JSON schema, never against the live catalogue, so it stays green with retired ids in it and no gate will ever say so.

- **Azure cost estimation returns None** — deployment names are user-defined strings, not model names, so `estimate_cost()` can't look up pricing. The pricing URL is still shown. **Until 23 Oct 2026 it didn't:** `llm_model` stayed at Claude's default for an Azure run, so the pre-run estimate and the summary priced Claude ("~$0.42 (claude-sonnet-4-6)"). `config._adopt_named_model` now copies `azure_deployment` (CLI, value-gated) and `anyllm_model` into `llm_model`, so everything that *reports* a model reports the one that runs. A deployment named after a priced model (`gpt-4o`) is now priced as that model, which is usually what it is

- **A deprecation page carrying no retirement date is not evidence the model is obtainable.** Gemini 2.5 Flash and Pro were "no longer available to new users" with no shutdown date, so both macOS picker models 404'd from a fresh account while the page stayed clean (4 Sep 2026). Only a call from a fresh account answers it; `scripts/check-providers-live.py` is that call.

## Claude, ChatGPT and Azure requests

- **Anthropic SDK timeout heuristic** — the SDK (v0.77+) rejects non-streaming requests when `max_tokens > ~21K` with `ValueError: "Streaming is required for operations that may take longer than 10 minutes"`. The heuristic is `3600 * max_tokens / 128000 > 600`. Fix: pass `timeout=600.0` to `client.messages.create()`, which bypasses the check. This is already done in `_analyze_anthropic()`. If you ever remove the explicit timeout, the SDK will start rejecting quote extraction calls

- **Azure OpenAI uses `AsyncAzureOpenAI`** — same OpenAI SDK, different client class. Key differences from regular OpenAI: needs `azure_endpoint` and `api_version` on client init, uses deployment name (not model name) as the `model` parameter. `configure azure` stores only the API key in keychain — endpoint and deployment are non-secret, go in env vars or `.env`

- **gpt-4o / gpt-4o-mini cap output at 16384 — the 64000 default is Claude-tuned.** `llm_max_tokens` defaults to 64000 (Claude Sonnet 4's hard cap). gpt-4o/gpt-4o-mini reject `max_tokens > 16384` with a 400 (`max_tokens is too large`). `client.py` clamps per-model via `_MODEL_MAX_OUTPUT_TOKENS` / `_clamp_max_tokens` (logs `llm_max_tokens_clamped`); models absent from the dict aren't clamped. **Raising the clamp doesn't help gpt-4o** — 16384 is its ceiling. Quote extraction (the output-heaviest stage) can legitimately need >16384 output on a *dense* transcript. **Fixed by smart-split** (`chunked-quote-extraction`, `f8ea55a`): truncation now raises a typed `TruncatedResponseError` (in `client.py`, all 5 provider detection sites), which `s09_quote_extraction._extract_with_split` catches and recovers from by reactively splitting the session and re-extracting per chunk (Map-Reduce, two-tier split → index-halving, 10% overlap, depth≤3, dedup on `verbatim_excerpt`). So a dense gpt-4o session completes instead of abandoning. The old `BRISTLENOSE_LLM_MAX_TOKENS=65536` hint (misleading for gpt-4o — the clamp caps it back) is gone. Only at depth-3 exhaustion does it surface a `Cause(category=OUTPUT_TRUNCATED)` ("switch to a larger-output model or pre-segment"). When adding a model whose output ceiling is below 64000, add it to `_MODEL_MAX_OUTPUT_TOKENS`.

- **Sampling parameters on Claude are per-MODEL, and rejected with a 400 — not ignored.** Anthropic removed `temperature` / `top_p` / `top_k` from **Opus 4.7 and Sonnet 5 onward**; Opus 4.6, Sonnet 4.6 and older still accept them. We send `temperature=0.1`, which is never the API default, so an ungated call to a post-4.6 model fails *every time*. `client.py` gates on `_ANTHROPIC_ACCEPTS_SAMPLING`, a **sunset list** beside `_MODEL_MAX_OUTPUT_TOKENS`: it only ever shrinks, unknown models fail **closed** (parameter dropped, call succeeds at the API default) rather than open, and when it empties you delete it and the kwarg. Don't reach for a version comparison — model ids don't sort, and a clever parse is wrong in a way nothing catches.

## Gemini

- **Gemini uses native JSON schema** — not JSON mode or tool use. `response_mime_type="application/json"` + `response_schema=schema_dict` on the `GenerationConfig`. This gives structured output without tool-call overhead

- **`_flatten_schema_for_gemini()`** — Gemini's schema support is a subset of JSON Schema. The helper inlines `$defs`/`$ref` (recursive resolution), converts `anyOf`-with-null to `{"type": "STRING", "nullable": true}`, maps Python types to Gemini types (`string`→`STRING`, `integer`→`INTEGER`, etc.), and strips unsupported keys (`title`, `default`, `$defs`). Without this, Gemini rejects Pydantic-generated schemas

- **Gemini async via `.aio` property** — `google.genai.Client` exposes async methods as `client.aio.models.generate_content()`, not a separate `AsyncClient` class. This is different from the Anthropic/OpenAI pattern

- **Gemini lazy client init** — same `_get_or_create_client()` pattern as other providers. Client is created on first call, cached as `_gemini_client` on the `LLMClient` instance

- **`google.genai.errors.APIError.details` is the WHOLE response JSON, not the details array.** The attribute name is misleading: `.details` returns the entire response-body dict (`{"error": {"code": ..., "message": ..., "status": ..., "details": [...]}}`). The actual array (`API_KEY_INVALID` reasons, etc.) lives nested at `details["error"]["details"]`. When classifying Gemini errors by reason (e.g. distinguishing `INVALID_ARGUMENT`-with-`API_KEY_INVALID`-detail from a plain bad argument), read `getattr(exc, 'details', None)` → guard `isinstance(blob, dict)` → drill into `blob["error"]["details"]` → guard `isinstance(inner, list)` before iterating. See `bristlenose/preflight/api_key.py:_validate_google` for the canonical traversal.

- **google-genai sends with NO timeout and NEVER retries unless asked** (`HttpOptions.timeout` unset → httpx `timeout=None`; `retry_options` unset → tenacity `stop_after_attempt(1)`). A connection that sleep or a network change killed quietly then held the call, and the run, for good: only s09 has a deadline of its own (R30, 24 Oct 2026). Both Gemini clients — the run's in `_analyze_google` and the preflight's in `preflight/api_key.py::_validate_google`, built apart — now carry `_GEMINI_TIMEOUT_S` (600 s, **passed in milliseconds**), and the run's adds `HttpRetryOptions(attempts=_CLOUD_MAX_RETRIES + 1)` (the SDK's own backoff, 1 s doubling to 60 s; it does not read `Retry-After`). Any new Gemini client needs both. The other SDKs' defaults are finite (600 s); only Anthropic's sets TCP keepalive (60/60/5), so after a wake a dead call surfaces in ~6 min on Claude and ~10 min elsewhere. Every timeout here counts **awake time only** (`time.monotonic` is `mach_absolute_time` on macOS). Tests: `tests/test_gemini.py::TestGeminiCallEnds`, `tests/test_preflight_api_key.py::TestGooglePreflightEnds`

## Local (Ollama)

- **Local LLM uses OpenAI SDK** — Ollama is OpenAI-compatible, so `_analyze_local()` in `llm/client.py` uses the same `openai.AsyncOpenAI` client with `base_url=settings.local_url` and `api_key="ollama"` (required by SDK but ignored by Ollama)

- **Local model retry logic** — `_analyze_local()` retries a reply that doesn't parse or validate up to 3 attempts, each time as the first request plus a turn naming the bad fields. Never resend the identical request (a small model gives the identical reply) and never put the reply in the turn or the error: it is the participant's words, and a long one pushes the system prompt out of a small context window. **The last attempt salvages (3 Nov 2026, owner call 56):** like the cloud providers, that attempt goes through `_validate_repairing` for every local schema: shape repairs, and for quotes a reply with one broken quote keeps the others (majority ceiling included) rather than losing the session after three tries; earlier attempts do not, so a retry that returns the whole reply still wins. Tests: `tests/test_local_structured_outputs.py`

- **Ollama in schema mode almost never returns a shape-invalid reply, so the last-attempt salvage is unreachable from a real Ollama run; test the `json_object` fallback with a proxy, not a bigger model.** Measured 3 Nov 2026 on this Mac: `gemma4:e4b` and `llama3.2:3b`, the second also at `temperature=1.9`, gave 5 of 5 and 7 of 7 calls `ok` at retry 0, because Ollama decodes against the grammar. Malformed replies appear only when the server refuses `json_schema` and the client falls back to `json_object` (llama.cpp, LM Studio, vLLM). To run that for real, put a 20-line loopback HTTP proxy in front of Ollama that answers `response_format: {"type": "json_schema"}` with a 400 naming `json_schema`, pass everything else through, and point `BRISTLENOSE_LOCAL_URL` at it: `llama3.2:3b` then needed retries on 3 of 7 calls and finished clean (2m11s on the 8-segment smoke fixture), and the new last-attempt path ran on a real reply. No reply was bad enough for `salvage_items` to drop a quote, so the drop itself has still only been seen under mocks and mutation. A fake that raises is no substitute for the refusal text: `_refuses_json_schema` reads the status and the words `json_schema`/`response_format`.

- **`_needs_provider_prompt()` checks Ollama status** — for local provider, it calls `validate_local_endpoint()` to check if Ollama is running and has the model; for cloud providers, it just checks if the API key is set

- **Local-provider preflight uses the openai SDK, not the `ollama` package.** Ollama exposes an OpenAI-compatible HTTP API, so the runtime `_analyze_local()` and the preflight `_validate_local()` both speak openai-SDK. The `ollama` Python package is **not** a project dependency — don't import it for new local-provider work. `openai.APIConnectionError` covers Ollama-not-running; `openai.NotFoundError` covers model-not-pulled. The recovery route is `recovery_message` switching on `(provider="local", error_class)` to emit Ollama-specific copy from the generic 4-bucket vocabulary.

## Errors, retries and refusals

- **Provider-error strings rendered via Rich need escaping.** `recovery_message` interpolates `str(exc)` from the provider SDK into copy that's `console.print`ed. A hostile / MITM'd provider response can embed `[link=…]` OSC-8 hyperlinks or other Rich markup that the terminal renders as clickable. `bristlenose/llm/billing_hints.py` uses `rich.markup.escape(raw_message)` at the interpolation site — preserves intentional locale-template markup while neutralising provider-controlled text. Same class as the `[name]`-style `console.print` gotcha above; provider exception strings are simply another untrusted-input channel.

- **Cloud clients carry `max_retries=_CLOUD_MAX_RETRIES` (6); don't hand-roll backoff.** The Anthropic/OpenAI/Azure SDKs already retry 429/408/409/5xx with exponential backoff *honouring the server's `Retry-After`/`retry-after-ms` header* (verified: openai 2.41.0 `_parse_retry_after_header`). The SDK default of 2 is too few for the request bursts smart-split can produce on a low-TPM tier (a Tier-1 gpt-4o account is 30k TPM → 429). Set once at construction in `_ensure_{anthropic,openai,azure}_client()`; every call inherits it. **Don't copy the OpenAI cookbook's tenacity/backoff snippets — they ignore `Retry-After` and the SDK does it better.** Local (Ollama) keeps the SDK default (localhost, no rate limits) + its own JSON-parse retry loop. The *proactive* layer (adaptive global concurrency / AIMD) is deferred — see the S3 "Adaptive `llm_concurrency`" item; build it only if logs show *sustained* (not transient-burst) `llm_call_failed | error_type=RateLimitError`.

- **A transport failure is `network` by its class, not its words** (`run_lifecycle.categorise_exception` → `anyllm.is_network_error`, provider-scoped call sites only). The text regex alone read ChatGPT's "Request timed out." and every bare httpx error Gemini raises as `unknown`. A new transport exception class an SDK starts raising belongs in `anyllm._NETWORK_NAMES`

- **A provider's content filter or refusal is `ContentBlockedError`, never an empty reply** (N168, owner ruling 1 Nov 2026). Sensitive interviews (health, on Azure especially) get declined, and each provider said it differently: Claude `stop_reason == "refusal"`, ChatGPT and Azure `finish_reason == "content_filter"` or a strict-mode `message.refusal` with no content, Gemini a `SAFETY`/`PROHIBITED_CONTENT`/`BLOCKLIST`/`SPII` finish reason or prompt block, Azure's own 400 with `error.code == "content_filter"` (read structurally by `is_content_blocked`, never from message text), any-llm's `content_filter`. `_build_cause` gives it the existing `api_request` category and the constant message "<stage> failed: the provider declined this session's text (content filter or refusal) on <provider>": never the provider's words (a refusal can quote the prompt) and no new locale key. It does NOT stop the retry: a blocked session is still tried again, and billed again, on the next Analyse; stopping that needs a worded decision. A new provider path that can see a refusal raises `ContentBlockedError` before it reads an empty reply as `Empty response from ...`. Tests: `tests/test_llm_content_blocked.py`.

## Testing LLM calls

- **A bare `AsyncMock` accepts any kwarg, so the suite cannot see a request-SHAPE break at all.** Every anthropic test mocks `messages.create` with `AsyncMock`/`MagicMock`, and `grep -rn autospec tests/` returns **nothing**. Consequence, twice over: 4246 tests were green against `anthropic 1.x`'s hard `TypeError` (the removed `temperature` kwarg, no `**kwargs` in the signature — the reason `pyproject.toml` carried a `<1` ceiling from 27 Aug to 5 Sep 2026; the floor is now `>=1.0` and the sampling rides in `extra_body`), and 4352 were green against a live 400 on `claude-opus-4-8`, a model the macOS picker was already offering. **Preflight could not save you either, until 20 Oct 2026:** `preflight/api_key.py::_validate_anthropic` made a real one-token call with the real model but sent **none** of the pipeline's params, so the preflight said the key was good and the run died at the first pipeline call (R104). It now sends the run's own parameters (next bullet), so a model that refuses `temperature`, or a cap above its ceiling, fails at the preflight. `configure`, and `doctor` for Claude, ChatGPT and Gemini, still check the key alone with a **free** `GET …/models` (`doctor.py::_validate_anthropic_key` and siblings), so they can still go green over a run that fails; sending the run's request there would add a paid call to each, which is a decision, not a fix. `run` is covered regardless: the paid preflight follows the doctor table. Doctor's Azure check was already a paid completion, and since 20 Oct 2026 it sends `request_params` with the inert prompt and reads a 400 as the request refused, in the provider's words (it read a 400 as a good key). The preflight's 24-hour cache is keyed by the request too (`request_fingerprint`: the wire model, `request_params`, a SHA-256 of the key, and the Azure endpoint and API version or the Ollama address), so a model, `llm_max_tokens`, temperature, key or endpoint changed the same day is checked again; it was keyed by provider alone until 20 Oct 2026, and by model and parameters alone for a day after. When you change what the request carries, assert the *shape* (`tests/test_llm_sampling_params.py` captures `create.await_args.kwargs`), and remember the model list in `LLMProvider.swift:75` is a second list that can drift from the client's.

- **A second request builder drifts from the first the day a default moves.** `preflight/api_key.py` builds its own one-token request. When the ChatGPT default moved to a GPT-5-class model, `analyze()` was gated onto `max_completion_tokens` and preflight was not — it kept sending `max_tokens=1`, which GPT-5 rejects, so `configure openai` failed on a good key while runs succeeded (4 Sep 2026). The live check calls `analyze()` only, so it could not see it either. When you gate a parameter in `client.py`, grep every other place that constructs a request to that provider (`preflight/`, `LLMValidator.swift`) and gate them off the same table. **Since 20 Oct 2026 there is one builder:** `client.request_params(provider, model, max_tokens, temperature)` returns every parameter a call carries besides its prompt and schema (output cap under the model's name for it, clamped; sampling where the model accepts it; Anthropic's explicit timeout), every `_analyze_*` reads it, and the preflight sends exactly that with the inert `"."` prompt (R104). Gate a parameter there, never at a call site. `tests/test_preflight_api_key.py::TestPreflightSendsThePipelinesRequest` captures both requests at the SDK for each provider and asserts they agree. The preflight therefore sends the run's output cap (64000 by default); billing is per token produced, so it costs what the short reply to `"."` costs, not the cap. One exception: Ollama gets a one-token cap, because it refuses no cap (so the run's proves nothing) and a small local model rambling on `"."` could hold setup for minutes. And a Claude 400 that is not a credit error is now said in the provider's words (`error_class=None`), not "the model is not available for your account": the 400s this request can meet are about the request.

- **A terse fixture prompt is a different test from the product.** The live check's hand-written prompt failed on Sonnet 5 five runs out of five; the six real stage templates fail only at quote clustering (stage 10, a string where an object was asked for) and thematic grouping (stage 11, the parent object nested inside a field) and pass extraction. A fixture that reproduces a failure more often than the product does is measuring the fixture. Use the real templates in `llm/prompts/` when the question is whether a model works.

## Prompts and platform quirks

- **Python 3.14 + pydantic v1 crash** — `import presidio_analyzer` → spacy → pydantic v1 → `ConfigError` on Python 3.14. `check_pii` in `doctor.py` catches `Exception` (not just `ImportError`) and returns `SKIP` when `pii_enabled=False` (the default). If adding new import-guarded checks, use `except Exception` for robustness

- **A length rule in a prompt is calibrated per model, and the production model obeys where the cheap one overshoots.** Measured 30 Oct 2026 (`experiments/signal-highlight-lab/`, signal-elaboration Step 6): told "at most 5 words and a quarter", Haiku 4.5 returned a median of 8 words and Sonnet 4.6 returned 5 (27 of 91 at four words or fewer, a length the owner's blind picks rejected). Told "6 to 9", Sonnet ran to 9 and Haiku to 11. So a number tuned on Haiku is wrong on Sonnet, the default, and a replay on the cheap model proves nothing about the shipped length. Replay on the model that ships, and score against a human's picks, not against the wording's own target. The adopted wording (5 to 7 words, a floor, a budget of two coloured bullets per card) was calibrated on Sonnet 4.6 and has not been run with the model writing the bullet and the span together.

## any-llm (the sixth provider)

- **One readiness answer.** `anyllm.readiness(settings)` is offline and returns a status (`ready`, `not-installed`, `broken`, `no-model`, `bad-model`, `native`, `unknown-provider`, `sdk-missing`, `no-key`); `anyllm.explain(ready)` is the wording. `configure`, `use`, `doctor`, the provider gate in `run`, the server's three key checks and `LLMClient` all ask it. Never decide readiness from `ENV_API_KEY_NAME`: it is `"None"` for llama.cpp, empty for Vertex, a sentence for SageMaker — building the provider and catching `MissingApiKeyError.env_var_name` is the only reliable answer. `anyllm.env_var_name` reads it only to name a variable or compare a key, guarded. Building can raise more than a missing key (Vertex: google-auth's `DefaultCredentialsError`), so readiness catches everything and returns `broken` with the detail: its callers include `doctor` and the server's key checks
- **Schema as a dict, never the Pydantic class.** Given a class, any-llm parses the reply itself and raises on truncation (`LengthFinishReasonError`) or bad JSON (`ValidationError`), discarding the content and usage, so `_validate_repairing` and s09's split-and-retry never run. `_analyze_anyllm` sends `{"type": "json_schema", ...}`, checks `finish_reason` / refusal / empty itself, and falls back once to `json_object` when a provider refuses the schema (remembered per client)
- **Typed errors are opt-in in 1.27** (`ANY_LLM_UNIFIED_EXCEPTIONS=1`, set in-process by `enable_unified_exceptions`). `classify_exception("anyllm", exc)` routes to `anyllm.classify`, which reads the provider's own exception (`original_exception`) with the provider-agnostic rules first. A provider-agnostic `402 → OUT_OF_CREDIT` rule exists for OpenRouter and DeepSeek
- **A pydantic `ValidationError` from inside any-llm** (1.27 rejects finish reasons outside OpenAI's five; fixed in 1.38) becomes `UnreadableReplyError` (a RuntimeError), logged by field path and type plus a short `finish_reason` enum, never quoting the reply — pydantic's message quotes the transcript. Stage 9 says "the model's reply didn't fit the expected format"
- **No `temperature` / `max_tokens`** unless the user set them (`request_params("anyllm", …)`, value gate against the field defaults): ours are refused by small-output and reasoning models, and a per-model table would be a new interim picker
- **Thinking off: every call sends `reasoning_effort="none"`** (`request_params("anyllm", …)`), any-llm's per-provider word for it. Through OpenRouter a hybrid model (Qwen 3.8 Flash, DeepSeek V4 Flash, Nemotron) thinks by default, billed as output; Qwen ran every s09 pass past the 570 s deadline. **Never send `"low"`**: Mistral maps every level but `auto`/`none` to `"high"`. A model that always thinks refuses `"none"` with a 400 naming reasoning (`_refuses_reasoning_off`), and both `_analyze_anyllm` and the preflight resend without it, the run remembering per client. `docs/design-any-llm.md` §5.3d has the measurements
- **A gateway's "Provider returned error" is the model's host, not the key** (`anyllm.upstream`, `docs/design-any-llm.md` §5.3e): the preflight buckets it `upstream_busy` / `upstream_failed` with `ValidationResult.host`, the run records `Cause.model_host`, and both say "Mistral, reached through OpenRouter, is busy". No extra retries for a shared pool: measured at ~38 minutes full, no `Retry-After`
- **The five built-in providers are refused as inner prefixes** (`anthropic:`, `openai:`, `gemini:`, `azureopenai:`, `ollama:`), pointed at their own command
- **Destination:** `anyllm.api_base` resolves the URL as any-llm does (`*_API_BASE` variable over the class default); `destination` names that host and says when it came from a variable. A prefix-based table of hosts would be wrong the day someone's shell profile sets a proxy
- **Retries:** our own loop in `_analyze_anyllm` on rate limits and 5xx (`_CLOUD_MAX_RETRIES`, honouring `Retry-After`, which any-llm keeps as a string): 1.27 can't set retries uniformly, and Mistral's SDK tries once
- **Keys:** a key the user just gave is checked first (and `shadowed_by` names a variable that will win at run time); otherwise the provider's environment variable (any-llm reads it), then the store, one entry per inner provider (`anyllm_<inner>`, "Bristlenose Mistral API Key (any-llm)", not in `CREDENTIALS`, so not in the Swift mirror). Passed as `api_key=`
- **Telemetry:** rows keyed on the request model (`provider:model`), never priced
- **Log a caught LLM error as `failure_summary(exc)`, never `%s` of it** (all providers): pydantic's text quotes the reply, and a provider's error string is its whole body (OpenRouter's moderation 403 carries `metadata.flagged_input`, the transcript). It reads the body through `original_exception`, never `__context__`. A no-leak test needs a short value: pydantic abbreviates a long `input_value`, so a long one passes with the leak in place
- **Rich:** lines that print a model string turn the highlighter off (`anthropic:claude` reads as IPv6) and escape install commands (`[any-llm]` reads as a style tag)
- **Tests:** `tests/test_anyllm.py` uses a fake `any_llm` shaped like 1.27; the `test` matrix never installs the real one, but the `any-llm-library` CI job does and runs the shape tests (class shape, error shape against the real `convert_exception`, thinking off, no telemetry, no network on import). - **`--anyllm anthropic:...` / `openai:...` can never pass `check-providers-live.py`.** `readiness` returns `native` for the built-in prefixes (`NATIVE_PREFIXES`) before any key or call, so it prints "X is built in".
