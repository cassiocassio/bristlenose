## CSS cascade, specificity and caching

**Three specificity traps live here, all three measured shipping wrong before being raised:** `.bn-session-duration { text-align: right }`, `.bn-session-speakers { white-space: nowrap }` and `.bn-session-meta { min-width: 12rem }` sit in the *templates* layer, which concatenates AFTER organisms (~5000 lines later in the served file) — so a bare `.bn-cell-*` rule ties at 0-1-0 and loses on source order. The grid answers with `.bn-sessions-row .bn-cell-duration`, `.bn-sessions-row .bn-cell-speakers` (both 0-2-0), and by simply not applying `.bn-session-meta` to the start cell.

**The speakers one is the cautionary case, because it made a whole ladder rung inert for eleven days.** The wrap override at ≤1285px is what lets the speakers column give up width as a shrink-pair member; defeated, names never wrapped, the `minmax(0, 1fr)` track shrank to its floor anyway, and the un-wrappable content spilled rightwards *across the Start and Sentiment columns*. It surfaced as overlapping header text in a narrow window (17 Aug 2026) and read like a grid-placement bug, which is the wrong place to look. **The tell for this whole class: a cell that ignores a property the organisms layer plainly sets.** When adding any `.bn-cell-*` rule, grep `templates/report.css` for the twin `.bn-session-*` class first — the cells carry both, and the templates layer always wins a tie. Don't fix it by editing `report.css`: those declarations are still correct for the `<table>` the sealed static render uses, which shares the classes.

- **A sibling combinator breaks silently when a wrapper is added, and nothing goes red.** `.bn-transcript-journey-header ~ .transcript-body .transcript-segment[id]` set the paragraphs' `scroll-margin-top`. When the gutter work (`3baf841f`) wrapped the body in `.bn-transcript-sheet`, the body stopped being the header's sibling, the rule matched nothing, and every `scrollIntoView({ block: "start" })` (a journey-chain click) landed its paragraph under the sticky header. Found 17 Oct 2026 while building the transcript timeline; now `~ :is(.transcript-body, .bn-transcript-sheet)`. **When you insert a wrapper element, grep the theme for `~` and `>` selectors naming the wrapped element.** **Tell:** a scroll that lands under a sticky header, where the margin variable is set but the computed `scroll-margin-top` is 0.

- **A running `bristlenose serve` caches the concatenated theme CSS IN MEMORY — edit `bristlenose/theme/*`, and the server keeps serving the old bytes until you restart it.** `render/theme_assets.py` lazy-loads and caches `load_default_css()`, so the *third* staleness layer (after the per-project baked copy and the browser cache, both below) is the server process itself. This is the nastiest of the three because the documented headless fix — force-fetch `link.href + "?v=" + Date.now()` with `cache: "no-store"` — **does not help**: it faithfully re-fetches from a server that is itself serving stale bytes, so the measurement looks authoritative and is wrong. Diagnosis that works: `curl -s http://127.0.0.1:<port>/report/assets/bristlenose-theme.css | grep -c '<a selector you just added>'` — 0 means restart the server, not fight the browser. **Tell:** a CSS change *partially* appears — rules you added in an earlier edit work, rules from the latest edit don't — because the cache was populated between the two edits. Cost a debug cycle on 6 Aug 2026 chasing two "specificity bugs" that were really one stale process; the specificity analysis was correct, the verification wasn't.

- **Theme CSS caches HARD in the browser — a plain reload (and even Playwright's CDP `Network.setCacheDisabled`) can serve STALE `/report/assets/bristlenose-theme.css` after you rebake.** Two layers bite when QA'ing a `bristlenose/theme/` change against plain `bristlenose serve` (not `--dev`): (1) the per-project **baked copy** `<proj>/bristlenose-output/assets/bristlenose-theme.css` wins over source (root CLAUDE "baked-CSS" gotcha) — rebake it first with the `load_default_css()` one-liner; (2) even after a rebake, the browser reuses the **cached stylesheet** on the next navigation — a normal reload shows old CSS, and `Network.setCacheDisabled` proved unreliable across Playwright calls (the parsed stylesheet had the old rules while `curl` of the same URL had the new ones). Interactive fix: `serve --dev` (live source CSS) or hard-reload (Cmd+Shift+R). **Headless/automated fix — force-fetch the current server CSS and swap it in, bypassing all cache:** `const link=document.querySelector('link[href*="bristlenose-theme"]'); const css=await (await fetch(link.href+"?v="+Date.now(),{cache:"no-store"})).text(); const s=document.createElement("style"); s.textContent=css; link.remove(); document.head.appendChild(s);` then measure. The frontend does NOT import theme CSS (it's the baked link, not a Vite chunk), so `npm run build` does nothing for theme changes — only rebake / `--dev` do. Cost ~4 debug cycles on 25 Jul chasing "my edit isn't applying" before switching to force-fetch-inject.

- **A state class only ONE of the two renderers writes is a rule that cannot fire in the app — and it looks exactly like the house idiom.** `.editable-text.editing` was the inline-edit state from the Round 2 refactor (`05aaef9e`, 16 Feb 2026) until 20 Sep — seven months. `.editing` is written in three places, all of them the frozen vanilla renderer (`theme/js/editing.js:53,177`, `names.js:140`); **`EditableText` has never added a class for that state at all.** So in the SPA — the product — editing a theme heading or description showed the browser's own focus ring and nothing else, while `CSS-REFERENCE.md` described a yellow highlight as the house treatment and two of the three selectors it named (`.name-cell.editing .name-text`, `.role-cell.editing .role-text`) were emitted by nothing at all. Nothing was ever red: a rule that matches no element is not an error, and the static render — which *does* write `.editing` — made the rule look alive to anyone who grepped. **Key a state on the DOM's own attribute wherever one exists** (`[contenteditable="true"]`, `[open]`, `[disabled]`, `[aria-expanded="true"]`): it *is* the state, it needs no co-operation from the component, and it cannot drift. Where you must use a class, grep both renderers for who writes it — `grep -rn "classList.add('x')" theme/js/` **and** `grep -rn '"x"' frontend/src` — before believing the rule is live. **Tell:** a state selector whose class appears in `theme/js/` but not in `frontend/src`, or vice versa. Found 20 Sep 2026; the fix is the `--bn-field-edit-*` block in `tokens.css`, which also carries the two-treatment rule (fill inverts with the ground) and its one exemption (quote crop keeps `--bn-colour-crop-bg`).

- **CSS specificity vs source order in concatenated theme** — `render/theme_assets.py` concatenates CSS files in `_THEME_FILES` order (tokens → atoms → molecules → organisms → templates). At **equal specificity**, the later file wins. `atoms/interactive.css` loads before `organisms/blockquote.css`, so `blockquote.bn-selected` (0,1,1) lost to `blockquote.quote-card` (0,1,1) even though both set `background`. Fix: interactive state selectors use `blockquote.quote-card.bn-selected` (0,2,1) to win regardless of source order. When adding new state classes that override organism-level base styles, **always qualify with the base class** to avoid source-order traps. **Same trap for `@supports` progressive-enhancement blocks** (`@supports` adds no specificity): the grid-lanes masonry block in `organisms/responsive-grid.css` reads as the home for masonry adoptions ("delete this block to revert every surface"), but `responsive-grid.css` loads *before* `codebook-panel.css`, so a `.codebook-grid { display: grid-lanes }` rule added there would lose the `display` declaration to the base `display: grid` further down the concatenation. Enhancement blocks belong **in the same file as the base rule, after it** — see `organisms/codebook-panel.css` (29 Jul 2026)

- **Count specificity, don't assert it in a comment — and never let a `@media print` override outlive the rule it was written against.** A print block in `templates/focus-mode.css` restored `border-left-color` on quote cards and carried a comment claiming `.quote-card.starred` (`molecules/quote-actions.css`) "is more specific and wins here, which is what we want". It isn't: `.quote-card.starred` is **(0,2,0)**; `.bn-focus-mode blockquote.quote-card:not(.bn-selected):not(.bn-focused)` is **(0,4,1)** — four classes plus an element, and `:not()` contributes the specificity of its argument. So the restore silently replaced `--bn-colour-starred` with `--bn-colour-border` and printing stripped the starred edge — the exact opposite of the comment, in the one output nobody re-reads before sending. Two lessons: (1) when you write "X is more specific" in a comment, **count both selectors first** — the comment is not evidence and it outlives the code it described; (2) print overrides are the least-observed CSS in the codebase, so anything that restores a value there needs the same `:not()` guards as the rule it's undoing (fixed 3 Aug 2026, pinned by `TestPrintRestoresTheArtefact` in `tests/test_focus_mode_css.py`).

## Layout and rendering mechanics

**Complex data tables are custom by nature — do not build a generic responsive-table system.** (Decided 6 Aug 2026.) The temptation after the Sessions grid is to extract a reusable "responsive table" abstraction for the next complex table. Don't: every decision in a table's responsive behaviour is a judgement about *its own content*, and five of them resist generalisation.

1. **Which columns matter** — the value of a column to the reader is per-table. There is no generic priority order.
2. **Reading order** — column order is semantic. What sits next to what is an argument about how the data is read, not a layout default.
3. **Columns have semantic dependencies** — dropping one datum can force dropping another that no longer makes sense alone. Degradation is a graph, not a list, and the edges are content-specific. (In Sessions: duration and the filename *merge* rather than one dropping, because a file without its duration is weaker; the badge survives everything because the name means nothing without a stable code to hang it on.)
4. **Fields have different natural min/max lengths** — a person's name, a filename and a user-journey chain size differently and break differently. One shrink rule cannot serve all three.
5. **Whether a field can be abbreviated is a judgement about recognition** — "will the reader still know what this is?" A surname can go because the first name still identifies the speaker; a filename middle-ellipsises because the head and tail carry the meaning; a journey chain cannot be truncated at all without lying about the path.

So: expect the next complex table to carry its own organism, its own measured thresholds and its own ladder, and expect that to be correct rather than duplicative. Share the *atoms* (badges, timecodes, sparklines, section headings) and the *reasoning pattern* — measure where your own content breaks, hold column order fixed so the eye never re-finds a column, shed detail before structure — never the numbers.

**The Sessions grid is a deliberate exception — do NOT fold its thresholds into this scale.** `organisms/sessions-grid.css` carries seven bespoke container-query values (1285 / 968 / 900 / 750 / 700 / 560 / 480), plus bespoke track geometry and a 1 : 1.5 shrink ratio. Decided 6 Aug 2026: this scale serves *card-flow* surfaces (quote grid, signal cards, code groups) that reflow by column count; the Sessions lens is a seven-column data grid with a shrink pair and a degradation ladder, and each value was measured against where its own content breaks. Snapping them to a card-reflow scale would trade a working design for a tidier-looking one. Tune them by eye in `docs/mockups/sessions-grid-playground.html`.

- **`.bn-session-table`** — wrapper section, resets margin; container-query container for the lens
- **`.bn-session-table tr`** (legacy) — `border-bottom` on `<tr>` not `<td>` (ensures full-width horizontal rules even with varying cell heights)
- **`.bn-session-moderators`** — header sentence above table ("Sessions moderated by [m1] Rachel")
- **`.bn-session-speakers`** — flex column for vertically stacked speaker entries
- **`.bn-session-journey`** — muted colour, smaller text, wraps below start date
- **`.bn-session-id`** — `#N` format session number, compact column
- **`.bn-session-duration`** — `text-align: right` on both `<th>` and `<td>`
- **`.bn-video-thumb`** — 96×54px placeholder (16:9 HD aspect ratio), grey background, centred play icon
- **`.bn-play-icon`** — play triangle (▶) inside thumbnail
- **`.bn-sparkline` / `.bn-sparkline-bar`** — per-session sentiment mini-bar chart. Container height: 54px (matches thumbnail) so baselines align. Bar heights set inline, colours via `--bn-sentiment-{name}` tokens
- **`.bn-interviews-link`** — folder header link. Legacy HTML: opens input folder via `file://` URI. React island: copies `file://` URI to clipboard (browsers block `file://` navigation from `http://` pages). Future: desktop app custom URL scheme (`bristlenose://open-folder?path=...`) for native Finder integration
- **`.bn-folder-icon`** — inline SVG folder icon in header link
- **Clickable rows** — `tbody tr[data-session]` gets `cursor: pointer` and `var(--bn-colour-hover)` on hover (in `report.css`). JS click handler in `global-nav.js` calls `navigateToSession()`. Dashboard table rows (`_initGlobalNav`) and Sessions tab rows (`_initSessionDrillDown`) both use this pattern. Clicks on `<a>` elements within rows (filenames, session links) are not intercepted

**Gotcha — measuring a card with `getBoundingClientRect()` FORCES the layout this is meant to skip.** The whole point of `content-visibility: auto` here is that there's no virtualisation, so hundreds of off-screen cards cost nothing until scrolled to. Querying geometry is the documented escape hatch: the browser must produce an accurate answer, so it lays the subtree out anyway. Any JS that reads rects for *every* registered quote (spatial arrow navigation does — `frontend/src/utils/spatialNav.ts`) therefore has a cost that scales with the total number of quotes passing the filter, **not** with what's on screen — and both quote islands mount at once, so the stress fixtures reach several thousand elements per keypress. It's still one reflow rather than N (no interleaved read-after-write), which is why it's acceptable at real study sizes and recorded rather than optimised. If you add another full-grid measurement, know that you're paying this, and prefer document-relative caching invalidated on layout change over per-keypress measuring.

**Gotcha:** `content-visibility: auto` applies `contain: layout style paint` implicitly. This creates a new containing block, but `.quote-group .quote-card` already has `position: relative`, so absolute-positioned action buttons (star, hide) are unaffected. If you add a new child that relies on a containing block *outside* the quote card (e.g. a portal or fixed-position overlay), it will be clipped — use a React portal mounted higher in the tree instead.

- **A measuring probe inside the box it measures takes that box's state classes — and a fit that measures itself then oscillates every frame.** The tab bar measures its one-row width in each spacing from two empty probes that sit inside it (`navBarMeasure.ts`), and `.bn-global-nav--condensed .bn-tab` was a bare descendant selector, so once the bar condensed, the *full* probe took the condensed padding too: full measured as condensed → "full fits" → back to full → measured right → condensed, in a narrow band of widths just under full. It read as violent jitter on the Project page in Safari (19 Oct 2026, from `479eec4b`). The condensed rules now carry `:not(.bn-nav-probe > .bn-tab)` (`tests/test_global_nav_css.py`). **Any state class a component toggles on itself must not reach the probes it measures that state with.** **Tell:** a layout that flips between two states only within a narrow band of widths, and holds outside it.

- **`background-clip: text` shimmer — keep `background-position` inside `[0%, 100%]`, and divide the band by the size factor.** With `background-repeat: no-repeat` (the sane setting for one travelling band) + `color: transparent`, the gradient *is* the text's paint. Animate `background-position` past `0%`/`100%` (e.g. `150%`, `-50%`) and the gradient image slides **fully off** the glyphs → the clipped text has nothing to paint → the whole label goes transparent and **vanishes** (it doesn't shimmer). Fix: `background-size` ≥ 200–300% and sweep position only within `[0%, 100%]` — the band enters/exits inside that range and parks off-window (base-only) during the gap. Second trap: gradient-stop percentages are relative to the *gradient image* (300% of the text), so a band width expressed as a fraction of the *text* must be divided by the size factor (`band / 6` for size 300% = ÷3 for the image, ÷2 for the half). Both bugs shipped in the first `atoms/shimmer.css` cut — text disappeared in both themes. See `atoms/shimmer.css`.

- **Standalone mockups that reuse `.tag-sidebar` render blank until you neutralise its reveal rule.** `organisms/sidebar.css:487` sets `.tag-sidebar { visibility: hidden; opacity: 0; grid-column: 5; position: sticky; height: 100vh }` — the panel only becomes visible when a `.layout.tags-open` ancestor flips it (`:505`). A `docs/mockups/*.html` that drops a `.tag-sidebar` in without that ancestor gets a fully-populated-but-invisible panel (content IS in the DOM; `visibility:hidden` + `opacity:0` hide it — not a JS bug). Fix in the mockup's own CSS with a more specific selector: `.tag-sidebar.mock-sidebar { visibility:visible; opacity:1; position:static; grid-column:auto; height:auto }`. Same trap for any organism that's reveal-gated by an ancestor state class — before reusing an organism standalone, grep its CSS for `visibility`/`opacity` toggled by a `.layout.*` parent. Cost ~20 min of "the JS must be broken" during the `mockup-tag-count-zero-suppression.html` build

- **`auto-fit` grid collapse is DEFEATED by a full-span (`grid-column: 1 / -1`) sibling → ragged right edge.** `repeat(auto-fit, minmax(…, 1fr))` only collapses *empty* tracks (letting the occupied ones stretch flush). A `grid-column: 1 / -1` child spans **every** track, so no track is ever empty — `auto-fit` silently behaves like `auto-fill`, keeps the empty trailing tracks, and any row with fewer items than tracks (e.g. 2 nav panes in a 4-track grid) gets a gap on the right. This is why `.bn-dashboard` (Project tab) is a fixed `1fr 1fr`, **not** the RAM auto-fill idiom the responsive-grid organism uses elsewhere: it carries full-span panes (stats, session table, featured row, coverage — all `.bn-dashboard-full` = `1 / -1`) alongside the two half-width nav lists, so RAM would ragged-right the nav row. Rule: a grid that mixes full-span children with a variable count of normal children can't use `auto-fit` to stay flush — use a fixed column count whose track count the normal children fill exactly. (Also: `grid-auto-flow: dense` **reorders** items to backfill gaps — never add it where source/reading order matters.) The featured-quotes row (`.bn-featured-row`) has no full-span sibling, so it *can* use fixed column counts that match its rendered card count: `#bn-app-root` renders exactly N cards (3 laptop / 5 at `--bn-breakpoint-wide` 1400px) and the grid is `repeat(N,1fr)` — flush because visible-count == column-count. Landed 14 Jul 2026 (`f7549a33`); see `docs/private/handoffs/dashboard-full-width-mvp.md` §Decisions

- **Symmetric inline padding on a component inside a *wrapping* chain reads as a stray character, not as padding.** Padding on an **inline** box paints only at the start of its first line fragment and the end of its last — never on the fragments between. So in a wrapping inline sequence (the Sessions lens journey chain: `label → label → label`), a label with `padding: … 0.3rem` indents line 1 *and* every line that opens with a fresh label, while a line that merely *continues* a wrapped label sits flush. The ragged result looks exactly like a stray nbsp or newline in the data, and that's how it gets reported (3 Aug 2026 — the user's first guess was "is that a nonbreaking space or a CR?"). **The tell that it's padding, not a character:** wrapped lines are indented *inconsistently* — a line beginning a new element indents, a line continuing a wrapped element is flush. A real stray character indents every wrapped line equally. **Fix pattern:** push all horizontal breathing room to the *trailing* edge (`padding-inline: 0 0.3rem` on both the item and the separator) — mid-line gaps are unchanged because each gap is just borrowed from the neighbour on its left, and nothing is left to paint at a line start. `text-indent` is not the fix (it only reaches line 1). Scope it to the wrapping context: `atoms/journey-label.css` keeps symmetric padding for the transcript header's `--overflow` chain, which is single-line + horizontally scrolled and needs the symmetric active pill

## Type, colour and tokens

**Corollary — don't hardcode px in anything that also renders on desktop.** The web (Inter) and desktop (SF Pro) scales differ at several stops — micro 9.6 vs 10, badge 11.5 vs 11, body line-height 1.5 vs 1.4 — so a literal size that looks right in a browser is off-scale in the app. This bit the welcome study-tools mockup (2 Aug 2026): it hardcoded 11/12/12.5px for cell chrome and carried its own drifted `--bn-text-*` block, so every quote card and badge inside its illustrations rendered slightly wrong, and its `--bn-font-body` still named Inter first — which beat the `-apple-system` fallback and showed the wrong *face* while the page around it was already SF. Fix pattern: copy the `--bn-text-*` / `--bn-track-*` block verbatim out of `tokens-desktop.css` and diff it mechanically rather than by eye. Note `-apple-system` does resolve to real SF Pro in Safari and Chrome on macOS, so a mockup can show the true face — no webfont needed.

Forcing `color-scheme: light` on one column and `dark` on another is the right way to put both appearances on one page (what `docs/mockups/*.html` want), and it *mostly* works: custom properties inherit as unresolved token streams, so a descendant's `var(--bn-colour-muted)` re-runs `light-dark()` in its own column's context.

**`color` is the exception, and it fails silently.** An inherited `color` is a *computed* value — `light-dark()` already resolved, once, wherever it was declared. So a `body { color: var(--bn-colour-text) }` resolves against the **page's** scheme and every descendant inherits that one colour, whatever column it sits in. The dark column then renders near-black ink on its near-black ground: no error, no warning, and the surrounding UI looks fine because everything *else* re-declares its colour.

**Fix: re-declare `color: var(--bn-colour-text)` on the forced-scheme container itself.** Substituting the var there resolves it against that element's `color-scheme`.

**Tell:** in a two-column light/dark comparison, the elements that set their own colour (`.description` → `--bn-colour-muted`) render correctly while plain inherited body text does not. That asymmetry *is* the diagnosis — it looks like one element is broken when the truth is that the working ones are re-substituting and the broken one is inheriting. Hit while building `docs/mockups/edit-affordance-states.html`, 22 Sep 2026.

**Logo + appearance toggle gotcha**: `<picture>` `<source>` media queries only respond to the OS-level `prefers-color-scheme`, not the page-level `data-theme`/`colorScheme` override set by the Settings toggle. Setting `img.src` inside a `<picture>` has no effect when a matching `<source>` exists. Workaround in `settings.js` (`_updateLogo`): physically removes the `<source>` element when the user forces light/dark, stashes it, and restores it when switching back to auto. Messy but unavoidable without duplicating the logo as two `<img>` elements toggled by CSS classes.

**Logo click**: wrapped in `<a class="report-logo-link" href="#project" onclick="switchToTab('project');return false;">`. Clicking the fish logo navigates to the Project tab (home). CSS in `atoms/logo.css`: `.report-logo-link` removes underline and sets `line-height: 0` to prevent extra vertical space around the image.

- **`blockquote .timecode`** in `blockquote.css` must use `--bn-colour-accent` not `--bn-colour-muted` — the `.timecode-bracket` children handle the muting. If you add a new timecode rendering context, ensure the parent rule uses accent

- **`--bn-colour-border-hover` token** — 3-state border progression for toolbar buttons: rest (`--bn-colour-border` gray-200) → hover (`--bn-colour-border-hover` gray-300) → active (`--bn-colour-accent` blue-600). Adding a new interactive bordered element should follow this pattern

- **Mute readable text with a colour token, never with `opacity`.** `--bn-colour-muted` clears WCAG AA on the panel by itself (~5:1); an `opacity` dim on top of it multiplies the loss and a clickable row lands near 2:1. Found 3 Oct 2026 on `.toc-link.not-imported` (`opacity: .5`, plus a second `.6` on the label). That rule turned out to be emitted by nothing since the v1 codebook sidebar was deleted, and it was removed rather than fixed: **before fixing a CSS rule, grep `frontend/src` for the class to confirm a shipped component still emits it.** Mockups in `docs/mockups/` link the live theme, so they are not evidence of a shipped surface. Opacity stays fine for hiding, fading in and out, and decorative marks.

- **Delete circles are red, not grey** — `badge-ai::after` and `.badge-user .badge-delete` use `var(--bn-colour-danger)` (red), not `var(--bn-colour-muted)` (grey). Changed to unify delete/deny colour across all badge types (sentiment delete, user tag delete, proposed badge deny pill). If adding a new deletable badge variant, use `--bn-colour-danger` for the `×`

- **`--bn-colour-danger` and `--bn-colour-success` are not in `tokens.css`** — badge CSS uses `var(--bn-colour-danger, #dc2626)` and `var(--bn-colour-success, #16a34a)` with hardcoded fallbacks. The tokens file defines `--bn-colour-negative` instead. The fallback values work but don't adapt in dark mode (delete circles stay `#dc2626` on dark backgrounds). The pill's dark mode overrides in `badge.css` handle this for the pill only. Future: add `--bn-colour-danger` / `--bn-colour-success` as proper `light-dark()` tokens

- **Font-weight tokens — the body tiers, and two of them do not render as the ladder promises.** (Six body tiers since `--bn-weight-semibold` (600) joined on 6 Oct 2026; the monospace weights are separate, above.) `--bn-weight-light` (370) · `-normal` (420) · `-emphasis` (490) · `-starred` (520) · `-semibold` (600) · `-strong` (700). This list said *four* and omitted 370 until 22 Sep 2026, which is part of why the first problem below went unnoticed: the token had three live consumers (`.badge`, `.toc-link`, `.session-entry-name`) and was in neither the table above nor here. `.badge` left it on 15 Oct 2026 for `--bn-weight-mono-tag`.
  - **370 is below the axis the web actually loads.** Both shells request `Inter:wght@<b>400</b>..700`, so 370 is off the bottom of the served variable range. Measured 21 Sep 2026 on the real headline string at 18px: **Chromium clamps it to 400 and renders byte-identically to 400** (231.17px for both), while **WebKit renders it 4.41px narrower** (226.77px). Everything from 400 up agrees exactly across both engines. So the token's stated job — subordinate text — is delivered in Safari and largely not in Chrome, where `.toc-link` at “light” differs from body by 0.53px. Fix is one character either way (token → 400, or the request → `wght@100..700`) but it is a design-system call across three surfaces, so it is recorded rather than taken.
  - **On the desktop SF Pro ladder, 490 and 520 are the SAME optical instance.** `--bn-weight-starred` reads as a rank above `-emphasis` and is not one: measured in WebKit (= the WKWebView the app ships) at 17px, 490→520 widens a 28-character line by **1.03px**, because both sit below SF Pro's Semibold. For scale, 490→420 is 3.63px and 490→700 is 10.89px. The first visible step above emphasis is ~590–600 and **no token names it**, so “make this heavier than a heading” has no answer short of 700, which is the page-title and destructive-verb weight. Don't reach for 520 to create hierarchy; it works for starred quotes because the ladder there is 420→520, not 490→520.
  - **How to measure this rather than argue about it:** render the string at both weights and compare `getBoundingClientRect().width` in WebKit *and* Chromium — identical widths mean the engine snapped both to one instance. Static fonts (Win 10 Segoe UI) still degrade 370/420/490→400 as before. Worked example, self-measuring: `docs/mockups/signals-sidebar-indent.html`. **A monospace face defeats this method:** every weight has the same fixed advance, so the widths are equal whether the engine snapped or not. Measure ink instead — draw the string to a canvas at each weight and sum the alpha. Measured 15 Oct 2026 for SF Mono at 420 and 490: WebKit +11% ink, Chromium identical, with all four widths the same to the hundredth **Not for monospace:** advances are fixed, so width cannot show a weight change. Measure DOM ink instead (screenshot, sum the darkness), never canvas, which in WebKit skips user-installed fonts (`docs/design-monospace-roles.md` §6, measurement traps).

## Interaction, controls and motion

- **The SPA writes `data-arrived`**, through `markArrived()` in `frontend/src/utils/arrival.ts`, never a class: React owns those elements' `className`. `useScrollToAnchor`'s `highlight: true` calls it.
- **The keyframe names only a `from`, and there is no fill-mode.** A `to` frame or `forwards` would leave a card without its own background. `tests/test_arrival_css.py` pins this, and pins that no rule animates the cue with a literal.

- **The static render** still writes `.anchor-highlight` from frozen `transcript-names.js`, and the atom styles it on `.transcript-segment` as before.
- **No reduced-motion override, by decision.** A colour fade moves nothing.

- **Focus outline convention** — `:focus:not(:focus-visible) { outline: none }` in `atoms/interactive.css` suppresses the browser's default focus outline for mouse/touch clicks globally. Keyboard Tab navigation still shows the blue ring via `:focus-visible` rules on individual components. When adding a new interactive element that needs a visible keyboard focus indicator, add a `:focus-visible` rule with `outline: 2px solid var(--bn-colour-accent); outline-offset: -2px;` — the global suppressor handles the mouse case automatically. Never add per-element `:focus:not(:focus-visible)` rules (the global rule covers it). For text inputs, `:focus { border-color: var(--bn-colour-accent) }` provides a secondary cue that works for both mouse and keyboard. **Focus *sinks* are the one exception** — an element that receives programmatic focus but isn't a control (currently only `.center`, the report content column: `tabIndex=-1` in embedded mode, focused by `SidebarLayout` when a sidebar closes since the rails are removed there) has no custom ring, so keyboard-initiated focus falls through to WebKit's default `outline:auto` — a fat accent rectangle around the whole report that reads as a broken rendering seam. For these, add a `:focus-visible { outline: none }` suppressor (the allowed form — the focus *move* is correct a11y and stays; only the stray default visual is dropped). This is desktop/embedded-only: `.center` isn't focusable in the browser/CLI SPA, so the ring never appears there

- **Modifier-clicks must open new tabs** — any clickable element that behaves like navigation (tabs, session links, stat cards, speaker links, dashboard links) must check `e.metaKey || e.ctrlKey || e.shiftKey` and let the default browser behaviour handle it (opens a new tab). Users don't know or care that this is a single-page app — cmd+click should always open a new tab. **Serve mode (React Router):** `<NavLink>` handles modifier-clicks natively for tabs. For other navigation, React click handlers check modifiers and `return` early (letting the `<a href>` handle it). **Static render:** vanilla JS pattern: `if (e.metaKey || e.ctrlKey || e.shiftKey) { window.open(window.location.pathname + '#' + target, '_blank'); return; }`. Already applied to: tab bar buttons (NavLink in serve / `initGlobalNav` in static), speaker links, featured quote cards, dashboard session/list links, TOC links, analysis page, and dashboard React island. When adding new click handlers for navigation-like actions, include the modifier-key guard

- **Modal infrastructure**: every React dialog draws through `frontend/src/components/Dialog.tsx`, and its look is the macOS sheet, measured 24 Oct 2026 (light), with the values in `tokens.css` § Dialogs (`--bn-overlay-scrim`, `--bn-modal-*`); dark is a judgement (black 50% scrim, the card lifted 9% towards white with a light hairline). The motion is asymmetric on purpose: in, a 32 px drop with the card solid by 100 ms; out, rise, fade and backdrop together at one linear pace. A transition takes the timing of the state it goes TO, so the resting rule carries the exit and `.visible` the entrance. The backdrop never closes a dialog. `atoms/modal.css` provides shared `.bn-overlay`, `.bn-modal`, `.bn-modal-close`, `.bn-modal-footer`, `.bn-modal-actions`, `.bn-btn`, `.bn-btn-cancel`, `.bn-btn-danger`, `.bn-btn-primary` classes. `.bn-modal` has `max-width: 24rem` default — override per-modal for wider content (e.g. `.help-modal { max-width: 600px }`). `js/modal.js` provides `createModal()` factory (returns `{ show, hide, isVisible, toggle }`) + `showConfirmModal()` reusable confirmation dialog + `_modalRegistry` + `closeTopmostModal()`. Help, feedback, codebook, and histogram modals all use these — don't duplicate overlay/card/close patterns

- **Toolbar button dual-class pattern** — tag filter and view switcher buttons use dual classes (`toolbar-btn tag-filter-btn`, `toolbar-btn view-switcher-btn`). The shared `.toolbar-btn` provides round-rect styling; the component-specific class allows dropdown-specific overrides. Don't remove either class

- **Pencil icon convention for inline editing — an affordance is hidden at rest and revealed by hovering its HOST, never permanently drawn at a faint tint.** Two halves, and the second was missing for months on the surface that needed it most.
  - **Edit mode**: pencils hide when the field enters edit mode, reappear on commit/cancel. The outline on the active field signals edit state; the pencil is redundant during editing and adds visual noise near the cursor (Microsoft 365 / Notion). Implementation: `{!isEditing && <button ...>}`. Applied to `.bn-name-pencil` (`person-badge.css`).
  - **Rest state**: `.edit-pencil` (`atoms/button.css`) was permanently visible at `--bn-colour-icon-idle` until 22 Sep 2026 — two mistakes at once. **(1) The token is semantically wrong**: `colors/_contract.css` defines it as *"Disabled/idle icon colour"* and this is a live control. **(2) There was no disclosure ramp at all** — the only `:hover` rule was on the pencil *itself*, so hovering the heading did nothing and the sole state change required the pointer to already be on a ~13px glyph. Measured from screenshots: **median ink 1.24:1 light, 1.44:1 dark** (peak 1.61 / 2.03 — peak and median diverge because U+270E is a hairline that is mostly antialiasing, so the token value flatters what the eye gets). Now: nothing at rest, `--bn-colour-muted` on host hover, accent on its own hover.
  - **The reveal is written parent-agnostically** — `:hover > .edit-pencil`, not an enumeration — because the pencil has four hosts (`h3`, `p.description`, the toc `<li>`, `blockquote.quote-card`) and is a direct child in all of them. At (0,2,0) it beats the base rule without `!important`.
  - **`:focus-visible` is load-bearing, not politeness.** An `opacity: 0` button is still in the tab order; without it a keyboard user lands on an invisible control. Same for the `@media (hover: none)` fallback — a hover-reveal is unreachable where there is no hover. **Any time you hide a control at rest, you owe both.**
  - **`.star-btn` is deliberately NOT on this pattern** and must not be swept into it: a star is a *state display* as well as a control, so a starred quote has to read as starred without hovering. It needs its own answer (probably idle→muted for the unstarred affordance, with `--bn-colour-starred` kept for the starred state)

- **A `prefers-reduced-motion` block is a *set*, not a checkbox — add a transition, add its selector there in the same edit.** `templates/focus-mode.css` gained a `.description` transition and didn't gain the matching `transition-duration: 0s`, so descriptions kept animating for exactly the users who asked them not to. The guarding test was `assert "prefers-reduced-motion" in css` — an existence check that cannot fail on a missing selector. It's now set equality between "selectors given a Focus transition" and "selectors zeroed under reduce" (`test_every_transitioned_element_is_zeroed_under_reduced_motion`). Apply the same shape to any future motion block: assert the two sets match, not that the at-rule exists.

## Inspector chrome and the native seam

- **`--bn-colour-inspector-bg` is a themeable chrome tint, not a content surface.** It's in the colour *contract* (`colors/_contract.css`) — every palette must define it (default `#f9f9fa`/`#1c1c1e`, Xcode's flat inspector; edo warms it to washi `#f7f2e6`). `.tag-sidebar` and `.toc-sidebar` backgrounds use it instead of `--bn-colour-bg` (the TOC side joined 14 Aug 2026 — it had shipped on the editor tier, invisible in light mode at a 2% delta, near-black beside the native sidebar in dark). The icon rails stay on `--bn-colour-bg`: browser-only chrome, hidden in `.layout.embedded`. The principle: Apple *cools* the neutral inspector off white, edo *warms* the paper — same subtle desaturated-sibling relationship, mirrored hue.

- **A light strip beside a panel that no CSS colour explains is the WINDOW showing through the transparent embedded body — and the mockup's guesses about that surface were both wrong.** The sticky panels live *inside* the `.layout` grid, so anything `body` pads outside the grid is ground a panel can never cover; in embedded mode `body` is `background: transparent`, so that ground is whatever macOS paints behind the WKWebView. Measured 20 Sep 2026 on macOS 27: pure `#ffffff` beside the `#f9f9f9` panel (Tahoe paints grey there; `docs/mockups/sidebar-seam-window-edge.html` modelled it as one of two greys and neither was right). It read as a failed join and was chased as a Swift seam problem for a session before pixel-sampling the screenshot found 24px of body padding — the embedded override at `templates/report.css` had replaced `padding-top` only. Rules that follow, all shipped that day: `body` pads the **top only** (bottom pad lives on `.layout > .center`, so the panels can reach the window bottom at scroll end; the Signals lens's `.center` opts out, because its sticky heatmap pane sits below that pad and would rest a pad above the window bottom); horizontal pads are **0 in embedded** and restored on `.center` where no panel sits between prose and an edge; and `.toc-sidebar` is a flex column like `.tag-sidebar`, or the outer box scrolls and the datum slips. **Tell:** a gap the tokens can't name — sample the pixels before proposing platform work, and read which edge the user means (the panel already reached the toolbar seam; "the top" was the bottom).

- **Sticky teleport.** `position: sticky; top: 0; height: 100vh` on a grid column whose *flow origin* is pushed down by an ancestor's `padding-top` (the `html[data-embedded] body` toolbar inset) will **teleport up by that padding amount on first scroll** — because `top: 0` anchors the sticky at y=0 while the element rests lower, so it snaps across the gap. Symptom: the panel's top band flickers blank↔tinted as you cross scroll=0. Fix: cancel the ancestor inset with a negative `margin-top` so flow origin == sticky anchor (`.tag-sidebar`), or match the sticky anchor to the origin with `top: calc(inset + …)` (`.minimap-slot`). **Decouple bg-bleed from content-inset:** the negative margin bleeds the tint to y=0 under the frost; a separate `padding-top` positions the content — they are NOT the same value.

- **First-baseline datum is web-internal (`--bn-first-baseline` RETIRED, 25 Jul 2026).** The original design aligned webview content + inspector first-line *text baselines* to the native sidebar's first lens-row ("Project") baseline via a signed `--bn-first-baseline` offset from the synced `--bn-toolbar-inset` line. The red-background test (23 Jul 2026) proved that cross-seam alignment is **unrealisable**: the webview's layout viewport already starts at the toolbar seam (macOS insets it natively), so the native "Project" baseline sits *above* the webview's origin and no CSS can reach it. The bridge's toolbar-inset residual is now **0** (`BridgeHandler.syncToolbarInset` — the old value double-counted the native inset, leaving ~52px dead space). So content and the flanking inspector share ONE web-internal datum: `--bn-space-xl` below the seam. The base `.tag-sidebar` bleed (`margin-top: -(inset+space-xl)`, `padding-top: inset+space-xl`) lands the "Tags" header at the same y as the body's first `<h1>` (body `padding-top: inset+space-xl`, h1 `margin-top: 0`) — no per-column override, no baseline literals. Tune via `--bn-space-xl` on the specimen lens; rebake the project's baked theme CSS per the root-CLAUDE frontend/CSS-QA gotcha. Full ground truth: `docs/design-lens-template.md` § "Native geometry".

- **`text-decoration: none` on a child does NOT remove an ancestor's underline — and `getComputedStyle` will tell you it does.** An ancestor's decoration is *painted through* its descendants, so a hovered `.toc-link` underlines the whole row including any count or badge inside it. Both obvious fixes are no-ops: `text-decoration: none` on the child, and making it an atomic inline (`display: inline-block`) — the latter is exempt per spec, but a **flex item is blockified rather than inline**, so a row that is `display: flex` gets no exemption. The only fix is to stop decorating the ancestor and decorate the text element instead (`.toc-link.v2-nav-row:hover { text-decoration: none }` + `… .codebook-toc-label { text-decoration: underline }`); `text-underline-offset` still inherits, so the offset survives. **The measurement trap is the expensive half:** `getComputedStyle(el).textDecorationLine` reports the *declared* value, not the painted one, so the child reads `"none"` in every broken variant. A probe built on it reported all three candidates as working. **Only a screenshot distinguishes them** — nothing in the suite can see a painted decoration, which is the same family as the "verifying only through a pipe" trap in the root CLAUDE.md. Same applies to any leading change: assemble the theme (`load_default_css()`), render, and look. Landed 31 Aug 2026 on the codebook v2 rail, where hovering a row underlined the pending count.

- **A leading LITERAL cannot fork platforms — so `line-height: 1.5` is a web-only value that ships to the Mac unforked.** `tokens-desktop.css` swaps the whole ladder under `[data-platform="desktop"]` (chrome 1.45 → 1.231, prose 1.5 → 1.4), and token-driven rules move with it while hardcoded ratios stay put. In the app that leaves the literals 20–38% looser than the chrome around them where on web they were 3–10% off, so **the surface you are least likely to be testing is the one where the drift is worst.** The inverse also bites: a rule that raises `font-size` without restating `line-height` inherits the *ratio* (the tokens are unitless), which is harmless at chrome sizes and wrong at body size — `.pg-desc` rendered 15px prose at the 13px chrome ratio until 31 Aug 2026. Decision procedure, the chrome/prose/glyph/special-case roles, and the register of what is still hardcoded: `docs/design-native-typography-grid.md` § Leading.

- **A rule gated on `.layout.embedded` cannot be seen in a browser, and the Mac app's bundled sidecar serves a BAKED copy of the CSS.** `.embedded` is set only by the Mac shell, so `bristlenose serve` in a browser never takes those rules and a bug in them cannot reproduce there (the minimap's viewport rect running under the scrollbar, found 7 Nov 2026, was one: the slot's extra `padding-right` in `sidebar.css` moved the ticks, but an absolutely positioned child ignores its containing block's padding, so the rect did not move). To measure the path from a browser, add the class by hand (`document.querySelector('.layout').classList.add('embedded')`) and label it a proxy. To see a CSS edit in the real app, a plain Debug run shows the sidecar's baked CSS, not your edit: run the `Bristlenose (External Server)` scheme (`BRISTLENOSE_DEV_EXTERNAL_PORT=8484`) against `bristlenose serve --dev <project>`. And when a container's padding changes, give every absolutely positioned child the same inset (`--bn-minimap-extra-pad-r` does this for the minimap).

## Tags, the tag filter and hidden quotes

- **Hidden quotes vs visibility filters**: hidden quotes use `.bn-hidden` class + `style.display = 'none'`. This is fundamentally different from search/tag-filter/starred hiding (which are temporary view filters). Every visibility restore path (`_showAllQuotes`, `_showStarredOnly`, `_restoreViewMode`, `_restoreQuotesForViewMode`, `_applyTagFilter`, `_applySearchFilter`) must check for `.bn-hidden` and skip those quotes. The CSS `display: none !important` on `.bn-hidden` is defence-in-depth. **Hidden quotes always lose selection** — `hideQuote()` removes the quote from `selectedQuoteIds` and strips `.bn-selected`; unhidden quotes always come back unselected

- **Hidden badge count depends on operation order in `hideQuote()`** — `_updateBadgeForGroup()` counts hidden quotes via `querySelectorAll('blockquote.bn-hidden')`. The `.bn-hidden` class and `style.display = 'none'` must be added to the quote **before** calling `_updateBadgeForGroup`, otherwise the count is off by one. But the ghost clone must be created **before** hiding (it needs visible content and dimensions). The correct order is: snapshot siblings → record rect → clone ghost → hide quote → animate siblings → build badge → animate ghost. This ordering bug was fixed in Feb 2026; if refactoring `hideQuote()`, preserve this sequence

- **Histogram delete-from-all**: clicking the hover `×` on a user tag label in the histogram shows a confirmation modal via `showConfirmModal()`, then removes that tag from every quote via `_deleteTagFromAllQuotes()` in `histogram.js`. This calls `persistUserTags()` which re-renders the histogram and re-applies tag filter

- **Reserved sentiment names** — `_RESERVED_SENTIMENTS` in `tags.js` blocks users from creating tags matching the 7 AI sentiment names (frustration, confusion, doubt, surprise, satisfaction, delight, confidence). Guard at both commit time (toast + skip) and suggestion filter (defence-in-depth). Case-insensitive comparison

- **Case-insensitive tag deduplication** — `closeTagInput()` uses `.some(t.toLowerCase() === valLower)` not `indexOf(val)`. If all target quotes already have the tag (any casing), shows toast "Tags are not case-sensitive". This prevents ghost duplicates like "UX" and "ux" on the same quote

- **Bulk tag visual feedback** — when committing a tag to multiple quotes, each new badge gets `.badge-bulk-flash` (0.8s blue ring pulse). A toast ("Tag 'Foo' applied to N quotes") only appears when some tagged quotes are off-screen — if all are visible, the flash alone is sufficient

- **`tagFocusedQuote()` selection guard** — pressing `t` only triggers bulk mode if the focused quote is in `selectedQuoteIds`. If focus is on a non-selected quote, `t` tags only that single quote. Matches the `+` click handler pattern in `tags.js`

- **Tag-filter rebuilds on every open** — `_buildTagFilterMenu()` is called each time the dropdown opens because user tags are dynamic. This also means codebook colour/group changes from the codebook window are picked up automatically without a dedicated `storage` event listener. Don't cache the menu DOM

- **Tag-filter codebook integration** — tags are grouped into tinted `.tag-filter-group` containers using `var(--bn-group-{set})` tokens (same as codebook panel columns). Ungrouped tags appear first as flat items with no wrapper. Search matches both tag names and group names (via `data-group-name` attribute). Uses `createReadOnlyBadge()` from `badge-utils.js` (no delete button) — don't switch to `createUserTagBadge()` which includes a `×` button

- **Search threshold is 8 tags** — the tag-filter search input only appears when there are 8+ tags. This is a UX heuristic hardcoded in `_buildTagFilterMenu()`. If changing, update the MODULES.md entry too
