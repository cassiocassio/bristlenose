## Serve lifecycle and the bridge

- **"Picking up Signals…" is the idle tier's status for a first report being built, derived on the Mac with no bridge message of its own (30 Oct 2026).** `SignalsPreparing.swift`: the line shows when the window's `lens-availability` says Signals is the ONLY lens withheld (`LensReadiness.isPreparingSignals`: a progressive run always withholds Project and Codebooks beside it) and no run is in flight. A run's end is bridged by a native prior (armed only when the study had no report when its run began, held up to 10 s, shown at least 2 s, confirmed by any post made since the run's start that describes a finished run), so the row stays two lines tall (46 pt against 32). It ranks in `ProjectSubtitle.resolveIdle` above screen reading and the missing/unanalysed deltas, shimmers under the same gate as `.running`, and Export Report dims for as long as it shows (any withheld lens makes the report partial). Server half and decisions: `docs/design-signals-lens-readiness.md`. Proof: `SignalsPreparingTests`, and `SignalsPreparingRowRenderTests` draws the real sidebar cell with the shipped locale.

- **"Is this progress line the current run's?" has a blind window: from spawn until the new run writes `run_started`, the newest `run_started` in the log is the PREVIOUS run's, so a run-id match says yes.** The events log is append-only and a Python run takes seconds to write its start; in that window the previous run's last `run_progress` and last `run_started` agree, and a Re-analyse read "8 sessions readable" as its own — the shoal gave way five seconds in (14 Oct 2026). `PipelineRunner.beginSpawnedRun` records the run newest at spawn and `EventLogReader.currentRunProgress` never reads its lines; an attached orphan passes nil (its own start is already newest). **Any new reader of the events log that asks "the current run's?" goes through `currentRunProgress` or makes the same capture** — `deriveFailureFromEvents` answers a different question by timestamp (`terminusIsCurrentAttempt`). Tell: a fresh run whose ring, count or pane jumps straight to the previous run's end state.

- **A popout from `WKUIDelegate.createWebViewWith` gets a live `window.opener` — the player's BroadcastChannel fallback never runs.** Measured 28 Sep 2026 with a WKWebView harness mirroring `WebView.swift` against the bundled sidecar: `opener` non-null, `postMessage` delivered, transcript glow + scroll + word highlight followed playback and scrubbing. `player.html` only opens the channel when `!window.opener`, so that path is dormant and untested, not a safety net. A scripted `.click()` is not a user gesture — a harness needs `javaScriptCanOpenWindowsAutomatically = true`, which the app itself leaves off.

- **A counter or token the page sends restarts with every document; state on the `WKWebView` outlives them.** The report numbers its right-clicks from 1 per page load (a JS module variable), while `BristlenoseWebView` kept the highest number it had seen for the life of the view, which survives `reloadFromOrigin` (⌘R, Reload Report, the reload after every run). So after a reload every right-click read as already used and the menus lost their items, until the count caught up (24 Oct 2026, four review lanes found it; the test said green). Reset such state when a main-frame navigation starts (`didStartProvisionalNavigation`, report view only), as `ContextTargetSlot.newDocument()` does. **Tell:** a web-fed native feature that works until the first reload.

- **A menu command can fail BELOW the gate — the bridge works perfectly and the operation is still meaningless.** Gating asks *can this command reach the web layer?* It cannot ask *is there anything there to answer it?*, and on 12 Sep 2026 four separate commands failed on the second question while passing the first. **⌘F** dispatched `menuAction("find")`, which reached `focusSearchInput()`, which queried `.search-input` — an element `Toolbar` never renders in embedded mode (`if (isEmbedded()) return null`). **⌘J** reached an explicit `break` behind a comment claiming the native layer handled it; no native handler existed, and an NSMenu key equivalent is matched *before* the responder chain, so it could not have. **⌘G** re-applied the query already in the box, because search here filters rather than highlights — a filter has no cursor and nothing to step to. **Five Codes commands** dispatched `bn:codebook-*` CustomEvents whose only listeners lived in the v1 `CodebookPanel` that `baa1aa0e` deleted (`v0.29.0~3`).

  **None of them produced a log line, and none was red.** `guard let webView` passed, `callAsyncJavaScript` resolved, the `catch` never fired. A `querySelector` miss returns `null`, an unhandled `switch` case falls through, and a `CustomEvent` with no listener resolves normally — every one of those is a *success* at the layer that reports. The drop-logging added for the ownership bug above sits one layer too high to see any of it.

  **Five review lanes reading the code found three of the four; the fourth was found by pressing the key.** So: **after gating a bridge-routed command, press it.** The matrix is three states — Welcome, a healthy report, a failed-run status page — and it is the only instrument that distinguishes "reaches the web layer" from "does something".

  **And when it does nothing, the fix is rarely the gate.** Dimming a command with no implementation is a `.disabled` that will never go live — a lie that reads as diligence. Withdraw it instead, using the `mergeCode` idiom in `CodesMenuContent`: comment it out with the reasoning and the restore path attached, and keep the locale keys so restoring is one line. `find` went native, `jumpToSelection` and `findNext`/`findPrevious` were withdrawn, the Codes five are deliberately left ungated pending a product call. The register of which is which is `docs/design-desktop-menu-actions.md` § Retired actions — **read it before writing a `case` for any action you find in that catalogue.**

- **`serveManager.stop()` from `applySelectionChange` is an app-wide act on per-window state.** Selection is per window; the sidecar is not. Every arm of that method that isn't "serve this project" used to stop the serve on everyone's behalf — and a new window starts with *no* selection, so merely opening one tore down the shared sidecar. The blast radius is total because a restart mints a new port and every web view is keyed on it (`ServeSession.viewID`), so all of them remount at `/report/`. Guard any serve teardown with `WindowRoster.anyProjectShown(excluding:)`, and note `switchProject` now no-ops on the path it is already serving — which is exactly what a second window asks for.

- **The detail-pane WebView must be keyed on `project.id` **+ serve port**, never on `project.id` alone.** `ServeSession.viewID` is `"\(projectID)-\(port)"` (`SharedConfigStore.swift:17`); the report view uses it at `ContentView.swift:2990`, and it doubles as the storage-partition key. The reason is a silent-failure class, not tidiness: the auth token is injected in `WebView.makeNSView` **only** (`WebView.swift:110`), so a view that keeps its identity across a port change never re-mounts — `updateNSView` loads the new port while reusing the *previous* sidecar's token, giving silent 401s behind a blank report that looks like success (the BUG-3 class). **Superseded context, 21 Aug 2026:** this invariant arrived with the Phase-A2 **warm-sidecar pool**, where re-pointing to a parked sidecar changed the port under a live `project.id`. **That pool is gone** — Stage 3b deleted `switchProject` in favour of one sidecar per project (`ServeFleet`), as `ServeManager.swift:423` says in the source; `ParkedSidecar.swift` and `switchProject`/`detachFronted`/`adoptFronted`/`tearDownEntry` survive as unreachable code. **The invariant outlived the mechanism that motivated it**, because a restart still mints a new port. Parking, the re-point probe and the switch-timing tiers are history: `docs/archive/design-desktop-switch-performance.md`.

- **Don't share `WKWebViewConfiguration` between WKWebViews** — each view needs its own config (they have separate `userContentController` for message handlers/scripts). Sharing a config and then calling `userContentController.add(_, name: "X")` on both views adds duplicate handlers to the same controller, which crashes. Share the data store and pool *via* the config

- **WKWebView `createWebViewWith` requires the provided configuration** — you MUST use the `configuration` parameter passed to `webView(_:createWebViewWith:for:windowFeatures:)`. Creating a fresh `WKWebViewConfiguration` and returning a WKWebView built with it crashes with `NSInternalInconsistencyException: "Returned WKWebView was not created with the given configuration."`. This means the popout inherits the parent's `userContentController` (including the bridge message handler). The bridge is accessible but player.html never calls it

- **WKWebView `window.open()` is blocked without `WKUIDelegate`** — `window.open()` silently returns `null` unless the Coordinator implements `WKUIDelegate` and `webView(_:createWebViewWith:for:windowFeatures:)`. No error in the console — the call just fails. This is why the video player didn't work in the desktop app before the WKUIDelegate was added

- **`window.blur`/`window.focus` don't fire in WKWebView** — the web view's `window` is always considered focused from the web content's perspective. macOS window activation must be pushed from the native side via `NSWindow.didBecomeKeyNotification`/`didResignKeyNotification` → `BridgeHandler.setWindowActive()`. The browser `blur`/`focus` listener in `AppLayout.tsx` only works in browser-based serve mode

- **Zombie serve processes** — if the app crashes without calling `stop()`, the sidecar self-terminates within ~2s via the parent-death watcher in `bristlenose/server/lifecycle.py`. To inspect manually: `lsof -i tcp -P -n | grep -i bristlenose-sidecar`. Next host launch uses `bind(0)`, so a slow-dying orphan never blocks startup. See "Zombie process cleanup" section above for the full design.

- **`Report:` readiness signal** — `bristlenose serve` prints this BEFORE Uvicorn accepts connections. The port-polling step in ServeManager handles the race. The sidecar will keep this log line and parser — it's the alpha readiness contract

- **Bridge code on main vs feature branch** — the `macos-app` branch has the bridge shims in `frontend/src/shims/bridge.ts`. The main branch build served by `bristlenose serve` won't post `ready` messages. The `didFinish` fallback in WebView handles this (shows content after 2s timeout)

- **Serve process gated on consent** — `serveManager.start()` is only called after `aiConsentVersion >= AIConsentView.currentVersion` (checked in `.onChange(of: selectedProject)`). When consent is granted (version updated), `.onChange(of: consentVersion)` starts serve for the already-selected project. This prevents any data leaving the machine before the user has seen the AI data disclosure (Apple Guideline 5.1.2(i))

- **Project menu actions use `Notification.Name` not bridge** — Show in Finder, Rename, Remove from Sidebar, New Project, New Folder, and Move To are native-side operations. They post notifications (`createNewProject`, `createNewFolder`, `renameSelectedProject`, `renameSelectedFolder`, `removeSelectedProjectsFromSidebar`, `deleteSelectedFolder`, `moveSelectedProject`) which ContentView receives via `.onReceive`. Project removal routes through `UndoableRemovalStore` (8s undo window + toast); folder removal is direct. This is different from all other menu actions which dispatch through `bridgeHandler.menuAction()` to the web layer

- **A per-window callback hung off an app-wide channel is the multi-window bug you will actually ship.** Bit twice in one day (17 Aug 2026), in unrelated code, with identical shape: something app-wide fans out to every window, and each window then runs *its own* handler. (1) `MenuCommands` posted 19 `NotificationCenter` broadcasts — every open window answered all of them, so ⌘N made a project per window and Rename opened an editor in each. (2) `SidebarDeselectMonitor` used `NSEvent.addLocalMonitorForEvents`, which is **app**-wide: each window installs one, each sees every click *anywhere in the app*, and each called its own `deselect` — so one click in one window's empty sidebar area deselected all six. Both were invisible at N=1 and total at N=2. A third, an app-wide *object*: one `ToastStore` injected into every window drew each window's toasts in all of them, until each window owned its own (R90, 20 Oct 2026, `tests/test_desktop_toast_scope.py`). A fourth, the same day: the status page's Send feedback broadcast `.showFeedbackSheet`, so one request opened a sheet in every window, and the menu's fallback with no project window open reached nobody (R82, `tests/test_desktop_feedback_scope.py`). When an app-level path genuinely has no window to name, stage a one-shot that one window claims (`FeedbackFallback`) rather than letting every receiver act. **The tell: any handler whose closure captures per-window state, registered on a channel that isn't scoped to a window.** For NSEvent monitors, compare `event.window` against your own view's `window`; for commands, route through `@FocusedValue` (`WindowCommandFocus.swift`) rather than broadcasting. Grep for `addLocalMonitorForEvents` and `NotificationCenter.default.post` when adding anything window-scoped — `desktop/scripts/check-menu-routing.sh` now holds the second one shut.

- **The desktop failure popover/classifier can mislabel — read the captured stderr, not the category.** `PipelineRunner.categoriseFailure` regex-matches the whole stderr *tail*, which always includes the `run`-startup doctor preflight block (`✓ Transcription mlx-whisper`, `— Whisper model … not cached`). A broad `whisper` / `(speech )?model` pattern matches that *benign* preflight, not the real error — a provider/model-mismatch **LLM 404** (`not_found_error … model: gemini-2.5-flash`) was mislabelled "Transcription failed — the speech model didn't load" for an entire debugging session (5 Jun 2026). **When a desktop run-failure label looks wrong, read the actual error** — the diagnostic capture writes the redacted tail to `<project>/.bristlenose/last-run-failure.log` (added on `desktop-provider-resolution`), or read the run subprocess stderr; don't trust the popover category ("Detailed cause not captured" means the structured cause was empty and the category is a guess). Classifier rule when touching `categoriseFailure`: check specific LLM-error markers (`provider says`, `not_found_error`) BEFORE the whisper check, and require real whisper error signatures (`PackageInstallError` / `snapshot_download` / `metallib` / `libjaccl`), never bare `model` / `whisper` (the preflight always prints them). Full root cause + fixes: `docs/private/archive/desktop-provider-resolution.md`.

- **`ServeManager` serve-lifecycle ownership is guarded by the `generation` counter — and `try? await Task.sleep` swallows `CancellationError`, so a bare `Task.cancel()` is toothless.** Every serve-lifecycle driver (`start`, `shutdown(timeout:)`, `switchProject(to:)`, the readiness + idle-timeout polls) is async and can be superseded mid-`await` by a newer `start()` — the common case is rapid project switches now that the cancel-on-switch modal is gone (`background-runs-view-switch`, A1). The supersession contract: `start()` bumps `generation` (`ServeManager.swift:139`); any path that spans an `await` captures `let myGeneration = generation` at entry and re-checks `guard generation == myGeneration` (or `!Task.isCancelled`) **after** each await, **before** writing terminal state (`process`, `state`, `readTask`) — see `shutdown()` `:306`/`:360` and `switchProject()` `:420`. The trap: the poll loops use `try? await Task.sleep(...)`, which **catches and discards `CancellationError`** — so storing a `switchTask` in `ContentView` and calling `.cancel()` on the next switch does **not** actually stop the in-flight teardown; only the explicit `Task.isCancelled`/`generation` checks do (this was the original Step-2.5 no-op trap — "store + cancel" looked like a fix but was inert). Without the post-await guard, a slow `shutdown()` that loses the race clobbers the winning `start()`'s state (Finding 18, fixed `717afa9`). **When adding a new serve-lifecycle path (e.g. any `restartIfRunning`-style driver), reuse the single `generation` token — do NOT add a second epoch counter or scatter ad-hoc `isCancelled` checks** (per `feedback_no_legacy_naming_in_new_code` and parsimony — one ownership token, not many). **A2's warm-sidecar pool (below) is now implemented and did exactly this** — the synchronous re-point bumps `generation` so a late cold-start readiness completion can't clobber it, and it actually *retired* the termination handler's epoch capture in favour of `ObjectIdentifier` identity routing (one identity check subsumes the fronted-vs-parked routing and the superseded-process no-op). **`restartIfRunning` follows the rule since 20 Oct 2026** — it captures `generation` before its Task and re-checks it before and after `shutdown`, so a `start()` that lands in between keeps the serve instead of being torn down and replaced by the old path. **And `shutdown` detaches `process` before it interrupts it**, so the exit it asked for reaches `handleTermination` as nobody's (no "stopped before it finished starting" flash on a restart during boot), and a spawned serve reading `.running` with no process means *going away* — `agentScopeURL` sends no PUT to it (R35 follow-ups).

- **`callAsyncJavaScript` error handling** — `BridgeHandler.switchToTab()` and `menuAction()` use `do/catch` (not `try?`) so JavaScript errors are logged to Xcode console. If a bridge call silently fails, check the console for `[BridgeHandler] ... FAILED:` messages

- **"Bristlenose didn't finish starting within 15 seconds" was a false failure from cold-start, not a real fault — fixed 20 Oct 2026 (R31). Don't misdiagnose its 90-second successor the same way (the 15 s one cost a long spelunk 13 Jul 2026).** The bundled sidecar is a ~447 MB PyInstaller bundle with **219 adhoc-signed inner Mach-Os**; the *first* exec under the App Sandbox pays a one-time kernel code-signature/dyld validation over all of them that could exceed the ServeManager's old flat 15 s serve-start deadline — so the very first launch (coldest possible: fresh install, nothing cached) times out stuck at "Checking your setup", while **Retry** (validation now cached) sails through. It is NOT a crash (no crash report), NOT the build, and NOT the sidecar: **to confirm in 5 s, run the bundled binary standalone** — `"<App>/Contents/Resources/bristlenose-sidecar/bristlenose-sidecar" serve <a-project-dir> --port 8177` — if it renders + LISTENs (it will), the sidecar/frontend are fine and you're looking at cold-start-vs-deadline. Fixed 20 Oct 2026: `ServeStartPolicy` fails on process exit at once (via `handleTermination`, with its status) and gives a live process 90 s, on a clock that stops while the Mac sleeps; the copy says 90 in all 21 locales. So a 90-second failure now means a live sidecar that never printed its `Report:` line. The escalating "first launch, one-time setup" boot copy was not added: BootView's progress phases are deliberately bar-only. Note: this sidecar accepts **three** subcommands, not one — `desktop/sidecar_entry.py` declares `_PASSTHROUGH_COMMANDS = {"doctor", "run"}` alongside the implicit `serve` (`run` is host-gated by `_BRISTLENOSE_HOSTED_BY_DESKTOP`; `doctor` is read-only and ungated, which is what lets the Health window shell out if it ever needs to). _Corrected 30 Jul 2026 — this line previously read "serve-only … its sole command is `serve`", which misled an assessment of whether `doctor` could run in the bundled app._ Serve preflight runs exactly one check, `serve_deps` (an import-presence probe that returns in milliseconds; it was listed but never dispatched until 11 Oct 2026, `fd6286ee`), so the hang is the exec/validation, not any doctor check.

- **When adding a new `PipelineState` case, audit `applyScanResult` for the early-return list.** `PipelineRunner.applyScanResult` guards the runner-owned states (`.running` / `.queued` / `.failed` / `.completedPartial` / `.failedWithDiagnostic`) from being clobbered by passive manifest scans. The two new diagnostic states added in `pipeline-diagnostic-popover-swift` weren't initially in this list; harness-injected state would render once then get reverted within seconds when the next scan ran. Class-of-bug rule: every new `PipelineState` case is presumed runner-owned (= early-return) unless you can prove otherwise. The compiler doesn't help here — `switch` over `PipelineState` in `applyScanResult` has a `default` arm. Audit it manually on every state addition. **And audit `PipelineState.keepsMachineAwake`** (next gotcha) — a new "work is executing" case must return `true` there or a run in that state will let the Mac idle-sleep.

- **Idle-sleep is held off during a run via `RunSleepAssertion` (`ProcessInfo.beginActivity(.userInitiated)`), driven off `state.didSet`.** A long unattended analysis on AC power used to freeze at the idle-sleep timer (the run didn't fail — it *stalled* until the user woke the Mac, reading as "the appliance gave up"). `PipelineRunner` now holds a `RunSleepAssertion` and, on every `state` mutation (`didSet → syncSleepAssertion`), sets it held = `state.values.contains(where: \.keepsMachineAwake)`. `keepsMachineAwake` is **`.running`-only** — `.queued` is deliberately excluded (the dequeue gap is sub-second, far below any idle-sleep timer; reviewers split on this, see the doc-comment). Design choices that are load-bearing, not incidental: **(1) `.userInitiated`, not `.idleDisplaySleepDisabled`** — disables idle *system* sleep but lets the display dim (no reason to burn the backlight for an unwatched job; `pmset -g assertions` shows one `PreventUserIdleSystemSleep` and NO display assertion, the considerate signal a Mac power-user checks for). **(2) It does NOT prevent *forced* sleep** — lid-close on battery sleeps the Mac regardless; that's an OS guarantee, and recovery is the resume path's job, not the assertion's. **(3) Driven off `state` (single source of truth), not instrumented per start/attach/exit site** — `state` only mutates on coarse transitions (progress churn lives in `liveData`, not `state`), and `setHeld` is idempotent, so it can't thrash or leak. **(4) `beginActivity` is sandbox-clean** (process-local power hint, no entitlement — unlike the `proc_listpids`/`security`/`lsof` execs that this file is otherwise scar tissue from). The `reason` string omits the app name (`pmset` already attributes it to `app.bristlenose`) and says "Analysis" not "pipeline" per the chrome convention. Edge machine + `keepsMachineAwake` mapping unit-tested in `RunSleepAssertionTests.swift` (begin/end injected, real `ProcessInfo` untouched).

- **A reconnected (orphan-attached) run reads "Resuming…", not "Analysing…", in the row subtitle.** `PipelineProgress.attachedFromOrphan` (set once at orphan-attach, `PipelineRunner` ~`:598`) was previously *set but never read*. It now feeds `RunProgressSubtitle.compose(resuming:)` via both callers (`ProjectRow.runningSubtitle`, `SidebarSubtitleText.activityText`). `resuming` swaps the generic lead verb "Analysing" → "Resuming" **only in the indeterminate gap** (no known stage yet) — the moment a real `run_progress` stage event flows, the stage verb leads ("Transcribing · 7 of 8 · …") and the resume is self-evident from motion. _Since 20 Oct 2026 (R19) an attach is rare and brief — a run stops itself when the app goes, so "Resuming…" is usually followed by Stopped within a second; a long one now means a run wedged in a C call. A second copy of the app no longer attaches the first copy's live run (decision #12, 22 Oct 2026): its parent is alive, so the second copy reads it off disk as a run it doesn't own._ This is the HIG-endorsed silent-inline-recovery pattern (no banner, no toast — `absence is information`); "Resuming…" earns its keep by narrating the otherwise-suspicious quiet moment right after relaunch. Locale key `chrome.pipeline.resuming` in all 7 `desktop.json`. The `attachedFromOrphan` flag never clears, so correctness rests on callers only consulting it while `.running` (true today — `ProjectSubtitle.resolve` owns terminal states); a fresh owned spawn writes a new `PipelineProgress` with the flag `false`. Tests: `RunProgressSubtitleTests.resuming*`.

- **Two writers on one reference, and the order between them decided by whether a sidecar was WARM.** `BridgeHandler.webView` — the outbound channel every native lens affordance dispatches through — was registered by `WebView.makeNSView` and cleared by `BridgeHandler.reset()` (per selection change). Nothing at either call site hints that their order varies, and it does: when the incoming project's sidecar is **already running**, SwiftUI builds the detail WebView in the *same update pass* as the selection change, so `makeNSView` registers first and `reset()` then wipes the fresh registration — **permanently**, because nothing re-registers (`updateNSView` doesn't). From a **cold** sidecar the order reverses and everything works. Net effect (1 Sep 2026): switching from a failed project to a good one left every sidebar lens row, the rail and ⌘1–⌘5 dead, while reaching the same project from Welcome worked. **The app looked entirely healthy** — *inbound* messages reach the Coordinator directly, so the lens capsule still tracked routes, in-page links still navigated, and only the app's own controls did nothing. **Rule: a reference whose lifetime belongs to a view is written by the view alone** — `makeNSView` registers, `dismantleNSView` deregisters **identity-guarded** (SwiftUI may build the replacement before tearing down its predecessor, so an unguarded clear reproduces the same wipe from the other side). Anything that needs "don't dispatch into the old document" asks the state machine (`documentState` → `.loading` → activations queue), not a second writer. **Two tells:** an affordance that works on one route into a state and not another (that asymmetry IS the ordering); and — the reason this survived so long — a `guard let x else { return }` on an outbound path that says nothing, so log every dropped dispatch. Pinned by `BridgeChannelOwnershipTests`; the diagnosis came from `documentState`/`activateLens` `.notice` logging, which is why it stays.

- **`ServeManager.start()` MUST reset `authToken` (and `serverVersion`) — `handleLine`'s capture is guarded `if authToken == nil`, and `switchProject` parks (doesn't stop) the outgoing sidecar.** The stdout capture at `handleLine` only grabs `[bristlenose] auth-token: <token>` when `authToken == nil` (so a parked sidecar's late line can't overwrite the fronted token — that routing is by `ObjectIdentifier`). But `switchProject(to:)`'s cold path *parks* the outgoing sidecar (`process → nil`) instead of `stop()`-ing it, so the defensive `stop()` at the top of `start()` doesn't fire and the previous sidecar's `authToken` lingers non-nil → the new cold-started sidecar's auth-token line is **skipped** → `authToken` points at the WRONG sidecar. The detail-pane WebView authenticates by **cookie**, so it keeps rendering — masking the staleness completely; the breakage only shows on a consumer that uses `authToken` as a **bearer header**. The native `MiroAPI` was the first such consumer, so Send-to-Miro → Connect returned the local bearer middleware's `{"detail":"Unauthorized"}` (NOT a Miro error — Miro says `Invalid Miro token: …`) after any project switch. First project after launch always worked (authToken starts nil), which made it look token-specific (the user even recreated the Miro app — a red herring). Fix (`6dc94a9a`): `start()` nils `authToken`/`serverVersion` after the `outputLines = []` reset, mirroring `stop()`/`shutdown()`. The warm re-point path (`adoptFronted`) sets `authToken = entry.authToken` directly and never hits `start()`, so it's unaffected. **Rule: any new native localhost client that sends `authToken` as a bearer depends on this reset — and "the WebView works" is NOT evidence the token is fresh (cookie auth ≠ bearer auth).** When a native API call 401s but the report renders, suspect `authToken` staleness first, and confirm the 401 string is the middleware's `"Unauthorized"` vs a route's specific detail.

- **Zombie cleanup is delegated to the sidecar (Apr 2026, A6 redesign).** The host no longer enumerates orphans — sandbox blocks `proc_listpids` anyway. The sidecar's parent-death watcher (`bristlenose/server/lifecycle.py`) self-terminates within ~2s of a host crash. The host uses `bind(0)` so a slow-dying orphan can't collide. External-server scheme is unaffected (`BRISTLENOSE_DEV_EXTERNAL_PORT` set → host doesn't spawn anything, doesn't set the watcher env var).

## Sidebar, toolbar and window layout

- **`NavigationSplitView`'s `columnVisibility` binding is not only your writes — AppKit reports each animation's END state into it, and a second write inside the first's animation gets those reports one write late.** Measured 28 Sep 2026 (`SidebarFitHarnessTests` s11, s22c, s23, s24): collapse, expand before it finishes, and the binding later receives `.detailOnly` — after the expand, with no write behind it — landing 11–281 ms after the app's last write locally, later on CI. So any state *inferred from a binding change* ("it became visible, so the researcher showed it") can be forged by a stale report, and any single geometry reading mid-animation can look like rest. `SidebarAutoCollapse` now takes ownership at its own collapse write, gives it up only on a resting reading, and treats a hide within `lateReportWindow` of its own write as its own (`DetailFloor.swift`). **Test trap that hid it for a week:** a Mac usually sends one *more* report and the column recovers by itself, so an assertion on the end state passes locally and fails on the runners. Assert the invariant at every report instead (`hiddenNotOurs` in the harness) — a self-correcting race is invisible to an end-state check.

(2) The obvious workaround — set `isHidden` and animate the width to zero — has a memory: the header states the hidden flag "is stored out when the NSTableView automatically saves out NSTableColumn state", so on a table with `autosaveTableColumns = true` a column hidden because the data was absent stays hidden after the data arrives. **Remove the column instead; removal carries no such state.** Live example: the cloud-import grid drops its Scheduled column when a listing carries no scheduled times (`syncScheduledColumn` in `CloudImportOutlineView.swift`, twin of `syncExpiresColumn`). Decide the set at mount, before the first `reloadData()`, or there is a frame in which the wrong column exists.

- **A column width set in code does not reach the layout until the table RE-FITS — and nothing re-fits at mount.** Measured 30 Sep 2026 (`.inset`, uniform autoresizing, Darwin 27): after `column.width = 240`, `rect(ofColumn:)` and the cell frames stayed at the old width through `tile()`, `layoutSubtreeIfNeeded` and a run-loop pass; only `sizeToFit()` or a window resize applied it. So (1) geometry derived from `rect(ofColumn:)` mixed with live `width`s is wrong after any change — re-fit first; and (2) a table whose scroll view is placed and sized after creation (SwiftUI's order) keeps its *declared* widths: the cloud-import grid opened as ~980pt of table in a 900pt window, with Status partly off the right edge — "✓ Impor" with an always-visible scroller. `CloudImportOutlineView.reportMinimumWidth` now `sizeToFit()`s on entering a window (`OutlineView.viewDidMoveToWindow`) and when the column set or a minimum changes, never on a progress tick. **Tell:** a last column clipped by the window edge rather than truncated with an ellipsis.

- **`.contextMenu` on a toolbar-hosted view is swallowed by macOS's "Customize Toolbar" menu — don't use it for debug/QA affordances on a `ToolbarItem`.** Right-clicking a toolbar item triggers the system toolbar context menu (Customize Toolbar…), not your SwiftUI `.contextMenu`, so a right-click "force state" gallery on a toolbar pill silently does nothing (same family as the `.onAppear`-on-toolbar-items unreliability above). For a DEBUG state harness that needs to drive a toolbar pill through its states, use the menu-bar Diagnostics menu's `#if DEBUG` harness section instead (Section 3 in `DiagnosticsMenuContent`, `MenuCommands.swift`) — it's reliable, discoverable, keeps the popover visually clean for screenshots, and (unlike a context menu on a self-hiding pill) is reachable even when the pill is idle, so forcing a scene can resurrect it. Pattern: `DebugMenuContent` View in `MenuCommands.swift` holding `@ObservedObject var ollamaDownload`; the Diagnostics menu is the 9th top-level element so it fits under the CommandsBuilder 10-cap. Hit on `beat3-provider-activation` 4 Jun 2026 — the pill's right-click harness never fired; replaced with the menu-bar menu (`065698a`).

- **Porting a mock illustration into a Swift webview string (`WelcomeIllustrationHTML.<name>`): three string traps + a build-free verify.** The study-tools + science illustrations are `docs/mockups/*.html` ported verbatim into a Swift `"""…"""` (autocode, manualTags, signal, quote, emergentThemes). Traps: (1) use **literal unicode** chars (`“`, `✓`, `—`) in the embedded HTML/JS — NOT `\uXXXX` JS escapes, which collide with Swift's `\u{…}` and won't compile; (2) no `\(` anywhere in the embedded CSS/JS except the intended interpolations (Swift reads `\(` as string interpolation), and no `"""`; (3) verify without a full Xcode build — extract the HTML (regex between the `"""` markers), substitute the three interpolations (`dark`/`palette`/`reduce`), then `node --check` the `<script>` and brace-count the `<style>` (caught every real error this way; `xcrun swiftc -parse` on the file catches Swift-side syntax). Every such illustration must gate on `@Environment(\.welcomeAnimationActive)` (`reduce = reduceMotion || !active`, folded into `.id()`), declare a `WelcomeIllustration.welcomeTurn` base so it joins the `WelcomeBaton` (one animation at a time), and route **every duration through `WelcomeTempo`** (14 Aug 2026): webviews bind `let kind` and interpolate `var PACE=\\(WelcomeTempo.jsStretch(for: kind)), LEAD=\\(WelcomeTempo.jsLeadMs);` with a `sleep()` that scales by PACE and a `setTimeout(run, LEAD)` kickoff; natives use `WelcomeTempo.stretch(for:)` / a `nap(_:)` helper. Never hardcode a raw beat — the group knob (`speed`) and per-illustration `pace(_:)` must reach it, and every play rests ~3s on its opening and finished frames (`leadInSeconds`/`holdEndSeconds`, absolute). The six remaining study-tools illustrations follow this pattern — `docs/design-welcome-studytools-illustrations.md`.

- **A welcome illustration's left edge is set TWICE — the Swift frame is the settled owner (14 Aug 2026); illustration content starts at x = 0.** `slotView` frames every illustration flush to the cell's 16pt content edge (`alignment: .leading`, no horizontal padding) — correct, and now canonical (`design-welcome-screen.md` §Cell 1): an illustration adds **no horizontal padding of its own**. The full-width `.agentChat`, the `.miro` stickies, and the native `.ingest`/`.clips` comply. The four older webviews still add their own `body{ padding: … }` on top — `.autocode`/`.manualTags` `2px 12px`, `.tag` `10px 14px`, `.starHide` `9px 14px` — so their drawn content sits **28–30pt** from the cell edge while the tag / title / body line / CTA sit at **16pt**. The tell is a cell whose illustration is visibly indented relative to the text above it. Vertical doubles the same way (`.padding(.vertical, 8)` in Swift **plus** the HTML's own 2/2/10/9). `.signal` additionally doesn't use flow layout at all — `position:absolute; left:50%; transform:translate(-50%,-50%) scale(s)`, horizontally centred and drifting with cell width, contradicting §2's "no cell centres its content" (`.agentChat` was re-authored out of that shape, 14 Aug 2026). When zeroing `.tag`/`.starHide`, note the left gutter is load-bearing (the pointer arcs in and the keycap presses there, with `body{overflow:hidden}` ready to clip them) — pull the card onto the edge rather than merely deleting the padding.

- **`fit()` clamps at `Math.min(0.9, …)`, so a bigger frame buys AIR, not content.** `.signal` — the one remaining centre-scaled illustration (`.agentChat` was re-authored to full-width normal flow, 14 Aug 2026) — computes `s = Math.min(0.9, (innerWidth-8)/w, (innerHeight-8)/h)`, so it can never exceed 90% of natural size. The four flow ones are `body{display:flex; align-items:center}`, which centres a fixed-height composition in whatever height it gets. So **relaxing an illustration's SwiftUI frame changes nothing visible**: to make one use more space it has to be re-authored to stretch (ideally by showing *more* — measure the box, add items until the next won't fit — rather than scaling one composition, since the box's aspect ratio swings ~2.2:1 → ~1.4:1 across cell sizes). Prototype in the mockup's **⌗ Full-bleed slot** section; decision recorded in `design-welcome-screen.md` §2.

## Lists, drag and drop, and navigation

- **`List(selection: Set<SidebarSelection>)` for multi-select** — Cmd+click and Shift+click work natively with `Set` binding. `soleSelection` helper derives single-item state for serve/persist. Bulk delete via menu notifications filters by type (projects only, folders only)

- **`Project.position` / `Folder.position` for sidebar ordering** — `Int` field, auto-assigned on creation (new items get 0, existing pushed +1). `.onMove` on `ForEach` handles drag-to-reorder. Backward compat: old `projects.json` without `position` defaults to 0; first load backfills positions from `createdAt` order

- **`SidebarSelection` enum for mixed-type selection** — `List(selection:)` binds to `SidebarSelection?` (`.project(UUID)` or `.folder(UUID)`) instead of `UUID?`. This lets projects and folders share the selection space while remaining type-safe. `@AppStorage("selectedProjectID")` only persists project selections (folders don't open a report). `DisclosureGroup` label `.tag()` propagates correctly — folder rows are selectable

- **View-based `NSOutlineView`/`NSTableView` inline rename: begin with `editColumn(_:row:with:select:)`, NOT `makeFirstResponder(field)` + `selectText(nil)`.** The intuitive pair *looks* right and half-works: the field draws its bezel and shows the name selected — but the **outline stays first responder**, so every keystroke goes to NSOutlineView's **type-select** instead of the field. Symptom is maddeningly specific: the row visibly enters edit mode, the text is selected, and typing does *nothing* (while typing works everywhere else in the app). `editColumn` is the canonical view-based begin — it engages the table's editing session and installs the window field editor as first responder. Belt-and-braces: also override `validateProposedFirstResponder(_:for:)` to `return true` for editable `NSTextField`s, because the default table implementation can *refuse* the field even after `editColumn` (same silent symptom). Cost a build cycle on 28 Jul 2026. **Second, load-bearing half — the reload guard:** a field editor is a subview of the edited cell, and `ProjectSidebarOutline.update()` calls a full `reloadData()` on every `liveData` tick (~1 Hz+ during a run), which tears the editor down mid-type and eats the keystrokes. Track an `editingNodeID` and skip the reload (in `update()` **and** `paletteDidChange()`) while it's non-nil — during an active edit the correct number of reloads of that row is **zero**, even a targeted `reloadItem`. The *other* rows still redraw: `update()` reloads them in place with `reloadData(forRowIndexes:)` when the rows are unchanged, or every run's progress freezes while a name is typed (R56, 21 Oct 2026). Clear `editingNodeID` *before* mutating the model, or the republished `update()` sees the guard still set and never reloads. Full mechanism + the slow-second-click guards: `docs/design-desktop-sidebar-appkit.md` §2.6.

- **Segmented Picker requires non-optional selection** — `Binding<Tab?>` doesn't work with `.pickerStyle(.segmented)`. The `tabBinding` in ContentView maps nil to `.project`

- **Tab.from(path:) prefix order** — check longest prefixes first (`/report/signals` before `/report/`). The project tab uses exact match to avoid matching all paths. The legacy `/report/analysis` prefix is checked too and also returns `.signals` — the lens was renamed in 0.30.0 and a bookmarked path must still land

- **`.onReceive` is a View modifier, not Scene** — attach it to the root View inside WindowGroup, not to the WindowGroup itself. The publisher is `NotificationCenter.default.publisher(for: NSApplication.willTerminateNotification)`

- **Don't replace `.pasteboard` in Commands** — `CommandGroup(replacing: .pasteboard)` removes Cut/Copy/Paste. WKWebView handles these via the responder chain. Only replace `.undoRedo` (for app-level undo) and `.help`

- **`@AppStorage` not `@SceneStorage` for project selection** — `selectedProjectPath` uses `@AppStorage` so the last-opened project persists across app launches. `@SceneStorage` doesn't survive relaunch for unsigned/debug-signed apps (macOS state restoration requires proper code signing). Xcode debug runs also reset scene storage between launches. Use `@AppStorage` for anything that must persist across relaunches

- **Navigation shims use module-level refs (not closures)** — `installNavigationShims()` in `frontend/src/shims/navigation.ts` stores `navigate` and `scrollToAnchor` in module-level variables. The `window.switchToTab` etc. functions read from these refs instead of closing over the parameters directly. This prevents a stale-closure bug where the initial `navigate` captured at mount doesn't work until the router is fully ready. The `useEffect` in `AppLayout.tsx` calls `installNavigationShims` on every `navigate`/`scrollToAnchor` change — the window functions are installed once (idempotent guard) but the refs always update

- **List selection must bind to `UUID?`, not a value-type model** — `List(selection: $selectedProject)` where `selectedProject` is `Project?` (a struct) breaks when any field on the selected project mutates (e.g. `updateLastOpened` changes `lastOpened`). SwiftUI compares the selection value against the list items by hash — if the hash changed, selection drops (flashes blue then deselects). Fix: bind to `$selectedID` (`UUID?`) and derive `selectedProject` as a computed property. UUIDs are stable across field mutations

- **ALL tap gestures on List rows break selection on macOS 26** — both `.onTapGesture` and `.simultaneousGesture(TapGesture())` on views inside `List` rows interfere with the List's built-in selection binding. `.onTapGesture` swallows the click entirely (row flashes but selection never commits). `.simultaneousGesture` works intermittently (selection sticks after 1 click then stops responding). This was confirmed with macOS 26.1 + Xcode 26.3. **Do not put any SwiftUI gesture recognisers on List row content.** _Slow-double-click rename was parked on this constraint ("needs NSEvent local monitor or AppKit subclass") — **UNPARKED 28 Jul 2026**: the AppKit subclass is exactly what shipped. `SidebarOutlineView` + `outlineView.action`/`doubleAction` with an `NSEvent.doubleClickInterval`-deferred arm (`ProjectSidebarOutline.swift:612-659`). Gesture-vs-selection interference doesn't arise on the AppKit path because the table owns both. The SwiftUI constraint above still holds for the flag-off path._

- **`.onDrop` on individual List rows breaks selection** — per-row `.onDrop(of:)` causes the same selection interference as tap gestures. _Historical note: workaround used to be `SidebarDropDelegate` + `RowFramePreferenceKey`/`FolderFramePreferenceKey` hit-testing on the List itself. Replaced May 2026 by per-row `.dropDestination(for: SidebarDrop.self)` — the newer `Transferable`-based API works on List rows without breaking selection. See next gotcha for the wrapper-Transferable pattern._ **RESOLVED 1 Aug 2026 (`bbda9a6a`) — and the superseded analysis below is why this paragraph keeps getting re-derived.** On the AppKit outline every case works through one unified insertion model: out of a folder, between folders, into a folder, and **within-scope reorder** (folders included — they became draggable in the same change). `DropRouting.resolve` returns one `DropPlan`; `ProjectIndex.apply(_:)` re-parents and renumbers `position` in every affected scope; the rows animate via `moveItem(at:inParent:to:inParent:)`. That also closed a latent ordering bug — `moveProject` used to set `folderId` and leave `position`, so a project leaving a folder carried its in-folder index into root and collided there, and the root sort has no tiebreak. Spec: `docs/design-desktop-sidebar-appkit.md` §3.3. _Superseded (18 Jun 2026): the per-container `.onMove` reorder-islands diagnosis — a drag can't cross a folder boundary, out-to-root has no internal-move target, Move-To covers it, POST-TF. That described the **SwiftUI `List`** path, which is not the sidebar the app runs._ **Still open: reorder has no undo** — see `docs/design-undo-debt.md`.

- **Never stack two `.dropDestination(for: T.self)` modifiers on the same view — use one with a wrapper `Transferable` exposing multiple `ProxyRepresentation`s.** Stacking is empirically broken on SwiftUI List rows and `DisclosureGroup` hosts (Apple DevForums thread 730367, FB12980427; WWDC22 Session 10062 "Meet Transferable"): the second registration silently fails to wire its closure, the drag shows refuse cursor, drop springs back. Sibling pattern on `ProjectRow` with one `.dropDestination(for: URL.self)` works fine. Canonical pattern is `SidebarDrop` in `desktop/Bristlenose/Bristlenose/SidebarDrop.swift` — an enum with `static var transferRepresentation: some TransferRepresentation` exposing each accepted type as a `ProxyRepresentation`; the single drop closure switches on the case. **Representation order matters** in the wrapper (primary first; fallback after); the receiver picks the first whose UTType the dragged item satisfies.

- **`.draggable(String)` auto-coerces to URL on the macOS pasteboard — use a typed `Transferable` newtype if you don't want URL.self drop targets to accept the drag.** Symptom on `sidebar-drop-folder-row` (May 2026): `.draggable(project.id.uuidString)` exported a String, but every `.dropDestination(for: URL.self)` in the sidebar (project rows, List-level Finder drop) lit up and accepted the internal drag, then routed it through the Finder-import path → wrong handler, project rows highlighted as drop targets during internal moves. Fix: `ProjectDragID` `Codable, Transferable` with `CodableRepresentation(contentType: .bristlenoseProjectDragID)` and a custom `UTType(exportedAs: "app.bristlenose.project-id", conformingTo: .data)`. Anchoring `conformingTo: .data` is load-bearing — without it the UTType inherits a default that URL-adjacent receivers may still accept. Same lesson applies any time you want a drag payload that strictly does NOT match URL.self.

- **`Label { ... } icon: { ... }` only takes content width — stretch to row width before attaching `.dropDestination` or `.contentShape`.** `FolderRow`'s `Label` had narrower hit-area than the rendered row in the sidebar — drops over the empty space right of the folder name fell through to the parent. Add `.frame(maxWidth: .infinity, alignment: .leading)` then `.contentShape(Rectangle())` to make the entire row width hittable. Same caveat applies wherever a row-shaped view in a SwiftUI `List` uses a Label-based body

- **`.contextMenu` on List rows does NOT break selection** — unlike gestures and drop targets, `.contextMenu` on rows works correctly. Right-click shows the menu, left-click selects. Context menu can live on the row (after `.tag()`) or inside the row View

- **`DisclosureGroup` inside `List` works for one-level folders** — `DisclosureGroup(isExpanded:)` binding reads from `Folder.collapsed` (inverted). The expand/collapse state is persisted in `projects.json` via `setFolderCollapsed()`. If nested folders were ever needed, `OutlineGroup` would be required instead

- **`Folder.collapsed`/`createdAt` backward compat** — old `projects.json` files have `FolderStub` shapes (just `id` and `name`). `Folder.init(from:)` uses `decodeIfPresent` with defaults (`collapsed = false`, `createdAt = Date()`) so old files parse correctly

- **Drag-and-drop uses async URL loading** — `NSItemProvider.loadItem` callbacks run on background threads. Use `withTaskGroup` + `withCheckedContinuation` to collect all URLs, then `await MainActor.run` to process. Never mutate `@State` or `@Published` from the callback directly

- **Empty-space deselection in `List(selection: Set<>)` on macOS 26** — `List(selection: $selection)` with a `Set` binding no longer auto-deselects when clicking empty space on macOS 26. SwiftUI gesture workarounds (`DragGesture(minimumDistance: 0)` as `.simultaneousGesture`) don't fire reliably. Fix: `SidebarDeselectMonitor: NSViewRepresentable` with `NSEvent.addLocalMonitorForEvents(matching: .leftMouseDown)`. In the handler, find the sidebar `NSTableView` (first table view in the window — WKWebView detail has none), convert the click to table coordinates, call `row(at:)`. If it returns -1 (click below all rows and within the table bounds), clear `selection = []`. Always `return event` to pass through

- **`NSOutlineView` variable row heights need `rowSizeStyle = .custom` — every other style silently ignores `heightOfRowByItem`.** The source-list cell (`ProjectSidebarOutline.swift`) sets per-row heights via the `heightOfRowByItem` delegate (single-line idle rows vs two-line status rows, `ProjectCellSpec.rowHeight`). But `rowSizeStyle` defaults to `.default`, and `.default`/`.small`/`.medium`/`.large` all pin a FIXED style height and **never call** the delegate — no error, no warning, the height work is simply **inert** (rows stayed cramped ~25pt vs the native 32pt source-list pitch). Only `.custom` consults `heightOfRowByItem`. This cost a full QA round: a row-pitch "fix" was committed and did *nothing* until `.custom` was set (`ProjectSidebarOutline.swift:126`). **Rule: set `rowSizeStyle = .custom` whenever you implement `heightOfRowByItem`** — you then own ALL row heights **and** the icon sizing (the style's automatic source-list icon sizing is gone, so set an explicit `NSImage.SymbolConfiguration(pointSize:)`; a bare `.medium`-scale config renders smaller than native, and a too-tight icon-column width then down-scales it further — two compounding ways to get cramped icons). Height + icon size are then pixel-tuned against native in Pixelmator; the measured constants live in `ProjectCellSpec` (32pt pitch, icon pointSize 16, 20pt column — all confirmed against Finder/Notes/Mail overlays, 22 Jun).

- **SwiftUI List inter-row gap steals drops from per-row `.dropDestination` modifiers.** `List` inserts a few pixels of vertical spacing between rows; that gap falls outside each row's drawn frame, so drops there bypass the per-row handler and hit the List-level fallback. Symptom: green+ cursor appears, drop creates a project at root instead of inside the folder the user was clearly aiming at. Fix: `.padding(.vertical, 2)` on the row content BEFORE `.contentShape(Rectangle())` (FolderRow) or before the drop-target overlay (ProjectRow) so the captured row frame extends to cover the inter-row gap. Pre-existing `RowFramePreferenceKey`/`FolderFramePreferenceKey` machinery is gone now (per-row `.dropDestination` handles hit-testing internally), but the gap-coverage padding pattern is still needed

- **AppKit `NSOutlineView` mode rows: fire click side-effects from `selectionIndexesForProposedSelection`, NOT `shouldSelectItem`; detect the click from the proposed set, NOT `clickedRow`/`NSApp.currentEvent`.** The flag-gated source-list sidebar (`ProjectSidebarOutline.swift`, `BristlenoseAppKitSidebar`) folds the 5 mode rows (lenses) into the same outline as the project list — kept *genuinely* selected so the table draws the exact system source-list capsule, but filtered out of `SidebarSelection` (lens nodes return `nil`). Two non-obvious delegate traps, each cost a debugging session (full write-up `docs/design-desktop-sidebar-appkit.md` §6; both marked DEAD END in the code): **(1) `shouldSelectItem` is NOT consulted for a row that won't end up selected.** When `selectionIndexesForProposedSelection` overrides the proposal to keep the project, the table never calls `shouldSelectItem` for the clicked lens — so a side effect fired there (`onActivateLens`/`switchToTab`) silently never runs (zero `shouldSelect` lines in the live trace). Put activation in the proposal handler, the one delegate reliably handed the clicked lens. **(2) `clickedRow` + `NSApp.currentEvent` event-gating misfires inside the proposal handler.** At the instant it runs, `currentEvent` is not a `.leftMouseDown` on a genuine click, so an `isMouseClick` gate reads `clickedRow == -1` → the proposal resolves to *deselect* → the project is dropped ("No Project Selected"). The reliable signal is the **proposed set itself**: AppKit puts the clicked (even unselectable) row INTO `proposedSelectionIndexes` — read the mode-click from that, no event introspection. Both lessons reduce to: **read the table's own truth; don't reconstruct user intent from `NSApp.currentEvent`.** Related: the active-lens capsule follows `activeTab` *honestly* (lags the async `switchToTab` route by one cycle) — optimistic pre-selection flickers because `update()` re-runs `applySelection` faster than the route resolves.

## SwiftUI and AppKit mechanics

- **`@ObservedObject` in a `Commands` struct is unreliable AND expensive** — use `let` (plain property) on the `Commands` struct, then `@ObservedObject` inside the `View` structs that are the content of `CommandMenu`/`CommandGroup`. Unreliable: it doesn't dependably re-render the body. Expensive: it still subscribes to the whole object, so every publish rewrites the whole menu bar, and an open Window menu collapses to its short form (see the pattern note above). See `MenuCommands.swift`

- **Porting a SwiftUI two-way binding to AppKit splits it into a read and a write — and the write is the half that goes missing.** The entry above is one expression carrying both halves: `DisclosureGroup(isExpanded: Binding(get: { !folder.collapsed }, set: { setFolderCollapsed(…) }))`. The AppKit outline ported the `get` into `reloadAndRestore()` and nothing ported the `set`, so a collapse lived only in the view, and the next `update()` — any selection change, any run's progress tick — sprang every folder open. It survived three months because every half that existed was correct and every test asserted the tree, never what a click writes. **When porting a `Binding(get:set:)` to a delegate, name the AppKit callback that calls the `set:` closure's callee before calling the row done** (here `outlineViewItemDidCollapse`/`DidExpand` → `setFolderCollapsed`, fixed 25 Sep 2026). **Tell:** state that holds until the next unrelated republish. `SidebarOutlineExpansionTests` is the harness for this class — it drives the real controller with no window.

- **`@Environment(\.dismiss)` is INERT inside an AppKit `NSPopover` — and it fails by looking fine.** A SwiftUI view hosted via `NSHostingController` inside an `NSPopover` has no SwiftUI presentation for `dismiss` to act on, so the call compiles, runs, and does nothing. The popover is held by the *controller*, and only the controller can close it. `IconPickerPopover` gets this right (an explicit callback → `self?.activePopover?.close()`); `ProjectDiagnosticPopover.showLog()` does not — its `dismiss()` has never worked, masked entirely because `.transient` closes the popover on the focus change when Console.app opens. **The mask is the whole trap**: a no-op dismiss is invisible whenever the action you just took happens to steal focus, and glaring the moment it doesn't (an Analyse button that starts a run and leaves the popover sitting there). **Rule: any SwiftUI view you present through `showRowPopover` closes via a caller-supplied callback, never `dismiss`.** Same family as the `.onAppear`-on-toolbar-items entry below — a SwiftUI lifecycle hook whose firing rule belongs to AppKit. (27 Aug 2026.)

- **Many-item page dots → windowed indicator, not one dot per item.** A `SlotRotator` with ~24 tips can't show 24 dots (≈400pt, overflows the cell). Prior art (iOS UIPageControl many-pages / Instagram `ScrollingPageControl`): cap the visible dots to what fits the row (`⌊width / pitch⌋` via `GeometryReader`) AND a legibility cap (HIG: >10 dots are hard to count at a glance); slide the window to keep the active dot central; shrink the outermost dot on any side that still has hidden items (the shrink is the "more that way" cue and fakes the motion). Full list stays reachable via arrows/swipe/chevrons + the a11y value ("n of total"). `SlotRotator.dots` in `WelcomeHomeView.swift`.

- **`.opacity` on a SwiftUI container fades each LEAF, not the container — overlapping children show through each other.** Put `.compositingGroup()` before the `.opacity` whenever the children overlap. The Welcome book shelf's resting curtain (`WelcomeTempo.restOpacity = 0.7`) made each cover and its shadow 70% on its own, so the back covers showed through the front one. That read as a cross-fade stuck halfway, and it shipped in 0.31.0–0.31.3 (fixed `6da68bce`, 27 Sep 2026). It only looked right while the cell was playing at 1.0, which is why it passed as "intermittent". Proved with an `ImageRenderer` probe: two overlapping rects at 0.7, sampled in the overlap, blue channel 0.83 without the group vs 1.00 with it. **Tell:** a fade that looks right on side-by-side content (chips, rows) and wrong on stacked content (cards, a menu over rows).

- **An `@EnvironmentObject` injected into only *some* scenes is a launch crash, not a nil — and the test host reports it as infrastructure.** Adding `@EnvironmentObject var cloudImport` to `ContentView` while injecting it only into the import `Window` scene traps in `EnvironmentObject.error()` the first time that body reads it. The app dies at startup, and `xcodebuild test` surfaces it as **"the test runner crashed before establishing connection"** — which reads like a wedged host or a DerivedData problem, and sends you to the wrong page of this file entirely. The crash report in `~/Library/Logs/DiagnosticReports/` names the property directly, so read that before touching the build. **Rule: an `@EnvironmentObject` read by a view reachable from more than one scene must be injected into every scene that can reach it** — the compiler checks the type and nothing checks the wiring. Found 18 Aug 2026 during the cloud-import sidebar ring; the window between the `ContentView` edit and the fix was one in which plain Cmd+R would not start the app.

- **Don't hang a lifetime on a third-party package's view-lifecycle callback.** `MCPAgentsSettingsView`'s revocation receipts were cleared in `.onAppear`, on the reasoning that the Settings package builds panes once and keeps them, so appear means "the pane was shown". It fires in **both** wrong directions. Too often: `SettingsTabViewController.animateTabTransition` calls `transition(from:to:)`, which removes and re-adds pane views — so switching to Appearance and back erased state the user had just created. Too rarely: `show(pane:)` early-returns when the pane is already active and `showWindow` never touches the view hierarchy, so ⌘W-then-⌘, may not fire it at all, and a menu item that deep-links to an already-open pane is a guaranteed no-op. The general rule: if a piece of state has a defined lifetime ("this visit", "until the window closes"), bind it to an event **you own** — `NSWindow.willCloseNotification` matched by object identity, a timestamp you compare — not to a SwiftUI callback whose firing rule belongs to AppKit and a vendored package. Same family as "`.onAppear` is unreliable on toolbar items" below, one layer up: there the callback never fires, here it fires on the wrong events. (21 Aug 2026.)

- **`Logger` takes an interpolation literal, not a `String` expression.** `log.notice("a" + (flag ? "b" : "c"))` fails with *"cannot convert value of type 'String' to expected argument type 'OSLogMessage'"* — the message must be a literal so the format can be built at compile time. Branch to two whole `log.notice("…")` calls rather than composing the string.

- **The `Settings` package's namespace enum collides with SwiftUI's `Settings` scene — reference the package types through `PkgSettings`.** Sindre Sorhus's `Settings` package (used for the Settings window) declares a top-level `enum Settings`; SwiftUI declares a top-level `struct Settings` (the scene). Any file importing BOTH sees `Settings` as ambiguous, so `Settings.Pane` / `Settings.PaneIdentifier` won't compile there (`'Settings' is ambiguous for type lookup`; it resolves to SwiftUI's, which has no `.Pane`). Module-qualifying as `Settings.Settings` **stays ambiguous** on the leading `Settings`. The fix (`SettingsPackageAlias.swift`): a `typealias PkgSettings = Settings` in a file that deliberately does **not** `import SwiftUI`, so `Settings` there resolves unambiguously to the package. Use `PkgSettings.Pane` / `PkgSettings.PaneIdentifier` everywhere else. (26 Jul 2026, Settings-package migration — cost the whole build until the SwiftUI-free alias file landed.)

- **AppKit reveal/overlay animations must read the cell's icon frame AFTER layout.** In `ProjectSidebarOutline`, reading `iconView.frame` immediately after `reloadData` returns `.zero` (Auto Layout hasn't resolved) → a 0×0, invisible overlay (the icon goes blank, then pops in with no animation). `maybeStartIconReveal` forces `outlineView.layoutSubtreeIfNeeded()` first, then converts the icon rect, with a static fallback if the frame is still unusable. See `docs/design-project-icons.md`.

- **`@MainActor` class static helpers need `nonisolated static` to be callable from `Task.detached`.** When a class is declared `@MainActor`, *all* its members inherit MainActor isolation — including `static` methods. A `Task.detached { … CopyMachinery.fileSize(of: url) … }` block fails with "main actor-isolated static method 'fileSize(of:)' cannot be called from outside of the actor." Mark the static helpers `nonisolated static` so they're callable from any context. Hit during `multi-project-drag-onto` `CopyMachinery` build (15 May 2026) — the actor itself is `@MainActor` (publishes `inFlight` for SwiftUI) but the FileManager/URL helpers it uses must run off-main inside the detached task. Same rule: `URL.resourceValues(forKeys:)` works fine off-main, only the actor's isolation rule fights you.

- **`.frame(width: 30, maxHeight: .infinity)` doesn't compile — "extra argument 'width' in call".** SwiftUI has two *separate* `.frame` overloads: the fixed one (`width:height:alignment:`) and the flexible one (`minWidth:idealWidth:maxWidth:minHeight:idealHeight:maxHeight:alignment:`). Mixing a fixed axis with a flexible one in a single call matches neither, and the error blames the *first* argument rather than the mix — which reads like "width isn't a real parameter" and sends you hunting the wrong thing. Fix: chain them — `.frame(width: 30).frame(maxHeight: .infinity)`. Common when building a fixed-width, full-height hit strip (e.g. `SlotRotator`'s chevron gutter in `WelcomeHomeView.swift`). Hit 15 Jul 2026.

- **macOS has no paging `TabView` — build carousels by hand.** `TabView { … }.tabViewStyle(.page)` is iOS/tvOS only; on macOS it renders as a plain tab bar (or fails), so every "swipe through cards" pattern needs building. Two macOS-native ingredients: an `NSViewRepresentable` overriding `scrollWheel` (read `scrollingDeltaX`, gate on `momentumPhase`/`phase` and add a short lock, or one flick fires a dozen steps) for trackpad/Magic-Mouse swipe, and `.accessibilityAdjustableAction` for VoiceOver (a content carousel has no selection model and doesn't need one). `NSPageController` exists but is heavy and animates whole views — if the content cross-fades in a fixed frame, you don't want it. Canonical: `SlotRotator` + `SwipeCatcher` in `WelcomeHomeView.swift`; design rationale in `docs/design-welcome-screen.md` §3a.

- **Hover-reveal chrome must key off hover ONLY — `@FocusState` persists after the pointer leaves.** A `revealed = hovering || focused` condition looks like generous progressive disclosure and ships as a bug: focus sticks once the view has been interacted with, so the chevrons/controls latch on and never hide again — and it presents as "hover isn't working" on *one* cell while identical cells behave, because only the focused one is stuck. Keyboard users are served by arrow keys / VO actions, not by the reveal. Hit 15 Jul 2026 on `SlotRotator` (Scientific-background cell stuck chevrons-on).

- **A full-bleed `.overlay` hit-strip (`contentShape(Rectangle())` + `.onTapGesture`) silently shadows leading-aligned interactive content beneath it.** `SlotRotator`'s edge chevrons were a 30pt-wide, *full-height* strip pinned `.overlay(alignment: .leading)` with an always-live tap gesture — so it sat directly on top of the leading-aligned `Learn →` link in the slot body and **ate every click** (ran "previous slide" instead of opening the URL). No error; the link just "doesn't work," and it affects all three rotator cells at once because they share the view. The fix (25 Jul 2026): scope the tap to the *visible control* (the disk band, `controlRow`-tall, bottom-aligned) not the whole strip, and add `.allowsHitTesting(revealed)` so the strip is inert unless the pointer is over the cell. Rule: an overlay that only *sometimes* shows a control must not hit-test its whole bounds — a hidden/edge tap column will shadow real content (especially leading-edge links). `WelcomeHomeView.chevron`.

- **Progressive disclosure in a fixed-geometry cell = `ViewThatFits(in: .vertical)`, and it must NOT carry `.fixedSize(vertical:)`.** The welcome Tip cell shows a core sentence always and a follow-up sentence *only when the (fixed golden-grid) cell can display the whole thing un-truncated* — that's exactly what `ViewThatFits` is for: give it two candidates (`core + more`, then `core`) and it renders the first that fits the cell's real height. The trap I hit (25 Jul 2026): adding `.fixedSize(horizontal: false, vertical: true)` to the candidates "to make the fit test honest" does the opposite — `fixedSize` forces each candidate to demand its full intrinsic height and **ignore the proposed size**, so (a) the chosen text overflows the fixed cell and visually balloons out of the grid, and (b) the fit test stops being responsive to cell size (every candidate reports full height regardless of space). Plain `Text` (no `fixedSize`) lets `ViewThatFits` measure the true wrapped height against the available height and pick correctly. Geometry stays fixed; content bends (`geometry_is_fixed_content_bends`). `WelcomeHomeView.tipBody` / `SlotItem.more`.
  **Two more rules, and a way to stop arguing about the third (22 Aug 2026, the diagnostic popover).** (a) **The greedy candidate goes last.** `ViewThatFits` picks the first child that fits and falls back to the last, so a `ScrollView` — greedy along its scroll axis — fits *every* proposal and must never lead; put it first and the ladder is dead code that renders perfectly. Same for any candidate carrying a `Spacer()` or `maxHeight: .infinity` (`WelcomeDegradationLab.swift:484` names this by its symptom). (b) **It needs a definite proposal in the measured axis.** With `nil` the first candidate trivially fits, and tall content renders un-scrolled and clips — no scroller, no error, no warning. (c) **Don't reason about whether it gets one — measure.** `NSHostingController(rootView:).view.fittingSize` is the size `NSPopover` and the Settings package both size from, it needs **no window and no running app**, and it works in a plain `@MainActor` unit test. Whether `.frame(maxHeight:)` reaches `ViewThatFits` as a definite proposal through a SwiftUI `.popover` was unanswerable from the layout docs and took one test to settle (it does). Assert *relationally* — taller content is taller, over-tall content measures exactly the ceiling — never in points, which pins a font metric and breaks on the next system font revision. `DiagnosticPopoverSizingTests.swift`.

- **SwiftUI view body too complex: extract into a `ViewModifier`, not more inline modifiers.** When the Swift type-checker bails with "the compiler is unable to type-check this expression in reasonable time; try breaking up the expression into distinct sub-expressions" on a SwiftUI `body`, the fix is to lift a chunk of `.sheet(…) .alert(…) .onChange(…)` modifiers into a dedicated `ViewModifier` struct and apply it via `.modifier(MyMod(…))`. Helps even when the contents are individually trivial — the type-checker's budget is per-expression, and bodies accrete modifiers across feature branches. Pattern: declare `private struct CopyDropPresentation: ViewModifier { … }` next to the View, take `@Binding` for state vars, the body's `content.sheet(…).alert(…)` collapses to one line in the parent. Hit during `multi-project-drag-onto` after adding NewFilesSheet `.sheet(item:)` + disk-space `.alert(…)` to `ContentView.body` (15 May 2026).

- **`isEditing` must learn that an edit ENDED from more than focus events — WebKit fires no `focusout` when the focused element is removed.** Enter on a quote edit unmounts the focused contenteditable; a heading editor drops `contenteditable` from the element that keeps focus. Neither fires focusout, so `editing-ended` was never posted, `isEditing` stuck at true, Edit ▸ Undo stayed hidden and ⌘Z went to WebKit's empty text undo — a committed quote edit could not be undone (owner QA, 4 Oct 2026; fixed `c4db0aef` with a `MutationObserver` in `useKeyboardShortcuts`' editing tracker). **Tell:** a menu item that should be there after an inline edit and only comes back once you click somewhere.

- **Undo/Redo editing guard (web editor only — a native field is `TextEditingFocus`, see Responder chain rules)** — when `isEditing`, the Undo/Redo menu items are hidden (not disabled) so Cmd+Z falls through to WKWebView's character-level text undo. When not editing, they intercept and route to the bridge. **Known HIG deviation:** this violates the "dim, never hide" menu principle. Hiding is necessary here because a disabled Cmd+Z menu item would still intercept the shortcut before it reaches WKWebView's responder chain — dimming prevents the key from falling through. Acceptable trade-off: character-level undo during text editing is more important than menu discoverability

- **SwiftUI `CommandsBuilder` caps at 10 elements per `body`.** Adding an 11th top-level `CommandGroup` / `CommandMenu` inside `MenuCommands.body` produces the misleading error `extra argument in call` on an unrelated `CommandGroup(...)` line — the result builder is bailing, the line it blames is just the first one past the cap. Fix: extract a related cluster into a child `Commands` struct (the four custom `CommandMenu`s for Project/Codes/Quotes/Video are grouped into `CustomMenus: Commands` for this reason). Same pattern as ViewBuilder's 10-view limit; same workaround. Hit 16 May 2026 when adding `Window > Bristlenose`.

- **macOS SwiftUI `.tint()` — five traps around palette-aware theming.** From the sidebar-four spike on `spike` branch (Jul 2026, commits `45abd972`→`9cf7f19a`):
  - **Doesn't cross `Scene` boundaries.** Each Scene body (`WindowGroup`, `Settings`, DEBUG `Window`) needs its own `.tint(color)` — a tint on `WindowGroup(id: "main")` does NOT reach the `Settings` scene. Symptom: Settings toggles/tab-icons stayed system-blue while the main window's SwiftUI accent had shifted to Edo. Fix: one `.tint(paletteAccent)` per scene body (`BristlenoseApp.swift`).
  - **Doesn't reach AppKit-wrapped controls.** `Toggle` (→ `NSSwitch`), `TabView` (→ `NSTabView`), `Picker` chevron all read `NSColor.controlAccentColor` directly at the AppKit layer, not the SwiftUI environment. Under a palette-aware tint they stay system-blue regardless. Consistent with what Xcode/Things/Bear/MarsEdit do under theme changes — usually the right answer is *accept*, per the seam-alignment discipline. If forced: custom `ToggleStyle` (~40 LOC per control) or `NSApp.appearance` override of `controlAccentColor` (hammer — hits every AppKit control system-wide, violates seam discipline).
  - **`layer.backgroundColor` from a dynamic `NSColor` snapshots to a static `CGColor`.** Asset-catalog colors returned via `NSColor(named:)` are dynamic — they re-resolve per draw against the effective appearance for text/image sites. But a `CALayer.backgroundColor` is a static `CGColor` set at assignment. Layers set from dynamic colors stick on the appearance-at-set-time — a system light↔dark toggle won't re-resolve. Fix: subclass a helper NSView, override `viewDidChangeEffectiveAppearance`, forward to a callback that re-sets the CGColor. Canonical example: `PaletteTintView` at the tail of `ProjectSidebarOutline.swift`. **And resolve the `CGColor` inside `view.effectiveAppearance.performAsCurrentDrawingAppearance { … }`:** a bare `.cgColor` resolves against `NSAppearance.current`, which outside a draw pass (a palette change, launch) is often Aqua, so dark mode got the *light* paper over the dark material — a mid-grey sidebar, intermittently (17 Oct 2026). Re-setting on appearance change alone does not fix that.
  - **`viewDidChangeEffectiveAppearance` is on `NSView`, not `NSViewController`.** Overriding it on a controller is a compile error. If the controller needs to react to appearance changes, forward via a helper NSView subclass (see above) or KVO on `NSView.effectiveAppearance`.
  - **Asset-catalog folder namespacing is off by default.** `Color("Palette/Edo/Paper")` silently returns a placeholder (magenta clear on macOS 15) unless every parent folder in `.xcassets` has `"provides-namespace": true` in its `Contents.json`. Flat names (`Color("PaletteEdoPaper")` / `NSColor(named: "PaletteEdoPaper")`) sidestep the flag entirely — that's the pattern the eight sidebar-four colorsets use.

## Sandbox, files and cloud

- **On macOS 27 another app's read of our container is decided by the RESPONSIBLE process, not by who signed the binary doing the read.** Cross-team container reads are denied without a dialog (`kTCCServiceSystemPolicyAppDataDetailed`; the grant is Files & Folders ▸ *host* ▸ Bristlenose). A binary signed by our own team is still denied while Claude, ChatGPT or Terminal is responsible for it, because TCC's subject is the host. The same binary launched as its **own** responsible process (`posix_spawn` + `responsibility_spawnattrs_setdisclaim`, private SPI) is treated as Bristlenose reading Bristlenose, and the read is allowed before TCC is consulted. Measured 29 Sep 2026 on 27.0 with a Terminal probe matrix and end to end in ChatGPT. Three traps when measuring: macOS **caches a denial per responsible process**, so only the first read in a fresh host is clean; an agent's own Bash sandbox refuses the read *before* TCC (EPERM with no tccd line — probe via `open -a Terminal x.command` instead); and read the tccd attribution (`AUTHREQ_ATTRIBUTION` → responsible/accessing), never the errno. Full record, the one-click ChatGPT plugin install, and the App Store question: `docs/design-mcp-native-proxy.md`; the Files & Folders UX for the Node proxy: `docs/design-mcp-files-and-folders.md`.

- **"The folder exists" is not "the app may read it" — under App Sandbox `FileManager.fileExists` answers without a grant.** `Project.availability` returns `.ready` on `fileExists(path)`, so a project whose security-scoped bookmark is missing or dead shows as available and then fails every read (`.unreachable(.unreadable)`, sidebar "Can't be read"). Diagnose it from the kernel, not the app: `/usr/bin/log show --predicate 'process == "kernel" AND eventMessage CONTAINS "deny(1) file-read-data"'` names the refused path. The app's container (projects.json, its defaults) is **TCC-blocked from the terminal** — `ls` says "Operation not permitted" and `defaults read app.bristlenose` says the domain does not exist — so you cannot inspect the bookmark from outside; reason from the deny lines. Every `createBookmark` site stored a `try?` nil in silence until 28 Sep 2026 (now logged under `project-index`). **A path whose last component is a symlink mints nothing even with the grant held**, while the folder it names mints (measured in the sandboxed test host, 21 Oct 2026). Such a row worked for the session its drop granted and read "Can't be read" from the next launch, so `mintBookmark` retries once at the resolved spelling of the path and the add stores that spelling, so the row's path and bookmark agree from the start (R50, `BookmarkMintTests`). A re-mint that fails after a move the folder made itself (launch heal, watcher) keeps the old bookmark, which still follows the folder; a Locate onto another folder stores nil. **Still open:** any other mint failure leaves a `.ready` row with no bookmark, and whether to show that or refuse the add is a product call. Also: a URL from Spotlight (`NSMetadataQuery`) carries no sandbox grant, so no bookmark can be made from it — only `NSOpenPanel` or a drop grants. (`a54c4dec`)

- **SQLite `?immutable=1` URI parameter is load-bearing for sandboxed read-only opens of WAL-mode DBs.** Symptom: `sqlite3_prepare_v2` returns "unable to open database file" with `os_unix.c:51044 (2) open(/path/to/db-wal) - No such file or directory` in the os_log. Cause: SQLite WAL journal-mode databases require the reader to access (and sometimes create) `*-wal` and `*-shm` companion files. Under macOS Sandbox, a `SQLITE_OPEN_READONLY` connection can't write the dir to create the WAL companion — it errors at prepare time. **Fix:** open via URI form with `?immutable=1`: `sqlite3_open_v2(CurationCountsReader.immutableURI(for: dbURL), &db, SQLITE_OPEN_READONLY | SQLITE_OPEN_NOMUTEX | SQLITE_OPEN_URI, nil)`. **Never build the URI as `"file:\(path)?immutable=1"`:** a `#` or `?` in the study's folder name cuts it short (the open fails and the sidebar reads unknown) and `%` plus two hex digits is decoded into another character; the helper percent-encodes through the URL (N56, 24 Oct 2026). This tells SQLite "this DB will not change during my session" — skip the WAL/SHM dance entirely. Trade-off: snapshot read; writes mid-scan return prior state. See `SourceFilesReader.swift` for the canonical use. Hit 16 May 2026 on `bristlenose.db` reads from a sandboxed `ProjectFolderWatcher`. **Corollary (the count-blank-after-run bug, `1e1d608`): `immutable=1` can't see WAL-resident commits, so the *writer* must checkpoint or those rows are invisible.** The `sessions` count is written by the *serve importer* (`bristlenose/server/importer.py`), NOT the pipeline run, on a long-lived WAL connection that doesn't auto-checkpoint small imports — so a just-imported count stayed in the `-wal`, the `immutable=1` sidebar read saw the stale main file (`nil`/old count), and it never self-corrected because the watcher's NSFilePresenter scope excludes `bristlenose-output/` (a DB-only change fires no rescan). The old "acceptable for watcher polling" framing was wrong for count data — it doesn't change via source-file events, so "the next callback re-scans" never fires. Two-part fix: (1) the importer PASSIVE-checkpoints after every commit (`_checkpoint_wal`, see `bristlenose/server/CLAUDE.md`) so immutable readers see the rows; (2) `ContentView.scheduleCountRescan` rides out the serve's ~1s re-import with a few spaced `ProjectFolderWatcher.refresh()` rescans on the analysing→terminal transition (the count lands ~1s+ *after* the pipeline-exit signal that drives the rescan). **Caught only by the `silent-failure-hunter` review agent** — four other agents + the plan all assumed the pipeline writes the count. When a desktop `immutable=1` read shows stale data, first check whether a *different process* (the serve) wrote it into an un-checkpointed WAL.

- **The Mac counts a study's files with `run`'s own file selection, so change the two walks together.** `ProjectFolderWatcher` publishes `ingestableFileCount` (the detail pane's "N files to analyse" and the Analyse gate) and `newFiles` (the `+N unanalysed` delta) from `ScanSelection`, a Swift port of `s01_ingest.iter_scanned_files` + `classify_file`: three levels deep, hidden entries, OS metadata, our artefacts, `bristlenose-output/` and the top-level `Discussion guide/` skipped, links after the real tree and once each, the home-folder and system-root refusal, `.ts` excluded. Until 21 Oct 2026 the watcher listed the top level only, so a study kept in per-participant folders read "Drag Interviews Here" with no Analyse while `run` would analyse all of it (decision #111). **It lists and stats and never opens a file** (`contentsOfDirectory`, `lstat`/`stat`, and `realpath` once per folder and per link, never per file), so a dataless iCloud recording is counted without being downloaded, and it runs on the watcher's `scanQueue`, never the main thread. The presenter's filter widened with it (`mayChangeTheCount`): a change anywhere the selection could see rescans, a folder renamed or trashed in Finder included, and a run's writes into `bristlenose-output/` still do not. **Anti-drift is a shared case table**, `tests/fixtures/scan-selection-contract.json`, asserted from both sides (`tests/test_scan_selection_contract.py`, `ScanSelectionContractTests`). A change to `run`'s selection that is not mirrored fails one of the two; edit the fixture only when the rule changes on purpose, and then both walks change with it. **`newFiles` cannot be a plain basename diff below the top level**, because `source_files` records ONE file per session (`files[0]`): the `.m4a` beside a Zoom folder's `.mp4` would read "+1 unanalysed" after every run and offer an Analyse that changes nothing. `ProjectFolderWatcher.newFiles` therefore treats a subfolder holding any ingested file as analysed whole, so a new participant folder is reported and a file added to an analysed one is not (a known gap). It matches names, not paths, because a recorded path goes stale on every folder rename (`missingIngestedFiles`).

- **AppleDouble `._*` files break Python scanners that read every file as UTF-8.** Symptom: `bristlenose serve` crashes on a project copied to ExFAT/FAT32/SMB volumes with `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb0` reading `._<transcript>.txt`. Cause: macOS Finder writes AppleDouble metadata sidecars (resource-fork + xattrs) as `._<filename>` files when copying to non-APFS filesystems. They're binary metadata, not user content. Python scanners that iterate `*.txt` pick them up. **Fix:** filter `._*` at every scan site — `bristlenose.utils.audio` ffprobe loop, `load_transcripts_from_dir`, source-file collection in `s01_ingest`. See `feedback_mac_filesystem_detritus.md` memory for the full list of macOS detritus filenames to skip. Hit 16 May 2026 during a Step 6 SD-card eject test; user workaround was `dot_clean /Volumes/X`. Chip filed for the durable fix.

- **`FileManager.copyItem` blocks *indefinitely* on an iCloud-evicted (dataless) source — check `.ubiquitousItemDownloadingStatus` first, never blind-copy a user-supplied file.** A dataless file (816 MB logical, `stat -f '%Sf'` flags `dataless`/`compressed`, `blocks=0`, API `ubiquitousItemDownloadingStatus == .notDownloaded`) makes `copyItem` go into `libcopyfile` → `com.apple.CloudDocs` to materialise it on the fly, and it **hangs forever** — no progress, no partial dest file, no error, no sandbox denial (`sample <pid>` shows the `libcopyfile`/`CloudDocs` frames). Worse, `Task.cancel()` can't break it: a synchronous `copyItem` mid-call never reaches `try Task.checkCancellation()` (which only fires *between* files), so a cancel wedges too — `CopyMachinery`'s `inFlight` never clears and the app needs a force-quit. **Before copying any user-dragged file, ask `CopyMachinery.isDataless` (`SF_DATALESS` plus iCloud's `.notDownloaded`); a placeholder is refused before anything is written, and asked again before each file (`c9176819`, pinned by `CopyMachineryDatalessTests`). Never a blind `copyItem`, and never `startDownloadingUbiquitousItem` with a progress query: Bristlenose does not fetch or narrate cloud files — `docs/design-cloud-files.md`.** Found 19 Jun 2026 during `project-status-line` QA; the private handoff (`copy-evicted-source.md`) proposed a download path and is superseded by `c9176819`. **Why it hangs rather than errors (measured 4 Sep 2026):** the sandboxed app runs the kernel's dataless-materialisation policy **ON** (`getiopolicy_np` → 2, pinned by `DatalessPolicyProbeTests`), so every syscall waits in `msleep` with no timeout; `EDEADLK` is what an **OFF**-policy process gets, and this app is not one. `NSFileCoordinator` does not change blocking under ON. The sidecar's `fs.py` already does detect-then-bounded-materialise — mirror that. **Two corrections from the same evening:** (1) the policy is inherited from whoever spawned you — GUI-descended processes (this app, Terminal, the test host) measure ON=2, but a launchd agent with no `MaterializeDatalessFiles` key measures OFF=1 and gets `EDEADLK` (errno 11, not 35) instead of a hang — so a probe run by hand and a probe run under launchd disagree, and neither is lying; (2) `brctl download`/`brctl evict` are **hidden from the usage but still work** on 26.4.1 when given a path (running them bare prints the usage, which is how "no longer exist" got written here that morning); `download` is asynchronous. The measured record — per-operation table, probes, verbatim results per OS version — is public: <https://github.com/cassiocassio/iCloud-wizzard-behind-the-curtain>; re-measure there before asserting anything new about dataless files.

- **`-34018 errSecMissingEntitlement` on `SecItemAdd` under App Sandbox means the entitlement/keychain-world is wrong — NOT a damaged keychain.** (A locked/corrupt login keychain returns `-25308`/`-25293` — different numbers, different problem; don't chase keychain repair.) Two compounding causes, both hit during the 2 Jun keychain-sandbox saga: (1) the app has no `keychain-access-groups` entitlement — add the **Keychain Sharing** capability (writes `$(AppIdentifierPrefix)app.bristlenose` into a `.entitlements` file + `CODE_SIGN_ENTITLEMENTS`); (2) a biometric `.biometryCurrentSet` `SecAccessControl` implicitly demands the **data-protection keychain**, which the file-based login keychain can't honour under sandbox. Fix that shipped (`8b2ef51`): drop the biometric ACL, move to the data-protection keychain — `kSecUseDataProtectionKeychain: true` in every query, `kSecAttrSynchronizable: true` on writes (= iCloud Keychain sync; the Mac-native default for a user's own *revocable* credential, and it survives a damaged login keychain since it's a separate partition), and **crucially `kSecAttrSynchronizable: kSecAttrSynchronizableAny` in the read/delete match queries** or synced items are invisible (a default query only matches non-synchronizable items). Reviewed + cleared as idiomatic by `what-would-gruber-say`: per-read Touch ID on a headlessly-read API key is the *anti*-convention (the sidecar reads the key at every launch → a `.biometryCurrentSet` ACL = Touch ID prompt on every app start); do app-level `LAContext`-on-reveal instead. Adding the capability regenerates the **dev provisioning profile** → a "Register Device" prompt (register your own Mac — correct; ad-hoc "Sign to Run Locally" has an empty `$(AppIdentifierPrefix)` and re-breaks the entitlement). Diagnose only via the **Xcode console** — failures log `[KeychainHelper] … failed: <OSStatus>`; a *successful* save is **silent** (no "success" line ever appears). And validate the **persisted** key (read it back, `ddec5c6`), not the in-memory typed value — a green "Online" must not outrun what actually landed in the Keychain. Full story + remaining work (Touch-ID-on-reveal, status-vocabulary fix): `docs/private/archive/keychain-sandbox-entitlement.md`. **NB pre-existing inverted setting:** Release config has `ENABLE_APP_SANDBOX = NO` (backwards — a MAS build must be sandboxed); flagged for the app-store-police pass, not yet fixed

- **Sandbox iteration: use `desktop/scripts/reset-sandbox-state.sh` between builds.** When iterating on App Sandbox / entitlements, stale state in `~/Library/Containers/app.bristlenose/Data` and the app's UserDefaults can wedge `libsecinit` on subsequent launches even when the underlying entitlements are correct. Symptom: `EXC_BREAKPOINT` in `_libsecinit_appsandbox.cold.*` during process startup, with no useful Swift backtrace. Cause: `secinitd` (the per-user agent that mints sandbox containers) can't identify the app — usually because of stale Container/UserDefaults cruft from a previous run, sometimes from a code-sign or bundle-ID change. Fix the stale-state path: `desktop/scripts/reset-sandbox-state.sh` (verbose by default; `--quiet` for one-line summary, `--dry-run` for safety preview). It SIGTERM/SIGKILLs the host + bundled sidecar, frees zombie listeners on the per-project port range (filtered to Bristlenose-named processes — won't kill an unrelated dev server in that range), wipes `~/Library/Containers/app.bristlenose/Data/*` (the directory itself is SIP-protected and can't be removed; only the inside), drops UserDefaults via `defaults delete` and bounces `cfprefsd`. Idempotent. Run it before every Cmd+R when chasing sandbox issues. Doesn't touch DerivedData (Cmd+Shift+K handles that). **Do NOT extend it to touch `~/Library/ContainerManager/`** — that's `containermanagerd`'s state; mutating it produces undefined behaviour across all sandboxed apps on the machine. macOS-only by design (every load-bearing piece — App Sandbox, Containers, defaults, cfprefsd — is Apple-specific).

- **In the inherited-sandbox sidecar, `NSHomeDirectory()` is the REAL home, so a system framework that caches under it fails — silently.** The host passes `HOME` as the container, but Foundation in a child that inherits the sandbox ignores that and resolves the user's real home; a sandboxed *app* (and a standalone sandboxed probe) resolves its container instead. Measured 13 Oct 2026 with Apple Vision in the real sidecar: the text model compiles once into `<home>/Library/Caches/<id>/com.apple.e5rt.e5bundlecache`, the write is refused, and `VNRecognizeTextRequest` returns failure with **no `NSError`** — the only trace is `e5rt_e5_compiler_create call failed (Code: 11)` / `Underlying detector load error` in `/usr/bin/log show` for the sidecar's pid. Setting `CFFIXED_USER_HOME` to the container before Foundation initialises fixed it. **Wired 13 Oct 2026** (`32e9d2b3`): `childEnvironment` sets it for the bundled sidecar under a sandboxed host (`BristlenoseShared.foundationHomeEnvironment`), and an end-to-end rebuild with only that wiring (no Python-side help) read 8/8 frames, with `NSHomeDirectory()` in the sidecar now the container. No Python code reads Foundation's home today (every lookup goes through `HOME`), so the variable has no consumer until a framework like Vision ships. Vision's first frame pays a ~41 s model compile once per build: the cache survives a relaunch (0.63 s) but a newly built sidecar compiled again. Same probe: the sandbox refuses POSIX semaphores, so `multiprocessing.Queue`/`Lock` raise `EPERM` in the sidecar. Record: `docs/design-screen-text-search.md` §3.3, `experiments/screen-text/README.md` § Third pass. **Tell:** a system framework that works in the CLI and in a standalone sandboxed app, and fails without an error in the sidecar.

- **App Sandbox blocks `Process()` exec of system binaries — and also blocks `proc_listpids` enumeration entirely.** _Measured 12 Oct 2026 from the sandboxed Debug test host: `Process()` of `/bin/ps` fails with `Operation not permitted`; `proc_pidinfo(PROC_PIDTBSDINFO)` and `proc_pidpath` answer for the same pid. `PipelineRunner.ownedRunVerdict` is the libproc form._ `Process` exec of `/bin/ps`, `/usr/sbin/lsof`, `/usr/bin/security` etc. is blocked at sandbox-launch regardless of the binary's own permissions. The "ps is allowed" intuition is wrong — sandbox enforces at the *exec* boundary, not the destination binary. Mac-canonical narrow-PID syscalls work fine (`proc_pidpath(pid, ...)`, `proc_pidfdinfo(pid, ...)` — these read state for a *known* PID), but the broader `proc_listpids(PROC_ALL_PIDS, ...)` enumeration call returns 0 (errno=EPERM) under sandbox. **Lesson learned A1c**: don't try to find orphan subprocesses at all — design so the orphan finds itself (sidecar's parent-death watcher in `bristlenose/server/lifecycle.py`).

- **`BRISTLENOSE_DEV_SIDECAR_PATH` cannot point at a venv outside the bundle when sandbox is on.** The `Bristlenose (Dev Sidecar)` scheme is the iteration-friendly path under non-sandboxed Debug, but under App Sandbox the host can't see anything outside `~/Library/Containers/app.bristlenose/Data/` or its bundle resources. `FileManager.isExecutableFile(atPath:)` against the worktree's `.venv/bin/bristlenose` returns false even when the file is genuinely there and `chmod +x`. ServeManager's `os.Logger` reports `Dev sidecar path is not a usable executable: <path> — not executable`. This means **Track A and Track C are coupled**: the only sidecar path that survives the sandbox flip is `Bundle.main.resourceURL/bristlenose-sidecar/bristlenose-sidecar` (bundle resources are inside the sandbox's `LSBundlePathSandboxExtensionKey` read scope by default). For sandbox-on iteration you must run against a built `.app` from the default `Bristlenose` scheme, not Dev Sidecar. (Discovered 29 Apr 2026 during A1 spike.)

- **Xcode now uses build-setting-driven entitlements for App Sandbox**, not a separate `Bristlenose.entitlements` file for the host. Toggling capabilities in the Signing & Capabilities pane writes `ENABLE_APP_SANDBOX = YES`, `ENABLE_OUTGOING_NETWORK_CONNECTIONS = YES`, `ENABLE_USER_SELECTED_FILES = readwrite`, etc. into the buildSettings block of `project.pbxproj`. The entitlements blob is generated at build time from these flags. Means you can enumerate the host's full granted set by grepping `ENABLE_*` in the pbxproj — no separate `.entitlements` file to keep in sync. The sidecar still uses an explicit `bristlenose-sidecar.entitlements` file because it's not an Xcode target with capability UI; Hardened Runtime + sandbox-inherit live there

- **Security-scoped bookmark creation needs `files.user-selected.read-write` granted before the XPC bootstrap works.** Without it, the very first `URL.bookmarkData(options: [.withSecurityScope, …])` call (typically inside `ProjectIndex.createBookmark(for:)`) hits `Sandbox: Bristlenose deny(1) mach-lookup com.apple.scopedbookmarksagent.xpc`. The drop completes silently-degraded — the project lands in the sidebar but no bookmark persists for re-launch. The grant authorises the XPC service automatically; no separate XPC entitlement needed. Confirmed via A1 spike (29 Apr 2026)

- **A security-scoped extension follows a renamed folder, and nothing re-resolves bookmarks on app activation — by decision.** Measured 13 Oct 2026 on a sandboxed Debug build with a folder granted by a real Finder drop: after a Finder rename, `URL(fileURLWithPath: newPath).bookmarkData(.withSecurityScope)` succeeds with only the *old* URL's lease scope open, the bookmark minted that way resolves and opens its scope from a cold relaunch, and the serve respawns on the new path. So `ProjectIndex.relocateProject` may mint from the bare new path on the watcher route; review finding 7 (the path-bound-extension hypothesis) is disproved for a same-volume rename, cross-volume untested. **And `refreshAvailability()` is deliberately not called on `didBecomeActive`** (it was, for one commit, `4ecf1437`): `resolveBookmark` starts a scope it never stops, so that was one leaked sandbox extension per project per ⌘-Tab, with the resolve running on the main actor with mounting and UI allowed — a beachball or an auth dialog on a sleeping NAS. Finder renames reach the app through `ProjectFolderWatcher.presentedItemDidMove`; launch and volume mount heal the rest. Don't re-add it from the handoff that asked for it.

- **A count that gates a destructive act returns nil for *unreadable*, never zero.** `CurationCountsReader.read` decides whether **Re-analyse…** asks before `--clean`, and a zero means "nothing to lose, run it". Until 21 Oct 2026 every failure read as zero: a file that would not open returned `.none`, and a file that opened but could not be read had each count's failure swallowed into 0, because `sqlite3_open_v2` reads nothing and the error (`SQLITE_NOTADB`, `_CORRUPT`, `_IOERR`) only arrives at the first `prepare` or `step`. Now it returns `CurationCounts?`: `stat` (not `fileExists`, which answers false for a sandbox refusal) separates *no database* (`ENOENT`, a real zero) from *can't see it*; a curation table the schema lacks (asked of `sqlite_master`, never guessed from `SQLITE_ERROR`, which also means "unsupported file format") is an older schema and zero for that line; a table that is there but can't be counted (renamed column, missing join table), and every other failure, is nil, and `ReAnalyseDecision.decide` confirms on nil with `desktop.chrome.reAnalyseLossUnknown` in place of the list (decision #1). `immutable=1` takes no locks, so a database the serve holds locked reads normally. **Trap met on the way:** in a function returning `CurationCounts?`, `return .none` is `Optional.none`, i.e. nil, not the type's own `static let none` — the compiler only warns ("assuming you mean 'Optional<CurationCounts>.none'"). Spell it `CurationCounts.none`. Pinned by `ProjectDBReadersTests` (`curationCountsAreNil…`, `curationCountsAreZeroNotNil…`) and `ReAnalyseDecisionTests`. **A commit still in `-wal` is nil too (decision #115, 21 Oct 2026).** The serve's `wal_autocheckpoint=1` cannot copy frames past another connection's open snapshot, and it does not retry when that reader finishes, only at the next commit. So a star made while any statement was in flight stayed invisible to `immutable=1`, and the count read zero. `walVouch` trusts the main file only when the `-wal` is absent or empty, or when all of these hold: another process holds `-shm`'s DMS lock (byte 128, `fcntl(F_GETLK)`; SQLite itself trusts an index only under that lock, and a process never sees its own POSIX locks, so the tests hold the database from a `/usr/bin/sqlite3` child, which also shows `F_GETLK` works under the sandboxed test host); the WAL-index header (`mxFrame` u32 at 16, `nBackfill` u32 at 96, native order; both 48-byte copies equal, `iVersion` 3007000) has the two equal; its salt (32..<40) is the `-wal` header's (16..<24, the same era); and no frame of that era sits past `mxFrame`. It is read before the count and again after, like a seqlock, and a moved index is nil. A `-wal` with no `-shm` is nil. Overcautious by design: a `-wal` that survived an unclean exit (recovery sets `nBackfill` to 0) shows the sheet on an idle study until its next commit; that is unverified and accepted. **Not the file size and not mtime:** a served `-wal` stays about 99 KB after every checkpoint, so size would show the sheet on every uncurated study, and a partial checkpoint leaves `-wal` older than the main file while the star is still only in the WAL. Both were measured in `tests/test_serve_wal_visibility.py`. Pinned by the eight `ProjectDBReadersTests` after `// MARK: - A commit still in the WAL`, each branch mutation-proved. `SourceFilesReader` (the sidebar session count) has the same blind spot, cosmetic for the session count and duration. **Not for the owed-session count** (`recodedSessionCount`, §J7 R3, 23 Oct 2026), which gates **Analyse**: that one read is vouched with `walVouch` before and after, an unvouched read is nil (unknown), and the watcher keeps the last known count rather than reading it as zero (`ProjectFolderWatcher.recodedSessionCount`), so a later scan or folder event answers it. Pinned by `RecodedSessionWorkTests` (`aRecodeOnlyInTheWALIsUnknownNotZero`, `anIndexNobodyHoldsIsUnknown`, `anUnknownCountKeepsTheLastOne`). This answers #116 for the count that matters.

## The sidecar: building, bundling and signing

- **Build-script pretty output goes through `report.sh` + `build_report.py` — see `desktop/scripts/REPORT-STYLE.md`.** Any build script renders a phase-grouped Rich report by sourcing `report.sh` and calling `bn_autowrap "$0" "$@"` + the `bn_step_*`/`bn_gate`/`bn_done` helpers (fixed 6-line recipe in REPORT-STYLE.md). Two traps when touching this: **(1) `report.sh` MUST stay bash-3.2-safe** — `ensure-sidecar.sh` + the Xcode "Ensure Sidecar Fresh" phase run under `/bin/bash` 3.2, so NO `local -A` / `mapfile` / `${var,,}` in `report.sh` (`_bn_field` replaces the assoc-array lookup; the *emitting* scripts may still require bash 4+ for their own logic — it's `report.sh` that must run anywhere). **(2) Nesting is handled by `_BN_ACTIVE`** — `bn_autowrap` exports it, so a child run *under* a rendering parent (`build-all.sh` → `check-*`) does NOT start a second renderer and its `bn_*` emit nothing (only the render owner's non-exported `_bn_owner=1` enables emission). **Escape hatch: `BN_REPORT=0 <script>`** → plain `==>` output instantly (also the automatic fallback when python / `build_report.py` are absent); the plain-mode parent claims `_bn_owner` too, so nested children stay silent there as well (5 Sep 2026). Wired into `build-all.sh` (validated on a real signed build) + the three standalone check gates; `sign-sidecar.sh`'s 220-file `wait -n` loop emitting `@bn bar` is the documented next enhancement.

- **mlx is bundled via `collect_all("mlx")`, not PyInstaller's default modulegraph walk.** PyInstaller's default analysis copies `mlx/core.cpython-312-darwin.so` and `mlx/lib/libmlx.dylib` but misses `mlx/lib/libjaccl.dylib` (linked via `@rpath` from libmlx), `mlx/lib/mlx.metallib` (~157 MB compiled Metal shader library, distributed via the separate `mlx-metal` wheel into the same `mlx/` dir), and several pure-python submodules mlx's native init probes. Symptoms when missing: `dlopen … Library not loaded: @rpath/libjaccl.dylib` (libjaccl) or the more inscrutable nanobind `Encountered an error while initializing the extension.` (metallib). Discovered during S3 bundle-trim (4 May 2026) — the failure had been masked by torch failing first in the import chain and reporting "mlx-whisper not installed". Spec uses `_MLX_DATAS, _MLX_BINARIES, _MLX_HIDDEN = collect_all("mlx")` and splices via `*_MLX_DATAS` etc. The bundle-manifest gate (`desktop/scripts/check-bundle-manifest.sh`) skips `ast.Starred` elements because they don't represent bristlenose source dirs.

- **`codesign --verify` a PyInstaller `--onedir` bundle by its OUTER EXECUTABLE, not the directory.** `codesign --verify --deep --strict desktop/Bristlenose/Resources/bristlenose-sidecar` (the *dir*) fails with "code has no resources but signature indicates they must be present" — a `--onedir` output is not an app bundle. Verify `…/bristlenose-sidecar/bristlenose-sidecar` (the executable) — that's what `sign-sidecar.sh` and `ensure-sidecar.sh` do.

- **`OSError: could not get source code` at sidecar import time → typeguard 4.x + PyInstaller + a package whose `@typechecked` decorator runs at module-load.** Symptom: bundled sidecar crashes during `from bristlenose.cli import app` with the chain `typeguard/_decorators.py:70 instrument() → inspect.py:1096 findsource() → OSError`. Cause: typeguard 4.x rewrites decorated functions' ASTs via `inspect.getsource()` at import time. PyInstaller's PYZ archive holds `.pyc` only — no `.py` source — so the rewrite fails. **Fix:** add the offending package to the spec's `module_collection_mode` dict with value `'pyz+py'` so PyInstaller bundles both bytecode and source. Example in `desktop/bristlenose-sidecar.spec`: `module_collection_mode={'inflect': 'pyz+py'}`. The class of bug recurs whenever a transitive dep adopts typeguard / beartype / `@validate_call` at module level — audit on every fresh `pip install` of `.venv-sidecar/`. Long-term protection: lockfile + spec compat registry in `docs/private/handoffs/sidecar-dep-lock.md`. Hit 16 May 2026 during the multi-project-folder-watcher acceptance walk.

- **Sidecar bundle is built against `.venv-sidecar/`, NOT the contributor `.venv/`.** A dedicated `$ROOT/.venv-sidecar/` carries only `.[serve,apple,desktop,mcp,voice]`, keeping PyInstaller's analysis off whatever the contributor manually pip-installed. The contributor's `.venv` is untouched — keep using it for tests and lint. `.[apple]` is mandatory (mlx-whisper isn't a core dep — without it the Mac build silently has no transcription). **As of 29 Jun 2026 `build-sidecar.sh` is PER-LAYER INCREMENTAL** (not "recreate every run"): frontend / venv / PyInstaller each rebuild only when their own fingerprint moves, so a Swift-only or one-line-Python iteration skips in ~0.3s. The venv recreates only when `pyproject.toml` OR the installed-package manifest changes (a `.deps-ok` sentinel, written last, guards against a half-installed venv being trusted). `--force` restores the original always-recreate behaviour; **release / `build-all.sh` pass `--force`** (so the typeguard/`pyz+py` fresh-install audit and the clean dep-closure are release-only now). `ensure-sidecar.sh` orchestrates build + sign (ffmpeg AND sidecar) + deep-verify. Full design + the Phase-3 Xcode-wiring TODO: `docs/design-desktop-build-orchestration.md`.

- **Sidecar fingerprint (`sidecar-source-hash.sh`) must EXCLUDE OS metadata.** It hashes `bristlenose/locales/**` and `frontend/src/**` with `find -type f`, which sweeps `.DS_Store` / AppleDouble `._*`. Finder touching a hashed dir then drifts the hash → a freshly-built bundle reads "STALE" and P rebuilds forever. The recipe now filters `-not -name '.DS_Store' -not -name '._*'`; **any new `find` clause added to that recipe must keep the filter** (or use the `is_os_metadata` convention). Cost a full QA round on 29 Jun 2026.

- **…and it must INCLUDE every bundled data dir — the other half of the same rule, and the more dangerous half.** Adding a directory to the spec's `datas` without adding it to `sidecar-source-hash.sh` doesn't weaken the gate, it **inverts** it: edits to that directory never move the hash, so `check-sidecar-freshness.sh` prints **"✓ bundled sidecar matches source"**, the Ensure phase skips the rebuild, and the `.app` keeps serving the old copy. A gate that answers *confidently and wrongly* is worse than no gate — you stop suspecting the bundle and start debugging source that was already correct. Bit on 5 Aug 2026: `bristlenose/theme/**` is bundled (`bristlenose-sidecar.spec:102`) but the recipe only swept `*.py` there, so a theme-only edit was invisible and a Focus Mode keyline "wouldn't take" — fixed source, stale stylesheet, confident green gate. **Rule: a new bundled data directory goes into `sidecar-source-hash.sh` in the SAME commit as its spec `datas` entry.** They are one decision. Tell: the gate says match, the `.app` behaves like the edit never happened, and `git diff` says it did. **The theme was one instance, not the class** — auditing the same day found four more uncovered `datas` entries, the worst being `bristlenose/llm/prompts` (every LLM-using stage loads those, so a prompt edit shipped the old prompt under a green gate; verified by an edit leaving the hash unmoved). All five are closed. **You no longer have to remember this rule** — `test-ensure-sidecar.sh` case 9 parses the spec's own `datas` paths and asserts each one moves the fingerprint, so a new entry without a recipe entry fails the test instead of shipping a confident lie. It probes a *non-`.py`* file by preference, since `bristlenose/**/*.py` is swept wholesale and a `.py` probe would prove nothing (`server/alembic` is exactly that shape). Run it after touching either file.

- **`ensure-sidecar` says "Stamped &lt;hash&gt;…" and the very next phase fails "STALE" — that is not a contradiction, it means you saved a file mid-build.** The fingerprint is snapshotted at `build-sidecar.sh` entry and written to `.source-stamp` after the build, but Vite and PyInstaller read the tree in between — so a hashed file saved during the build yields a bundle that genuinely lacks the edit, and the gate is right. The window is the build's own duration (58s when this bit on 4 Aug 2026: stamped `8c89d089`, gate read `1d2897c4` one second later). **Do not "fix" it by stamping a post-build hash** — that makes the stamp claim the bundle holds an edit PyInstaller never read, turning a loud failure into a silently stale bundle. `build-sidecar.sh` now recomputes at the tail and fails with the window width + both hashes, so the message names the save rather than accusing the bundle; just re-run once your edits settle. Iterating fast enough to keep hitting it → use the **Dev Sidecar** / **External Server** schemes, which serve live source. Design: `docs/design-desktop-build-orchestration.md` §The third staleness class.

- **The `Ensure Sidecar Fresh` build phase runs under Xcode's STRIPPED PATH — scripts must resolve their own toolchain, and bare `bash <child>` overrides the child's shebang.** Xcode build phases get PATH ≈ `/usr/bin:/bin:/usr/sbin:/sbin` + the developer dir — no Homebrew, no mise/asdf/pyenv shims. Two ways this bit on first wiring (29 Jun 2026): (1) `build-sidecar.sh` couldn't find `python3.12`; (2) `ensure-sidecar.sh` launches `sign-sidecar.sh` via `bash "$SCRIPT_DIR/sign-sidecar.sh"` (bare `bash`, which OVERRIDES the `#!/usr/bin/env bash` shebang), so it resolved to `/bin/bash` 3.2 instead of Homebrew bash 5.x — and `sign-sidecar.sh` needs 4.3+. Both scripts now **augment PATH with the Homebrew prefix only when the tool isn't already resolvable** (a configured PATH is respected, never reordered) and **error loudly** otherwise. Scope: this is **macOS-only** (an Xcode build phase — Linux/Windows never run it; the CLI's Linux CI builds the wheel, not the sidecar). The fallback is Homebrew because that's this project's documented Mac toolchain (`.tool-versions` pins `python 3.12` / `node 24`; `node@24` is keg-only so it has its own keg prepend). **A contributor on a non-Homebrew toolchain (mise/asdf/pyenv/python.org) must put their `python3.12` + `bash` 4.3+ on the build's PATH** — deliberately not a universal auto-resolver (sourcing the login shell misses mise's `.zshrc` activation; enumerating shim dirs rots). When adding a new build-phase script or a new `bash <child>` shell-out, assume the stripped PATH and the shebang-override.

- **The bundled sidecar can silently lag the repo — when desktop progress/telemetry looks dead, check the events-file `bristlenose_version` BEFORE suspecting the Swift side.** _Mostly closed since 29 Jun 2026: the Phase-3 `Ensure Sidecar Fresh` build phase runs `ensure-sidecar.sh` before Copy Sidecar Resources, so a plain Cmd+R now rebuilds+signs+re-embeds a stale bundle automatically — no hand-run rebuild + clean build. The lag can still bite if ensure was skipped (`BRISTLENOSE_SKIP_SIDECAR_ENSURE=1` — which `test-swift.sh` sets, so the Debug app it leaves in the shared DerivedData carries whatever sidecar was embedded before; opening that app instead of pressing Cmd+R runs old Python, as a 13 Oct 2026 hand test of progressive lenses did), errored, or you're inspecting a bundle built before this phase existed, so the diagnosis below stays useful._ Historically the PyInstaller sidecar was only rebuilt by `desktop/scripts/build-sidecar.sh`; an Xcode Cmd+R rebuilt the *Swift* app but reused whatever sidecar bundle was already in `Resources/`. So a freshly-edited backend (new `run_progress` fields, new event kinds, new manifest keys) is **absent** if the bundle predates it — and the Swift side renders perfectly against data that never arrives. Worked example (22 Jun 2026): the determinate ETA ring (`SidebarActivityRing`) stayed on the indeterminate spinner across 7 runs; root cause was the active bundle being **0.15.14** (built Jun 8) while `run_progress` emit (`stage_fraction`/`predicted_total_seconds`, the ring's only fuel) landed in **0.15.16** (`010910a`). No emit → `ringFraction` nil → spinner, forever, regardless of run count. **Diagnosis in one command:** `grep -o '"bristlenose_version":"[^"]*"' <folder>/bristlenose-output/.bristlenose/pipeline-events.jsonl | head -1` and compare to `bristlenose/__init__.py`. (A run that emits only `run_started`+`run_completed` and no `run_progress` is the tell.) **Fix (now automatic):** a plain Cmd+R runs `Ensure Sidecar Fresh` → `ensure-sidecar.sh`, which rebuilds+signs the stale bundle and Copy Sidecar Resources (`alwaysOutOfDate=1`) re-embeds it — no manual step. To force it by hand (e.g. ensure was skipped): `desktop/scripts/ensure-sidecar.sh` (or the lower-level `desktop/scripts/build-sidecar.sh && SIGN_IDENTITY="-" desktop/scripts/sign-sidecar.sh`), then Cmd+R. Faster dev loop: the **Bristlenose (Dev Sidecar)** scheme spawns `$(SRCROOT)/../../.venv/bin/bristlenose` (live venv source) instead of the bundle, sidestepping the rebuild entirely. The same handshake env var (`_BRISTLENOSE_HOSTED_BY_DESKTOP`, set by `BristlenoseShared.childEnvironment`) satisfies the sidecar's `run` host-gate either way. **Same trap, frontend layer (23 Jun 2026) — now AUTOMATED (29 Jun 2026):** `build-sidecar.sh` historically bundled the *existing* `bristlenose/server/static/` and did **not** `npm run build` first, so a new *SPA* feature (a new bridge post, island, or effect) was absent from the bundled scheme until you hand-ran `npm run build` **then** `build-sidecar.sh`. Worked example: the lens-contextual window subtitles (`LensSubtitleSync` over the `lens-subtitle` bridge message) rendered **blank** on the bundled scheme because the bundled `static/` predated the component — while Sessions/Project (a Swift-side DB read, not SPA-sourced) worked, the diagnostic tell (native-sourced present, SPA-sourced blank → stale bundled SPA, not a bridge bug). **Fixed:** `build-sidecar.sh` now runs `npm run build` as its first step, and the sidecar source-fingerprint (`sidecar-source-hash.sh`) covers `frontend/src` + `bristlenose/locales`, so `check-sidecar-freshness.sh` **fails the Xcode build** if the bundle predates a frontend edit (same loud gate that already covered Python). So a sidecar rebuild now self-heals the SPA — no separate `npm run build` — and a from-cloud ditto'd bundle is flagged stale until rebuilt. The PostToolUse hook `frontend-stale-reminder.sh` nudges after frontend/locale edits. The **Dev Sidecar** scheme (live venv serving the live `static/`) still sidesteps the rebuild for fast iteration.

- **`mlx_whisper` also needs `collect_all`** — same pattern as mlx. The package ships `mlx_whisper/assets/{mel_filters.npz, gpt2.tiktoken, multilingual.tiktoken}` which `mlx_whisper/audio.py::mel_filters` and the tokenizer load via `os.path.dirname(__file__) + "/assets/…"`. Without them `import mlx_whisper` succeeds, model loads succeed, but the first `mlx_whisper.transcribe(...)` call fails with `[load_npz] Input must be a zip file …` because the path resolves to a non-existent location inside the bundle. Spec calls `collect_all("mlx_whisper")` and splices the lists alongside mlx's. Found 4 May 2026 by an end-to-end smoke run, after S3's `import mlx_whisper` fix unmasked it.

- **`sqladmin` also needs `collect_all` — and the failure is a construction-time `ValueError`, not a runtime one (mlx/mlx_whisper are the reverse).** SQLAdmin's `Admin(...)` builds `PackageLoader("sqladmin", "templates")` (+ a nested `templates/sqladmin` loader, + a `statics/` mount) at construction, so a bare `sqladmin` hiddenimport bundles the code into the PYZ but leaves `sqladmin/templates/` + `sqladmin/statics/` behind → `ValueError: PackageLoader could not find a 'templates' directory in the 'sqladmin' package` **the instant `/admin` is mounted**. Symptom on desktop: sidecar dies at ~0.2 s with `sidecar_exit reason=uncaught_exception exc=ValueError`, read as "Last run failed. CLI exited with code 1." Fix: `_SQLADMIN_DATAS, _SQLADMIN_BINARIES, _SQLADMIN_HIDDEN = collect_all("sqladmin")` spliced into datas/binaries/**hiddenimports** (all three — an early version of the fix wired datas+binaries but forgot hiddenimports). Found + fixed 14 Jul 2026. This is now the **rule of three** for Jinja2/asset-carrying third-party deps (mlx, mlx_whisper, sqladmin): if a bundled package loads its own `templates/`/`statics/`/`assets/` via package-relative paths, it needs `collect_all`. Two guards keep it fixed: (1) the spec is in `sidecar-source-hash.sh` so a spec-only edit forces a rebuild (it silently didn't, first time); (2) `check_bundle_admin_panel()` in `doctor.py` reproduces the `PackageLoader` construction under `doctor --self-test` (build-all step 2a) so a missing-datas bundle fails the *build*, not a user launch. See `docs/design-desktop-debug-admin-panel.md` § Guarding the packaging.

- **App Store §2.5.2 `itms-services` static-scan trap — the bundled CPython carries it, and `grep` can't see it.** App Store Connect runs an automated static string scan that rejects any binary *containing* the literal `itms-services` ("the app uses the itms-services URL scheme to install an app") — **even though the code never runs** ([CPython gh-120522](https://github.com/python/cpython/issues/120522)). CPython 3.12 introduced it into `Lib/urllib/parse.py`; **our Homebrew `python@3.12.13` is NOT built with `--with-app-store-compliance`** (verify: `python3 -c "import sysconfig; print(sysconfig.get_config_var('CONFIG_ARGS'))"` — no such flag), so it freezes into the sidecar's `urllib.parse`. **Verified present 16 Jul 2026.** The first TF upload (14 Jul) was bounced for three OTHER reasons but NOT this — either the scan didn't fire on that path or we got lucky; it's a latent blocker for the next **App Store** (not TestFlight-internal) submission. **The nasty part: it's INVISIBLE to `grep`/`strings` on the bundle** — PyInstaller marshals the stdlib into code objects inside a **zlib-compressed PYZ**, so the literal is never plaintext (all four of `grep -ral`, `grep -a`, `strings` returned ZERO on the shipped xcarchive; the string is real, they just can't reach it). It also nests inside a *tuple* constant (`uses_netloc = [...]` compiles to a `LOAD_CONST` tuple), so even a naive `co_consts` walk that doesn't recurse into containers misses it. **Fix (shipped):** the PyInstaller spec strips it at freeze time — `_strip_app_store_noncompliant_strings(a)` in `desktop/bristlenose-sidecar.spec` recompiles `urllib.parse` from a length-preserving-patched copy of its own source (`'itms-services'` → `'itmx-services'`, an inert scheme BN never parses) and swaps the cached code object in `CONF['code_cache'][id(a.pure)]` **before `PYZ(a.pure)`** freezes it (PYZ copies code objects out of that cache at construction, so patch-before-construct is load-bearing). Validated on PyInstaller 6.19 **and** 6.21. **Gate (shipped):** `desktop/scripts/check-sidecar-appstore-strings.{sh,py}` decompresses the PYZ and scans code-object constants (recursing into tuples) + byte-scans on-disk files; wired into `build-all.sh` as **step 2c** (runs for ad-hoc builds too, so a stale strip is caught in the inner loop, not at ASC upload). The `.sh` probes `import PyInstaller` and falls back `.venv-sidecar → .venv` — which mattered: a concurrent `.venv-sidecar` rebuild stripped its PyInstaller mid-session and the wrapper transparently used `.venv`. **A raw `check-...py` call under a broken `.venv-sidecar` exits 1 from an uncaught `ImportError`, which looks exactly like a real detection — always run the `.sh` wrapper, or confirm `import PyInstaller` first.** The generic version of this trap (other packagers, the detection recipe) lives in the shared `.claude/agents/app-store-police.md` (§2.5.2 + survival checklist item 11); this bullet is the BN-specific wiring. Route any change here through the app-store-police agent before an App Store submit.

- **`Copy Sidecar Resources` script: `cp` and `rsync -a` disagree on symlink dereferencing.** The xcodeproj `Copy Sidecar Resources` shell-script build phase (in `desktop/Bristlenose/Bristlenose.xcodeproj/project.pbxproj`) copies ffmpeg/ffprobe/models from `desktop/Bristlenose/Resources/` into the built `.app`. It uses `cp -p` for ffmpeg/ffprobe (which dereferences file symlinks by default → real bytes in the .app) but `rsync -a --delete` for `models/` (where `-a` includes `-l` → preserves symlinks). When the source is a symlink (e.g. a worktree pointing back at main's gitignored binaries), `models/` ships into the .app as a dangling absolute-path symlink, while ffmpeg/ffprobe ship as real binaries. Verified during the 6 May 2026 test run. Fix when needed: `rsync -aL --delete` (`-L`/`--copy-links` dereferences). Generalised lesson: every copy site that touches a symlink needs an explicit dereference choice — `cp` and `rsync` disagree on every Unix, not just macOS.

- **For materialising a PyInstaller sidecar bundle (or any macOS bundle) from main into a worktree, use `ditto`, not `cp -R*`.** `cp -RL` dereferences *every* symlink including the internal ones, which blows up rpath-relative library structures (e.g. mlx's metallib lookup fails with "Failed to load the default metallib. library not found"). `cp -R` / `cp -RP` preserves internal symlinks but doesn't handle extended attributes / resource forks / codesignatures the way bundles need. `ditto src dst` is Apple's purpose-built bundle copier: preserves internal symlinks, xattrs, signatures; auto-dereferences the source argument if it's a symlink to a directory. Used by `/new-feature` Step 9 to copy main's sidecar bundle into each fresh worktree (~428 MB real bytes per worktree; symlinking the bundle at the top level breaks the rsync-`-a` phase above, so `ditto` is the load-bearing answer). Hit twice on 14 May 2026 before landing on `ditto`.

- **`excludes=` in the spec drops one named module, not its transitive deps.** Mental shortcut "the only file in `mlx_whisper` that imports torch is `torch_whisper.py`, so excluding it kills 284 MB of torch" is wrong — torch is also reached via `huggingface_hub.serialization._torch`, `scipy._lib.array_api_compat.torch.*`, `onnxruntime.transformers.machine_info`, and `functorch.*` (torch's own internal subpackage). When investigating "why is X still in the bundle," read `desktop/build/pyinstaller/bristlenose-sidecar/xref-bristlenose-sidecar.html` for the actual incoming-edge list — don't grep `import X`. Confirmed during S1 + S2 surgical pass (4 May 2026).

- **`plutil -extract` splits the key path on dots, so it CANNOT read a reverse-DNS entitlement key.** `plutil -extract com.apple.developer.associated-domains raw -o - Foo.entitlements` reports *"No value at that key path or invalid key path"* on a file that plainly contains the key and passes `plutil -lint` — because `com`/`apple`/`developer`/… are parsed as four levels of nesting. Every entitlement key is reverse-DNS, so this affects all of them, and the error message accuses the file rather than the query. Cost a round-trip on 16 Aug 2026 auditing the associated-domains addition. Read the whole plist instead: `plutil -convert json -o - Foo.entitlements | python3 -c 'import json,sys; print(json.load(sys.stdin).get("com.apple.developer.associated-domains"))'`. Same family as the "unescape roff hyphens before auditing the man page" trap in the root `CLAUDE.md` — a mechanical audit whose *tooling* manufactures the false negative

- **`codesign --force --entitlements <file>` without `--remove-signature` first is unreliable when probing minimum entitlement sets** — if the outer binary already has a signature that grants, say, `disable-library-validation`, re-signing with `--force` and a trimmed entitlements file will appear to succeed (`codesign -dv` shows the new entitlements), but the process still runs because the inner `.dylib`/`.so`/`Python.framework` files retain their own signatures with the old entitlements. To genuinely test a minimum set: `codesign --remove-signature <binary>` first, then `codesign --force --options=runtime --entitlements … --sign - <binary>`. Confirmed during Track C C0 (18 Apr 2026). See `docs/design-desktop-python-runtime.md` §"How this was determined"

## Xcode, build settings and debugging

- **A custom Info.plist key cannot go in an `INFOPLIST_KEY_…` build setting — Xcode carries only Apple's own keys that way and drops the rest without a word.** The app's Info.plist is generated (`GENERATE_INFOPLIST_FILE = YES`, no file in the tree), so a key of our own goes in a partial plist merged with `INFOPLIST_FILE`: `desktop/Bristlenose/Bristlenose-OAuth-Info.plist` holds the cloud-import client IDs (18 Oct 2026). Keep such a file **outside** `Bristlenose/`, or the synced folder also copies it as a resource. Two follow-ons: a hosted test reads the merged result as `Bundle.main` (the test host is the real app; `OAuthBundledClientIDTests`), and `Bundle(for: SomeAppType.self)` in a hosted test is the **app** bundle too, so a test wanting a bundle *without* the key needs a class declared in the test target (`MicrosoftOAuthConfigTests.missingClientID`).

- **Xcode stale indexer** — sometimes shows "no member" errors that `xcodebuild` doesn't. Fix: `Cmd+Shift+K` (Clean Build Folder) then `Cmd+R`

- **Debugging the desktop app's runtime: two traps.** (1) **A shell function named `log` shadows `/usr/bin/log`** in this repo's profile — `log show …` / `log stream …` fail with `(eval):log:1: too many arguments`. Always call **`/usr/bin/log`** by full path. (2) The app logs via `Logger(subsystem: "app.bristlenose")` at **`.info`**, which macOS does **not persist** to the log store — so `log show --last …` returns only the header even with `--info --debug` (the events existed but weren't captured). To see startup/serve logs you must **`/usr/bin/log stream --predicate 'subsystem == "app.bristlenose"' --level debug`** live *while relaunching* (Cmd+R). Per-project sidecar logs (persisted) live at `<output>/.bristlenose/bristlenose.log`, but only exist once a project actually serves.

- **Debug builds: main executable is a stub; code lives in `Bristlenose.debug.dylib`.** Xcode's incremental-linking optimisation. Release builds link directly into the main executable with no debug dylib. When writing post-archive gates that scan for string literals (`desktop/scripts/check-release-binary.sh`), scan every Mach-O in `Contents/MacOS` + `Contents/Frameworks`, not just the main executable — or Debug smoke-tests of the gate will show false negatives (main stub has no literals). The gate itself should only run against Release archives; Debug is expected to contain the `#if DEBUG` branch by design.

- **Xcode expands `$(SRCROOT)` reliably in scheme env-var values; `$(HOME)` is debated.** Use `$(SRCROOT)/../../.venv/bin/bristlenose` in shared schemes that need a repo-root-relative path — it expands to the project parent regardless of where the contributor cloned the repo. Avoid `$(HOME)` (may or may not expand depending on Xcode version / context) and avoid hardcoded `/Users/you/...` paths (personal, brittle).

- **QA env vars in committed xcschemes must have `isEnabled = "NO"`.** The shared scheme `xcshareddata/xcschemes/Bristlenose.xcscheme` is checked in. When adding a debug/QA env var (e.g. `BRISTLENOSE_DEBUG_DIAGNOSTIC_FIXTURE`), Xcode's "Edit Scheme" UI defaults the new row to `isEnabled = "YES"`. Committing it that way means every contributor's `Cmd+R` injects the fixture state by default — the app boots into the QA fixture instead of normal behaviour. Pattern: when QA is done, either delete the row from the scheme OR set `isEnabled = "NO"` so it's available as a one-checkbox toggle for future QA but not active by default. The `xcshareddata/xcschemes/Bristlenose.xcscheme` diff is the audit site — grep for `isEnabled = "YES"` before committing a scheme change. Hit on `unify-failure-popover` 20 May 2026 — `failed_no_summary` was almost committed enabled, caught at the end-session verify pass. **It also breaks `xcodebuild test`, not just `Cmd+R`:** the Test action sets `shouldUseLaunchSchemeArgsEnv = "YES"`, so it inherits the Run action's env vars. A `BRISTLENOSE_DEBUG_OLLAMA_TAG` left enabled made `OllamaCatalog.recommendedTag()` return the override during tests, which failed the unrelated `LLMProviderTests/availableModels_containDefault` (the override tag isn't in the curated `availableModels`). Hit on `beat3-provider-activation` 4 Jun 2026 — the test failure is the loud signal that a QA env var is enabled in the committed scheme.

- **Committing during an Xcode build fails the build — the sidecar's freshness guard sees the pre-commit stash.** `build-sidecar.sh` hashes `bristlenose/` + `frontend/src` before and after PyInstaller and refuses to stamp a bundle if they differ ("source changed while the sidecar was building"). pre-commit's `[INFO] Stashing unstaged files` + restore rewrites those files mid-build, so a `git commit` issued while `xcodebuild` runs (or a concurrent session saving under `bristlenose/`) trips it every time — three failed builds on 20 Sep 2026 before the cause was read out of `desktop/build/ensure-sidecar.log`. Nothing is broken; the bundle it built is discarded and the next quiet run stamps. Sequence commits and builds; if another session is editing `bristlenose/`, wait for it or use the Dev Sidecar scheme, which serves live source and skips the rebuild.

- **Xcode's "Validate Project Settings" nag wants to enable Hardened Runtime for Debug — always REFUSE.** After adding an SPM package (or an SDK bump), Xcode re-offers "recommended" build settings including *"Target 'Bristlenose' — Enable hardened runtime"* which sets `ENABLE_HARDENED_RUNTIME=YES` for **Debug**. This project deliberately keeps HR **off for Debug, on for Release/TestFlight** (see "Current state vs target state" above) — Debug relaxes it so dev-mode mlx-whisper **JIT transcription** (needs `allow-jit` / `allow-unsigned-executable-memory`, only wired for the Release sidecar) and dev-sidecar signing keep working. Accepting it would mutate the App-Store-audited signing config and break dev runs. Click **Cancel**. The Dead-Code-Stripping and String-Catalog-Symbol-Generation items in the same dialog are harmless-but-pointless (the app uses JSON i18n, not `.xcstrings`); don't bundle them in either. The dialog recurs — the answer stays no. (26 Jul 2026.)

- **Safari Web Inspector for WKWebView debugging** — enable `webView.isInspectable = true` (already set in `#if DEBUG`). Open Safari → Develop → Bristlenose → pick the localhost page. The inspector opens in a Safari window, so the Bristlenose app window stays inactive — perfect for debugging inactive-window behaviour

- **Web Inspector** — enabled via `webView.isInspectable = true` in `#if DEBUG` builds only. Right-click → Inspect Element works in debug builds for diagnosing bridge/CSS issues

## Platform APIs, policy and sign-in

- **`import Security` does NOT re-export Foundation on macOS 15 SDK** — `KeychainHelper.swift` needs both `import Foundation` and `import Security`. Without Foundation, `Data` and `ProcessInfo` are undefined. The code review suggested `import Security` alone would suffice — it doesn't

- **"This application does not support printing. Please contact the application's developer." is the App Sandbox refusing the print panel — not a missing responder.** It is raised from `PMPrepareAppKitPrintPanelPrivate` inside `NSPrintPanel.beginSheet…` when the process lacks `com.apple.security.print`, i.e. `ENABLE_RESOURCE_ACCESS_PRINTING = NO` in the pbxproj. That was the setting in both configurations until 21 Oct 2026 (R69), so File ▸ Print never printed in any sandboxed build; the write-up blamed the dimmed menu item for letting ⌘P fall through, and a throwaway probe showed otherwise: `NSApp.mainMenu.performKeyEquivalent` takes ⌘P with Print dimmed, and nothing reaches `print:`. The general lesson is the one above, from the other side: **a sandbox capability is a build setting, so an `ENABLE_RESOURCE_ACCESS_* = NO` line is a feature switched off with no error at the call site.** Before shipping anything that talks to a system service (printing, camera, Bluetooth, contacts…), grep the pbxproj for its `ENABLE_RESOURCE_ACCESS_*` row. R69 pinned the entitlement present; since the 23 Oct withdrawal the same pins assert it absent. **Probing a refusal like this in a test:** swizzle `NSAlert.runModal` to a recorder first, or the refusal is an app-modal alert and the test hangs instead of failing.

- **`dlsym` a WebKit SPI identifier by its C name, which carries a leading underscore.** The SDK's `WebKit.tbd` lists `__WKMenuItemIdentifierOpenLink` (Mach-O name), so the C symbol is `_WKMenuItemIdentifierOpenLink`; `dlsym(…, "WKMenuItemIdentifierOpenLink")` returns NULL and reads as "WebKit no longer exports it". The value is the string WebKit sets on the item (`WKMenuItemIdentifierOpenLink`, no underscore). Open WebKit by path first (`dlopen("/System/Library/Frameworks/WebKit.framework/WebKit", RTLD_NOW)`): a probe that hasn't loaded it gets NULL from `RTLD_DEFAULT` too. `ReportContextMenuTests.everyWebKitIdentifierWeMatchIsWebKitsOwn` is the worked example.

- **Two system APIs retain the object you hand them, so "drop my reference and `deinit` cleans up" never runs.** `WKUserContentController.add(_:name:)` retains its script message handler, and `NSFileCoordinator.addFilePresenter` retains its presenter. Both were paired with a cleanup that relied on the object being freed: the report view's Coordinator (which holds the web view) was never removed from the content controller, so every project switch leaked the old view, still able to post into the shared bridge. `ProjectFolderWatcher` called `removeFilePresenter` only in `deinit`, which therefore never ran, so a released project's security scope stayed open and its scans went on. Fixed 11 Oct 2026 (`d29c4fc4`, `1e6dcf7f`): `dismantleNSView` removes the handler, and the watcher has an explicit `stop()`. **Rule: anything registered with a system object is unregistered by an explicit call on the way out, never by `deinit`.** **Tell, and the test:** hold a `weak` reference, drop the strong one, and assert it is nil (`BridgeChannelOwnershipTests`, `ProjectFolderWatcherLifetimeTests`). Both premises were proved red that way before the fix.

- **Apple HIG pages are JavaScript-rendered — `curl` / `WebFetch` returns only the static shell.** Loading `https://developer.apple.com/design/human-interface-guidelines/<slug>` from a non-browser client gets the HTML wrapper with `<title>Apple Developer Documentation</title>` and no body content. The real content is fetched client-side from the DocC JSON API. **Confirmed working endpoint** (probed 15 May 2026): `https://developer.apple.com/tutorials/data/design/human-interface-guidelines/{slug}.json` — slug matches the URL path segment (`sidebars`, `color`, `typography`, etc.). Returns full DocC JSON: `primaryContentSections[0].content[]` carries the actual body (paragraph/heading/aside/list nodes); `references{}` resolves inline link identifiers; `metadata.customMetadata.alert-date` is the change-log freshness marker. The JSON also covers macOS-26-Tahoe-era updates the training cut may have missed. When citing HIG conventions in design discussions, **fetch the JSON and quote the actual section** rather than recalling from training — my training was demonstrably fuzzy on typography roles, semantic colour usage, and sidebar conventions specifically (15 May 2026 session). Long-term plan in `docs/private/handoffs/hig-corpus.md`: build a local mirror, wire `what-would-gruber-say` + adjacent agents to read from it.

- **`URLResourceValues.volumeIdentifier` is typed as `Any?`/opaque, not `Hashable`.** Apple types it as `NSCopying & NSObjectProtocol & NSSecureCoding` in the docs; in Swift 6 strict mode you can't wrap it in `AnyHashable` directly ("'AnyObject' cannot be used as a type conforming to protocol 'Hashable' because 'Hashable' has static requirements"). To compare two volumes, cast both to `NSObject` and use `isEqual:` — that's what `CopyMachinery.sourcesShareVolume(with:sources:)` does. Use this whenever same-volume detection matters (clonefile shortcut, disk-space precheck skip, etc.).

- **`.nonPersistent()` creates a new partition every call** — the most common mistake with multi-WKWebView setups. Two views that each call `.nonPersistent()` are fully isolated (no BroadcastChannel, no shared localStorage, no shared cookies). Store the instance in a singleton (`SharedConfigStore.shared.dataStore`) and pass it to both configs. See `docs/design-wkwebview-messaging.md`

- **Custom URL schemes + `.nonPersistent()` crash WebKit on macOS 26** — `WKURLSchemeHandler` with a custom scheme (e.g. `spike://`) and `.nonPersistent()` data store crashes the WebKit network process. Use HTTP (localhost) instead. Bug is specific to custom schemes, not a general `.nonPersistent()` regression

- **`kSecAttrAccessControl` and `kSecAttrAccessible` are mutually exclusive** — the `SecAccessControl` object built by `SecAccessControlCreateWithFlags(_, protection, flags, _)` embeds the protection class. Passing both attributes to `SecItemAdd` produces `errSecParam` (-50). Choose one: plain `kSecAttrAccessible` for unlock-only items, or `kSecAttrAccessControl` for biometry/passcode-gated items. Used by `KeychainHelper.set` (May 2026 Touch ID change). **Separate gotcha:** whether `SecItemUpdate` with a new `kSecAttrAccessControl` rewrites an existing item's ACL is not contractually documented by Apple — don't promise "re-saving upgrades the entry" in user-facing docstrings; the reliable upgrade path (delete + add) is forbidden by `feedback_never_script_keychain_deletion`. Surface `errSecAuthFailed` as a distinct log line so an invalidated-`.biometryCurrentSet` entry (enrolment changed, or user cancelled the auth sheet) is greppable from Console.app rather than producing a silent `false` return

- **An HTTPS OAuth callback wants `webcredentials:`, NOT `applinks:` — and getting it wrong fails by HANGING, with no error anywhere.** `ASWebAuthenticationSession.Callback.https(host:path:)` (macOS 14.4+) is validated against the Associated Domains **`webcredentials`** service specifically. With an `applinks`-only entry — the intuitive choice, since "route a URL back to my app" is what applinks is for — the session opens, the consent page renders, the user approves, and **nothing ever comes back**: no callback, no timeout, no `ASWebAuthenticationSessionError`. Added 16 Aug 2026 for Zoom cloud import (`webcredentials:bristlenose.app`, both build configs). The other half is a static `apple-app-site-association` at `https://<host>/.well-known/apple-app-site-association` listing `<TeamID>.<BundleID>` — here `Z56GZVA2QB.app.bristlenose` — served over HTTPS with **no redirect** and **`Content-Type: application/json`**. That last one bites on Apache: Apple requires the file be extensionless ("don't append `.json`"), so the server guesses and DreamHost serves `text/plain`, which `swcd` rejects silently. A scoped `<Files "apple-app-site-association">ForceType application/json</Files>` fixes it. Both halves or neither works. If macOS already cached a failed lookup, `swcutil reset`. **And note Release will not self-heal:** adding this entitlement means the Manual-signed `Bristlenose Mac App Store` profile needs Associated Domains enabled on the App ID, or the archive fails to sign — Debug is Automatic and mints its own, so the failure hides until someone archives for TestFlight

- **An HTTPS OAuth callback on a developer Mac can fail because a DIFFERENT copy of the app is the one macOS consults.** `swcd` takes an app's Associated Domains claim per bundle ID, and LaunchServices may hold dozens of registered `app.bristlenose` bundles: the `.dmg` in `/Applications`, archive exports, mounted `.dmg` volumes, and a scratch DerivedData from every past session (101 on 17 Oct 2026). When the copy it reads lacks `webcredentials:bristlenose.app` (a `.dmg` cut before 18 Oct 2026 does), the Zoom sign-in fails in ~10 ms with no sheet, and our window says "Sign-in didn't finish", because Apple reports this with the same code as a user cancel. **Diagnose:** `/usr/bin/log show --last 5m --style compact | grep 'not associated with domain'` (SafariLaunchAgent names the app ID and domain), and `sudo swcutil show | grep -i bristlenose` (no entry = never registered). **Fix:** unregister every copy but the build under test (`lsregister -dump` lists them; `lsregister -u <path>` each; `lsregister -f <build>`), then `sudo swcutil reset`, ⌘Q and relaunch. Nothing is deleted, and `lsregister -f` restores any of them. Real users have one copy and never hit this. Measured 17 Oct 2026, first live Zoom sign-in.

- **Printing is post-v1 (owner, 23 Oct 2026): no `com.apple.security.print`, no File ▸ Print or Page Setup, no ⌘P.** What printed was not a deliverable (`docs/design-printing.md`). `ENABLE_RESOURCE_ACCESS_PRINTING = NO` in both configurations; `PrintEntitlementTests`, `tests/test_entitlements_split.py::TestTheSandboxRefusesPrinting` and both artefact gates fail if it comes back, and `PrintActions` is parked unreferenced. The entry below is the R69 record, still true of the mechanism.

- **Consent version bumping** — when AI disclosure content materially changes (new cloud provider, new data category sent to LLMs), bump `AIConsentView.currentVersion`. The dialog re-shows for users who acknowledged a lower version. Bump for: adding a new cloud provider, sending a new data type. Don't bump for: copy tweaks, layout changes, adding Ollama features

- **`-only-testing` needs the trailing `()` for a Swift Testing test.** `-only-testing:BristlenoseTests/Suite/test` starts the suite, runs nothing and exits 0 with no verdict line; `-only-testing:'BristlenoseTests/Suite/test()'` runs it. A suite-level selector needs no parentheses. Cost two silent runs on 25 Sep 2026.

- **Getting a measured VALUE out of a Swift test: only a file works, and the file must land inside the container.** xcodebuild's default reporter drops the test process's stdout, so `print()` reaches nothing; `Logger.notice(…, privacy: .public)` from the test host did not surface in `log show` either; and an `Issue.record("<payload>")` comment does not reach the test log — the run reports the failure and swallows the message. Three channels, three silent losses, four build/test cycles (3 Sep 2026, measuring Settings pane heights). **Write the value to a file, and assert the write.** The host is sandboxed — `ENABLE_APP_SANDBOX = YES` arrives as a *build setting*, not from `BristlenoseDebug.entitlements` (root `CLAUDE.md` has the full trap) — so `~/Documents` and `/private/tmp` are both denied, and a `try?` makes the denial look exactly like a test that never ran. `NSTemporaryDirectory()` resolves to `~/Library/Containers/app.bristlenose/Data/tmp/`, which is writable from inside and readable from outside. Same family as the `&& ok` gate that cannot fail: the reassuring path is the one that reports nothing. **Correction, 29 Sep 2026: the `Issue.record` message is not lost, it is only absent from the text log** — pass `-resultBundlePath` and read it back with `xcrun xcresulttool get test-results tests --path <xcresult> --compact`, where each recorded comment is the `name` of a `"Failure Message"` node, verbatim and multi-line. No file, no container, no TCC. The test goes red on purpose, so keep it in a throwaway probe. Each name starts `Issue recorded: `, so strip that before matching a payload prefix of your own. **And the file route above no longer works from a shell: on 17 Oct 2026 `cat ~/Library/Containers/app.bristlenose/Data/tmp/…` answered `Operation not permitted` (TCC).** Use the result bundle. **Probing `SidebarOutlineController` headless:** its `i18n` is `weak`, so `controller.i18n = I18n()` is nil at once — hold the `I18n` in a local, or every tooltip (the agent badge's included) reads as absent. A real inline rename needs a key window (`orderFrontRegardless` + `makeKey` off-screen); without one `beginRename` rolls back.

- **A Swift test that spins `RunLoop.main.run(until:)` freezes every SwiftUI animation at frame 0 — suspend with `Task.sleep` instead.** A synchronous test body holds the main dispatch queue, and SwiftUI drives animation through it, so an animated `columnVisibility` write started, never advanced, and was completed instantly by the *next* animated write — the view lagged one state behind, and "the sidebar comes back at 0 pt" looked like a real AppKit bug for a whole round of diagnosis (25 Sep 2026, `SidebarFitHarnessTests`). `DispatchQueue.main.async` blocks never run inside such a test for the same reason. Make the test `async` and `try await Task.sleep(…)`, which returns the main thread to the app's run loop. **Tell:** an animated change that does nothing for two seconds while the non-animated one works. **Getting values out:** `Attachment.record(text, named:)` lands in the `.xcresult` and `xcrun xcresulttool export attachments --path <xcresult> --output-path <dir>` reads it back — the working channel where stdout is dropped and the container tmp is TCC-blocked from outside (the file route below).

- **A verification sweep run before all the edits have landed reports clean, because there is nothing to verify.** Distinct from a wrong check — the check is correct and the input is empty, and a zero-result grep is indistinguishable from a zero-problem grep. Hit during a `/true-the-docs` pass: the cross-reference check ran after the first of three docs was edited, that doc's added lines happened to contain no paths, and "no output" was read as "no dead links". The dead-link check only found anything on a re-run after all three had landed. **Two habits:** run the sweep *last*, and when a check produces no output, assert the input was non-empty before believing it (`… | wc -l` alongside the check, or a loud `no candidates to check` branch). Generalises to any audit loop — `for x in $(cmd)` with an empty `cmd` runs the body zero times, exits 0, and prints nothing. Same shape as the `&& ok` gate that cannot fail, in the root `CLAUDE.md`. (27 Aug 2026.)

- **Verifying Swift while another session edits the same tree is not verification — isolate.** With a concurrent session mid-edit on a shared type, six successive builds of *identical* source reported 3 → 1 → 10 → 1 errors, and the ten were cascades *into* my own files from a half-saved protocol next door. The fix is a throwaway worktree at HEAD with only your own changed files copied in:
  ```bash
  git worktree add --detach /tmp/bn-verify HEAD
  cp <your changed files> /tmp/bn-verify/<same paths>
  ln -sfn "$PWD/desktop/Bristlenose/Resources" /tmp/bn-verify/desktop/Bristlenose/Resources
  cd /tmp/bn-verify/desktop/Bristlenose
  BRISTLENOSE_SKIP_SIDECAR_ENSURE=1 BRISTLENOSE_ALLOW_STALE_SIDECAR=1 \
    xcodebuild build-for-testing -scheme Bristlenose -configuration Debug \
    -destination 'platform=macOS,arch=arm64' -derivedDataPath /tmp/bn-vdd \
    BRISTLENOSE_SKIP_SIDECAR_ENSURE=1 BRISTLENOSE_ALLOW_STALE_SIDECAR=1
  ```
  Three things bite in that order, all documented separately above but never together: the **first** build fails on `GeneratedBuildInfo` (gitignored, written by a build phase — just re-run); the Ensure phase then wants `frontend/node_modules`, which a worktree doesn't have; and the freshness gate then calls the sidecar STALE. The two env vars are the Swift-only bypass, and **they must be passed twice** — once as environment, once as an `xcodebuild` setting — or the build phase's own shell doesn't see them. `git worktree remove --force` when done. This is also what surfaced the missing-commit gotcha above. **Copy a file only if every hunk in it is yours** — `git diff <file>` first; a file another session is also editing brings their half-finished hunk across, and the worktree build fails on a property defined in one of their other uncommitted files. Apply your own hunk instead: `git diff <file>`, keep the hunk, `git apply` it in the worktree onto `git show HEAD:<file>` (24 Oct 2026, `MenuCommands.swift` during R85).

- **`StubURLProtocol` redirects arrive with NO headers, and the adapters' fetches never reach it unless you pass the session through.** The stub answers a 3xx with `wasRedirectedTo: URLRequest(url: next)`, a fresh request, so a test asserting that a header *survived* a redirect is really testing whether the redirect delegate set it explicitly (which is what `CloudDownloader` now does for Zoom's domain rule; whether real URLSession keeps `Authorization` across hosts is undocumented). And `TeamsSource` / `GoogleMeetSource` build `CloudDownloader()` with no session, so an adapter-level `fetch` goes to the real network and fails as `downloadFailed` — only `ZoomSource` passes its injected session through (`injectedSession`, 17 Oct 2026). Copy that seam before writing a Teams or Meet fetch test.

- **A new Swift Testing suite that drives `StubURLProtocol` must be nested inside `CloudTransportTests` and `.serialized`.** The stub is process-wide static state, so a top-level sibling suite runs *in parallel* with the existing ones and steals their queued responses — one test consumes the 400 meant for another and the assertion times out on an empty spy. Nesting (`extension CloudTransportTests { @Suite(…, .serialized) struct … }`) puts it under the parent's serialisation. That file's header already records the same lesson from the other direction (three suites that passed in isolation and failed six tests in the full run); this is the cross-file corollary.

- **"The test runner hung before establishing connection" is a modal dialog at launch — the host app is the real app, and it opened something that waits for a click.** Distinct from the *crashed* variant below (a crash leaves a report in DiagnosticReports; a hang leaves nothing). Measured 4 Sep 2026: a keychain read at launch reached a login-keychain item `bristlenose configure` had created, securityd put up *"Bristlenose wants to use your confidential information"* for the test host (`/usr/bin/log show --predicate 'process == "securityd" AND category == "kcacl"'` shows `displaying keychain prompt for Bristlenose.app(<pid>)` at the second the run started), nothing in xcodebuild's output said so, and the suite sat for its six-minute deadline until the dialog was answered by hand. Any launch-time path that can raise UI — a keychain ACL prompt, an `NSAlert`, a TCC request — hangs every test run on a machine in that state, which is a developer's machine by definition. Keychain reads are `quiet` by default for exactly this reason (`KeychainInteraction`); when the hang recurs, the kcacl log is the first place to look. **A test that renders a real view is the other route in:** the second run of the same day did not hang the runner but raised three dialogs from `SettingsRefitTests` (it measures `LLMSettingsView`, whose key field reads with interaction allowed and saves on focus change), and wrote to the developer's keychain — which is why `KeychainHelper` is in-memory under a test host now. A dialog during `xcodebuild test` always has one of these two shapes: a launch-time read, or a rendered view.

- **A shared working tree hides missing commits — and `main` not building is invisible from it.** `CloudPlatform.swift` shipped reading `BristlenoseFlags.cloudImportZoom` while that flag's definition sat *uncommitted* in the same tree. Every build on this machine passed, because the definition was right there; a fresh checkout of `main` failed at `CloudPlatform.swift:52`. **CI *did* build the Swift target and did not catch it** (18 Aug 2026, `c837f8b5`) — for a reason worth more than the incident. `mac-build.yml` has compiled every `desktop/**` push since 20 May 2026, but its `xcodebuild | tee` ran under GitHub's default `bash -e` *without* `pipefail`, so the step exited with `tee`'s status and the workflow was structurally incapable of failing. It reported success on every run, including the ones carrying 16 compile errors. This line used to read *"CI does not build the Swift target"* — false when written, three months after the workflow landed, and worse than a plain error: it made the gap look greenfield (*stand up macOS CI*) rather than one step (*add a step to the green workflow you already have*), which is how it survived another fortnight. Fixed 2 Sep 2026; the workflow now also runs `BristlenoseTests`. **The habit: a claim about what CI does is checkable in one command — read the workflow, and read a run's log rather than its badge.** The tell is that there is no tell — the only way to see it is to build somewhere the uncommitted file isn't. When a session adds a *reader* in one file and its *definition* in another, check `git status` before believing a green build, or build at HEAD in a throwaway worktree.
