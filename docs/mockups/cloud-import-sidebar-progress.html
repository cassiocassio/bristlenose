The ring in the sidebar, and who tells it what

The researcher presses Import, sees it working, and closes the window — because it looks like it is working. From that moment the only place the download exists on screen is the project's own row. This is what goes there, and how it gets there.

Design artefact · 17 Aug 2026 · relates to docs/design-cloud-import.md §9, docs/design-sidebar-activity-indicators.md

The finding that shapes all of this: the component already exists. ProjectRowActivityIndicator.Kind already has .copying(fraction:) — “a drag-import copy is in flight into this project, fraction is the 0…1 byte ratio, always determinate” — rendered identically to the run ring and sharing its hover-to-cancel, differing only in the onStop closure the call site supplies. A cloud download is a copy from further away. Nothing needs drawing. The work is entirely in the plumbing, and in one number.

1 — What survives the window closing

This is the load-bearing fact and it is already true: the store that owns the download lives above the window, so closing the window changes nothing about the transfer.

So there is no “keep it alive” problem to solve. The transfer already outlives the window. What is missing is only that nothing above the waterline currently publishes a per-project number, and nothing in the sidebar currently looks for one.

2 — The traffic, in order

Five messages. Three of them already exist and are used by drag-and-drop today; the two marked in orange are the new ones.

#From → toMessageWhy it is there
1Window → Store startFetch(destination:) Exists. The lease URL, so the publish move lands inside the sandbox grant.
2Store → Runner beginReceiving(projectID:
weights:)		 New. Declares the batch before the first byte, so the row is already showing something when the window closes two seconds later. weights is what the denominator is built from — see §4. Sibling of the existing beginAddingInterviews(projectID:count:), which is the same act with no fraction.
3Store → Runner receiving(projectID:
fraction:)		 New. One weighted number for the whole batch, recomputed on each FetchProgress. Clamped monotonic by RunProgressMath.clampedFraction — the same function the run ring uses, for the same reason.
4Runner → Row Kind.copying(fraction:) Exists, unchanged. Three renderers already switch on it (ProjectRow, ProjectSidebarOutline, ProjectSubtitle).
5Row → Store onStop → stopFetch() The ring's hover-✕ already carries an onStop closure; the call site supplies it. Cancel the batch from the row, with the window shut.

Why the Runner in the middle rather than the row reading the store directly. Download and analysis are consecutive on the same project, and the row must never show two things at once or flicker at the handover. One owner of “is this project busy, and how busy” is what makes the seam invisible. It is also where the precedent is: CopyMachinery already publishes exactly this shape and the row already merges it.

Two sweeps, not one blended bar. A single 0→100% spanning both phases needs a weight for “how much of the wall clock is download vs transcription”, and that ratio swings from 10:1 to 1:20 depending on file size and whether the model is cached. A ring built on a number that wrong stalls visibly at the seam, which is the specific way a progress indicator loses the user's trust. Two honest sweeps with the subtitle naming the phase costs one restart and lies about nothing.

And they cancel differently. Stopping a download is not stopping an analysis — different confirmations, different consequences, different recovery. The hover-✕ must mean the right thing at each moment, and a blended ring has no moment to switch on.

4 — The denominator, measured at commit

Sizes are unknown while the researcher is choosing — that much is structural. But the moment they commit, Bristlenose asks Google for the file grant, and a grant is exactly what a size read needs. So the totals are knowable a second after mouseup, before a single byte of video moves.

#MomentWhat is knownWhat the sidebar shows
1Mouseup on Import 5 Recordings Count, titles, durations. No bytes. Nothing yet — the Picker is about to take the screen.
2Google's Picker The batch can shrink here. requestMediaGrant unions what was granted, not what was asked — the researcher may deselect inside the Picker. Still nothing. A ring that started at mouseup would be counting files the researcher is in the middle of removing.
3Grant held —
prepareBatch returns		 Everything. One files.get?fields=size per granted file, four at a time, sub-second for a batch this size. Exact total bytes, exact per-file bytes. Ring appears at 0%, subtitle names the batch. Expectations set: “4 recordings · 1.2 GB”.
4Transfers start Bytes written per file, and after a few seconds a settled throughput. Ring fills against a measured total. Time remaining appears only once the rate has calibrated.
5Last byte lands — Ring completes to 100%, holds a beat, then restarts at 0 as Transcribing.

This is the version to build, and it is smaller than the estimate it replaces. driveFileSize(fileID:accessToken:) already exists in the Meet adapter — it is called per file inside fetch, one round trip too late to be useful. Hoisting it to a sweep between prepareBatch and the task group turns the ring's denominator from a guess into a measurement, and needs no new API.

It also un-blinds the free-space precheck. That check reads sizeBytes, which is nil on every Google row, so today it cannot warn before a multi- gigabyte batch. Step 3 is the moment it becomes possible and the moment it is useful — before the first byte, not at file four with the disk full.

Two ways this ships silently wrong

Counting the ticked set instead of the granted set. The Picker is a real decision point and the code already honours it — grantedFileIDs.formUnion(picked), “honour what was granted, never what was asked for”. A denominator built at mouseup from ticks is too big whenever the researcher deselects, so the ring stops at 80% over a batch that finished perfectly. It fails toward looking broken, which is the better direction, but it is still a lie about a completed job.

Completing the arc over a partial batch. If two downloads fail, the ring must stop where it stands — not sweep to 100% before handing over. A filled ring is the strongest “done” signal on the row, and putting it over an incomplete import is this feature's own failure mode wearing the phase indicator's clothes.

The fallback, and where the estimate still earns its keep

A size read can fail per file, and a platform may serve neither size nor grant. So the weights degrade: measured bytes → duration → equal share. Duration is worth having in the ladder because it is startlingly better than counting files, which is the obvious alternative.

Known at list time — it arrives from the Meet API with the recording — and for a fixed codec it tracks bytes closely. Not needed when the size read works; the right thing to fall back to when it doesn't.

Clamp regardless. Measured or estimated, the denominator can still move — a size read that lands late, a file dropped from the grant. RunProgressMath.clampedFraction(raw:previous:) already exists for a ring whose total is a moving target, one feature over. Same problem, same answer, and it costs one call.

Time remaining waits for calibration. Bytes-remaining over the first sample says “4 hours”. The run ring already refuses this — nil → indeterminate spinner (uncalibrated first run before any measured signal) — and the download deserves the same discipline: the ring fills from the first byte, the words hold until the rate settles.

A global toolbar pillno Per-project activity lives on the project's row — settled 19 Jun 2026, and it is why the drag-import copy pill was removed.

6 — Open, and genuinely open

Two projects receiving at once. CopyMachinery allows exactly one in-flight copy and refuses a second. The import store is per-window and there is one window globally, so today it cannot happen either — but the ring is per-row and would render N of them correctly, so this is a policy question rather than a rendering one.

What the row says when the batch was stopped or partly failed. The ring disappears; the words are what remain. That belongs with the decision about whether a partial batch starts an analysis at all — same fork, and it should be answered once.
