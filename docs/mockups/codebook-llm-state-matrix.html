2  Axis B — codebook state (per framework)

Decided: a codebook is installed or not installed, and that is very nearly all of it. A run is a per-project activity, not a property of the codebook — so it belongs where per-project activity already lives, and the codebook card carries at most an acknowledgement that the click landed.

The codebase already states this rule, in the copying case of ProjectSubtitle: the toolbar copy pill was removed because “copy is a per-project op, so it lives on the row; the title-bar pill is reserved for app-global ops… Mac direct manipulation: feedback appears on the row you dropped onto.” AutoCode is the same shape. Out-of-credit, being genuinely app-global, is the pill’s business and nobody else’s.

The one thing the split does not cover

It handles activity cleanly and leaves residue homeless. A run in flight has the row and the chip; a run that failed has the toast — and then the toast goes away. What remains is a codebook that is installed and has coded nothing, and under the pure model nothing anywhere says so. That residue is the subject of §7, and it is the only reason the card carries anything beyond Install/Uninstall at all.

6  Decided

  1. A codebook is installed or not installed. A run is a per-project activity, not a codebook property — same rule the codebase already applies to copy, where the toolbar pill was removed in favour of the row.
  2. Running shows on the card as ✦ Autocoding… and no more. Direct manipulation: feedback appears on the thing that was clicked. Progress, elapsed and Cancel stay on the chip, which is the cross-navigation surface. The sparkle is already the AutoCode mark (autocode.chip.coding), so this is existing vocabulary.
  3. Partial gets a third segment: · ⚠ Partial 58 of 72, appended to the sentence that is already there. No new chrome, no status word standing alone, and the ⚠ is the settled WARNING glyph — “complete, usable, not what was asked”, which is exactly what a partial is.
  4. Failure reasons go to the project status popover, whose stated job is telling an alpha tester what failed. Not to the card, which says only that coding did not happen.
  5. Uninstall during a run cancels, then removes — it does not become a disabled button with a tooltip. The intent is legitimate, Cancel already exists on the chip, and design-pipeline-diagnostic-popover.md records that .help(...) tooltips were dropped from this surface family. The uninstall sheet already states destructive impact and is the place for one more sentence.

7  What that decision costs to build

Ordered. The first item gates the rest — none of §4’s renderings can exist until the lens can see a job.

  1. The lens must fetch coverage. getAutoCodeStatus has zero call sites in the island, its navigator or its page, and CodebookResponse carries no job data — only framework_quote_totals, which counts accepted tags and cannot answer “how much did it read”. A per-framework {status, processed, total} alongside it is the smallest thing that serves every rendering above.prerequisite
  2. The sidebar has no case coding. 23 ProjectSubtitle cases — running, queued, copying, importingBatch, completedPartial — and not one about coding or tagging. “The project row shows the run” is the right model and not yet the behaviour.
  3. A partial is still a permanent hole, whatever the card says. 409 already_applied blocks a re-run and reapply_to_new_quotes only codes sessions imported after the watermark, so the 14 unread quotes are unreachable by every existing path. The card would be honestly reporting a state with no exit. The quotes are known at failure time — they are the batches that raised — so finishing the job is available and would make the segment self-clearing.
  4. AutoCode has no cause to put in the popover. The popover eats PipelineState from the pipeline events log — stages, per-session causes, a terminus. An AutoCode job has none of those. Routing its failures there means giving it a cause in that vocabulary, not giving the popover a second data path.

8  Still open

  1. What the card says when nothing was coded at all. Partial 0 of 72 is wrong — nothing partial happened. It also has to cover the refused case, where no job exists to have a denominator. And it must stay distinguishable from the legitimate “ran fine, matched nothing”, which today renders identically.
  2. Whether partial should be a resting state at all. If §7.3 is done and the job finishes itself, the ⚠ segment is transient — a thing seen briefly and then gone. If it is not done, the segment is permanent and names a dead end. Same pixels, very different promise.
