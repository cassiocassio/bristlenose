6  The gaps

Ranked by what a researcher loses. No treatments proposed.

  1. A partial run is a permanent hole, and it is the one the rate limits produce. 58 of 72 quotes coded, job completed — so start_autocode_job refuses a re-run with 409 already_applied, and reapply_to_new_quotes only ever codes sessions imported after the watermark. The 14 quotes nobody looked at are unreachable by every path that exists. This is the state a rate-limited run lands in, which makes it the real rate-limit defect — the backoff people reach for is already there, six SDK retries deep, honouring Retry-After.
  2. Three outcomes share one rendering. Coded-nothing, refused-before- starting, and coded-nothing-because-nothing-matched are the same pixels. The third is a legitimate result, so the researcher cannot treat a bare 28 tags as a problem — which means the signal is not merely weak, it is uninterpretable.
  3. Recovery exists and cannot be reached. A failed job is discarded and re-run by the start guard — pinned by test_dead_job_can_be_rerun — but the card reads Uninstall, because the template was imported before the job ran. The only route back is Uninstall → Install, which nobody would guess and which throws away the researcher’s own edits to those tags.
  4. Nothing re-runs after the condition lifts. A provider switch or a new key posts .bristlenosePrefsChanged and restarts the sidecar — a strong signal, unused. A top-up emits nothing at all, and OutOfCreditModel’s own comment records that refocus re-reads the cache without revalidating, so even the pill lingers.
  5. The lens reads no job state at all, so none of the above can be rendered without first giving it the data. That is the prerequisite for every treatment, and it is a wiring job, not a design one.
