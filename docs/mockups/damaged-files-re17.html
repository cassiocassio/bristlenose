Damaged files: what the researcher sees

One rule for three files. Bristlenose never writes over a file it couldn’t read. A file the researcher edits (people.yaml) is left where it is, and the message names the broken line. A file Bristlenose keeps for itself (the pipeline manifest, projects.json) is set aside as .damaged-<stamp> and a new one is started. The message appears once, where the researcher is looking: the terminal for the CLI, the app for the Mac.

Palette Scheme
Artefact: the real pixels. Every word is a shipped key, or the frame bar flags it as owner-written. Commentary: why it works. Not the product.

Commentary

What’s wrong today

PipelineRunner.swift reads the manifest with JSONSerialization. When parsing throws, which is what a truncated file does, the code falls into the same catch as a failed read, so the row says Can’t be read. That state also sets needsFolderAccess, so the popover offers Locate…, a folder-permission remedy for a folder that is fine. Only a file that parses but has the wrong shape reaches “Project file damaged”.

Either way the row is a dead end. pipelineIsFree refuses every .unreachable, so the menu has neither Analyse nor Re-analyse, although the shipped sentence says “re-analysing will rebuild it”. Re-analyse would be the wrong verb anyway: it’s --clean, which discards the researcher’s stars and tags.

After

A failed read stays .unreadable. A read that worked but won’t parse is .damaged, which is error kind, as it already is. .damaged counts as “pipeline free” for Analyse only. The run sets the file aside (pipeline-manifest.json.damaged-<stamp>) and runs every stage again. Nothing new is drawn: the pill, the glyph, the popover, Show Log and the menu item all ship today. The only change is the one sentence.

Not built (owner, 22 Oct): a last-good copy of the manifest. It’s parked until after V1. R111 came from the 19 Oct audit’s probe, a damaged manifest has never been seen in the wild, and since 04d30698 the write fsyncs before it replaces the file.

Commentary

A keeps today’s shape (an em-dash clause, as in its siblings in the diagnostic.unreachable.* family) and its first half. It changes the verb to the one on the menu and says what the rebuild costs.

B is honest about a second cost: re-extracted quotes won’t come out identical, so curation on those that change can be orphaned. It runs to two clauses and adds a loss warning without a confirm. The house rule is to confirm only for a real loss, and this one is uncertain.

C needs no translation work, but its verb disagrees with the menu item. That mismatch is the bug this decision exists to remove.

Your project list couldn’t be read

It was set aside and a new list started. Your projects are untouched in their folders, with their reports and edits — drag each folder into the sidebar to add it back.

Commentary

Mechanism: a stock NSAlert (.warning), presented as a sheet on the first window once launch has settled. It isn’t app-modal, because the message is about this window’s empty sidebar. It shows once, after ProjectIndex.load() has moved the file to projects.json.damaged-<stamp>, and never again unless another file is damaged. There is no Show in Finder: the copy sits in the app’s container, where a researcher can do nothing with it.

Remedy 1 (do something): drag the folders back. The research is safe, because each project’s database and edits live in its own folder (bristlenose-output/.bristlenose/bristlenose.db, matched by the study marker). What is lost is the sidebar arrangement: groups, order, icons and agent access.

Edge case, accepted: if the set-aside itself fails (saveRefused), the same alert shows, but projects added back last only until the next launch. That launch tries the set-aside again.

Commentary

people.yaml is the researcher’s file (“edit them freely”, says its header), so a typo is theirs to fix, and the fix is one line in a file left exactly where they made it. The run gets the same tolerance in analyze, render and coverage. With no decision needed, write_people_file becomes atomic (tmp + fsync + replace), so Bristlenose can no longer truncate the file itself.

“Pipeline manifest” stays CLI vocabulary. status already uses it, and a CLI researcher can find the file. The Mac never says it: there it is the shipped “Project file damaged”.
