1 · The toolbar sequence

Each lens, today and proposed. The subtitle is the shipped per-lens subtitle; the counts are illustrative.

Decided (3 Oct 2026; design doc §4.3–4.4, rev 3). Leading is unchanged: the list toggle, then the back/forward group with its current behaviour, then the title and per-lens subtitle. Trailing has two groups:

  • One actions capsule, as today: Export first, then the lens's own buttons.
  • Search on its own, always the rightmost item: the native .searchable field. Wide: room for a real input field. Narrow: still its own control, and focusing it expands it in place. Multi-lens search is next, so search's prominence will only grow.
  • Live on Quotes. On Sessions, Codebook and Signals it's present but doesn't respond yet, which replaces today's disabled button. Placeholder stays “Search” there too (decided 3 Oct): alpha, no interim wording. Project has no search until ⌥⌘F ships.

Not chosen. An earlier draft of this page put Export in a third group of its own, between the lens buttons and Search: rejected, Export stays first in the capsule as it is today. A lens-aware subtitle was floated as an idea and turned out to be already shipped (the SPA sends each lens's subtitle over the bridge), so it isn't a decision here.

The field's look. Today's hand-drawn capsule has a .quaternary fill, and macOS 26 wraps it in the shared glass, giving a grey pill inside a glass pill (frames marked “today”). The native field is the clean, light glass that NetNewsWire and Photos get.

Narrow window: what folds first

When space runs out, the whole actions capsule folds into », Export included, since it's part of the capsule. Search stays on its own: it shrinks to a magnifier and expands in place when focused. That's the native field's own behaviour. The back/forward group is untouched.

How the decision was reached (3 Oct 2026). In order: B (a labelled footer, from Notes/Reminders/Mail's + −) → C (B plus Things' explaining menu) → D (B plus a Settings gear, from Things' sliders and Mail's ?) → the owner called the stack “too apologetic” and “non-standard” → back to B stripped bare → E, the purist NetNewsWire default, chosen; C rejected as too verbose, D rejected because its label repeats the main area's New Project prompt and ⌘, is where Settings lives. Click behaviour: a plain menu, so New Folder is discovered (decided later the same day). Spec: §3.3 rev 3.

Decided: E. The sidebar's own toolbar holds, in order:

  • Sidebar toggle hard against the traffic lights. It's the last control left when the sidebar is narrow, so it's always findable.
  • +⌄ trailing, right-aligned to the sidebar's width, opening New Project… / New Folder… (both shipped menu.file.* strings). It hides when the sidebar is narrow, and disappears with the sidebar, as NetNewsWire's does.

The in-list grey row (A) goes. B, C and D stay on the page as the alternatives we considered.

Implementation (plan reviewed 3 Oct 2026, five agents + parsimony pass): the smallest change. The sidebar already has a toolbar item — today's New Folder button (folder.badge.plus, frame A) — and the +⌄ takes that exact slot: same modifier, same placement, the button swapped for a menu. The sidebar toggle is not touched: it is the system's, already beside the traffic lights, and the fit-to-width logic and its tests drive it through AppKit. The flag-off AppKit sidebar has no toolbar item today and gets none in rev 3. Removing the grey row is its own commit, proven against the macOS 26 empty-list trap before it lands.

Build checks: (1) hiding when narrow is whatever the system does with the slot — observed, not engineered. (2) Bettina's discoverability gap is covered by the visible +, ⌘N, and the empty project's own button (section 3). Correction: the main window with nothing selected now shows a drop-only card (399d5da1, 3 Oct 2026), so “the main area already shows New Project” — the reason given against D — no longer holds; D stays rejected on the ⌘, grounds.

Click behaviour, decided: a plain menu, as in NetNewsWire. A click opens New Project… / New Folder…, so New Folder gets discovered. Build check: where the + sits in the AppKit sidebar.

Not drawn: no − beside the +. Deleting a project stays in the right-click menu and the menu bar, with its confirmation.

3 · The empty project: fill it without dragging

After New Project, the detail pane asks for interviews. Today it only accepts a drop.

Bettina's “make it first” model already works up to the second step: New Project creates the project and puts its name into rename mode. Then the pane says “Drag Interviews Here” with no button, which is a dead end for anyone who doesn't drag (dragInterviewsPane, ContentView.swift).

Decided (3 Oct 2026): 2b. The pane keeps its shipped title and description and gains a primary Choose Interviews… button, whose picker accepts files and folders. That's one new key. Option 2a, rejected, reused the shipped menu.file.addFiles (“Add Files…”). No new string, but today's picker (addFilesToSelectedProject) takes files only, not folders. 2b needs a picker that also accepts folders, since researchers often keep one folder per study. It reuses the Add Files panel rather than adding a second one; the two names for one act (“Choose Interviews…” on the pane, “Add Files…” in the menu) are accepted for now. Dropping still works.

Related, not in this work: with no project selected the main window now shows a drop-only “Drop a folder” card (399d5da1, 3 Oct 2026) — the same dead end for a user who doesn't drag. That card belongs to the Welcome work; noted here so the next pass sees it.
