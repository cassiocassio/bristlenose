2 · Finding a project in a long sidebar (item 7)

The 22 Mar ask was a mechanism (.searchable()). That mechanism is measured dead on this split view. The need is still real for a researcher with twenty studies. Three ways to meet it; the frames crop to the sidebar, because that is all that changes.

A · Type-select, as AppKit gives it

Sibling: Finder's sidebar and every NSOutlineView; our own PersonPickerPopover implements typeSelectStringFor by hand for word-start matching.

the researcher has typed "ro" with the sidebar focused

Build cost
S — possibly nil: allowsTypeSelect defaults to true and nothing in ProjectSidebarOutline turns it off. Verify in hands; if a row's cell view hides its string from AppKit, implement typeSelectStringFor as the person picker does (word-start match, so "on" finds "Diary — onboarding").
Layers touched
ProjectSidebarOutline.swift at most.
Risks
Invisible until known; no affordance says it exists. That is the Mac norm for sidebars (Finder, Mail), and it fits "not needy UX".
Rules out
Nothing. B can sit on top.

B · A filter field in the sidebar column

Sibling: CloudImportWindow's .searchable(placement: .toolbar) filter (its own window, so the split-view trap does not apply); Xcode's navigator filter at the column's foot.

a filter field at the column's foot; rows that do not match fall away

Build cost
M — an NSSearchField hosted in the sidebar column's footer (sidebarWithFooter is where a sidebar item goes, per the gotcha), a filter on the outline's data source that keeps folders whose children match, and a way to clear it when the selection changes. Not .searchable.
Layers touched
ProjectSidebarOutline.swift, ContentView's sidebar footer, one new key in 21 locales (the placeholder).
Risks
A field that is empty 99% of the time takes 28 pt from a column that already fights for height (the lens rail, the footer version line). Filtering an outline with folders is a classic source of "where did my project go" when the filter is forgotten. Finder, Mail and Notes do not do this for their sidebars; Xcode does because its navigator holds thousands of rows.
Rules out
Nothing, but it occupies the footer slot that the sidebar status roll (10 Nov decisions pending) may also want.

C · Nothing further — the menu bar is the finder

Sibling: Help ▸ Search already indexes every menu item; Window menu lists open windows.

no change to the sidebar

Build cost
—
Risks
Help ▸ Search finds menu items, not projects; the sidebar's folders and drag-to-reorder are the sanctioned way to keep a long list findable. At twenty studies this holds; at eighty it does not, and the sessions-are-1:1 research pattern (18 Oct 2026) says most researchers run a handful of studies a year.
Rules out
Nothing.
Commentary — §2, is this Bristlenosey?

Kind: navigating the project sidebar (ruling docs: design-project-sidebar.md, design-desktop-sidebar-appkit.md). A follows the outline's own primitive and needs nothing new unless a check proves type-select off; B departs with a sentence ("the sidebar is an outline; we add a filter because the list can outgrow a screen") that Xcode supports and Finder, Mail and Notes do not; C is the status quo. The one thing not to do is re-spike .searchable on the split view: the measurements are in docs/design-desktop-toolbar-appkit.md so that nobody re-derives them.

Open fact the owner can settle in ten seconds: click a project row, type the first letters of another project's name, see whether the selection moves. If it does, A is already shipped and this item closes as done with no commit.

In a browser, text shows an I-beam because any text might be selected. In a Mac app, static text shows the arrow; the I-beam appears over fields. The embedded report is a web page inside a Mac window, so it currently behaves as a browser. Three positions.

Commentary — §3

The glyphs drawn beside each card are the macOS arrow and I-beam at roughly 1×, placed where the pointer rests; they are not part of the page. B is the only option that treats the question as a scope, which is the word the finding used. Its cost is one rule because the platform fork already exists for type (tokens-desktop.css); it is where this belongs, not in React and not in Swift (WKWebView cannot override a page's cursor without injecting CSS, which is the same rule in a worse place). A is a defensible no, with Mail as the precedent; it should be a decision rather than a default.

Recommendation

Close the row. Ten of its thirteen items are done, done better or made moot by later decisions, and the two that remain are small enough to settle in a morning. Re-file the two as their own one-line items so the 22 Mar bundle stops reading as open work.

Item 7: A, after a ten-second check. Click a row and type; if the selection moves, it is shipped.
