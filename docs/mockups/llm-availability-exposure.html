LLM availability — how to expose it

An exposure sketch, not a design. The plumbing landed first (an all-batches-failed job is now failed and classified; the refusal mapper is wired back up; the Mac out-of-credit pill hears about sidecar jobs). What is still open is where availability should show, and how hard it should push. The argument below is that the honest answer is three tiers, because the three states are known at three different moments and with three different confidences — one global “LLM unavailable” switch would have to pick one and be wrong about the other two.

1  Three tiers, not one switch

The distinction that matters is when the answer is knowable and how long it stays true. Configuration is a local fact and never stale. Credit is a fact about someone else’s server, and is stale the instant it is read. What actually happened is only knowable after spending.

4  Which surfaces need which tier

Every server route that spends tokens, and what it does today. The gap is not that a systemwide model is missing — pipeline_view/eligibility.py is one, exposed at GET /api/pipeline — it is that its only consumer is a table in Settings.

The shared helper the table implies

Two hand-rolled copies of _has_api_key exist (routes/autocode.py, elaboration.py), neither reading the provider registry — a third provider-name switch to forget when a provider is added. One llm_availability(settings) → (ok, RefusalReason) collapses both and gives the four ungated surfaces the same vocabulary AutoCode already speaks.not done

5  Open questions

  1. A refused install leaves the codebook installed. onInstall is importCodebookTemplate() then startAutoCode(). If the second refuses, the tags are in the codebook and nothing is coded — a half-install, which is exactly the separate-Apply state v2 exists to remove. Three answers: pre-flight before the import; roll the import back; or accept it and say so. This is a product call, not a bug fix, which is why the plumbing pass left it alone.
  2. Should tier 2 be per-control at all? The inline warning above is drawn per card. The alternative is that the pill is the only ambient signal and cards say nothing — quieter, consistent with “chrome only for what the appliance cannot cope with”, and it costs a researcher one wasted click. The sketch shows the louder option so the quieter one can be chosen deliberately.
  3. Does tier 1 differ on web and Mac? “Set up AI…” opens a native pane on the Mac and a modal on the web. Same verb, different destination — or does the web, where there is no Settings ▸ AI, need different words?
  4. What about Azure and Gemini? Per the classifier’s own honesty note, out-of-credit is only isolable on Anthropic and OpenAI; Azure has no per-account credit and Gemini folds credit, quota and free-tier cap into one signal. So tier 2 cannot exist for half the cloud providers. Silence is the right default there — but the tier-1 and tier-3 treatments must not look broken in its absence.
  5. Not proposed: a credit probe in serve mode. preflight/api_key.py already spends ~$0.0001 to answer this for run/analyze. Extending it to serve would charge the researcher for a question they did not ask, on a surface they may only be reading, and it still cannot answer for two providers. The run is the probe.
