Moderator identity: what we have, what breaks, what we need

A code-truth report on the one-name-per-code limit as it meets moderators and observers: every prior investigation and decision indexed, the as-built mechanism and schema mapped, and the consequences for the researcher drawn as frames so the failure modes can be designed out rather than argued about.

Read against commit 1446e4d (1 Oct 2026). "Shipped" frames cite the file that draws them. "Measured" claims were observed by someone running code (the transcripts plan, 30 Sep); "read" claims come from reading the code at HEAD without executing it.

Palette

In five sentences

  1. The mechanism is settled and the symptom is live. A speaker code carries exactly one name everywhere in a study (docs/design-people.md §0), participant codes are numbered study-wide, and moderator and observer codes restart at m1/o1 in every session (s05b_identify_speakers.py:451). Two moderators in one study therefore share one slot, and one name.
  2. The decision is taken, not built. Decision 1 (24 Aug 2026): identity lives above codes; the escape is naming, and naming session 9's moderator "Mike" renumbers him to m2. Decision 2 (25 Aug): moderators and observers are named in exports, participants are not. None of the UX that carries either decision exists in the tree, and the register that says the People lens "ships" is wrong.
  3. The researcher's one available correction makes it worse. The pencil on m1 opens an editor in every session at once (measured broken in Chromium and WebKit), a commit renames every session, the server writes one Person row of twelve, and the next run or reload reverts or spreads the edit by whichever row the database returns first.
  4. It travels. Moderator names are preserved in the HTML export by design, so the wrong colleague is credited with running a session in the one deliverable the recipient cannot check, and the MCP overview answers an agent with the same name for every session.
  5. Decided 1 Oct 2026, route C (Part 5b): unknown is stored as unknown. A session's moderator is null until a platform label proposes an identity or a person picks one; identities are minted on that evidence and numbered as they appear; m? renders the gap; proposed badges use the shipped AutoCode treatment in the app and read plain in the export; nothing asks the researcher to do anything. Names and identities move to the database; people.yaml is read once and retired as a store.
  6. The cloud-import transcripts plan is right to defer naming moderators from platform labels, and its study-wide-code idea (Q4) is the cheapest route to a fix, provided the key is the platform's participant id, not a display string, which decision 1's "never auto-merge on name equality" would otherwise forbid.

Part 1 Where the finding came from

A review finding on the cloud-import transcripts plan

The sentence under review is a finding against docs/design-cloud-import-transcripts.md (status: proposal; the HEAD commit of this branch). Its own §0b records the same fact from the other side, and §3 item 1d acts on it:

design-cloud-import-transcripts.md §0b, "Names", 1 Oct 2026

The literal wording of the finding ("the rule that every named speaker gets a name will hit that one-name-per-code limit for moderators…") is not in the tree. The plan's "every named speaker" became "every named participant" in 1d as a result of it; that narrowing is the finding, applied.

The plan is inconsistent about the deferred step it points at. §0 "Deliberately later" calls it 1c, study-wide moderator codes by platform participant id, not display name; §3 files the same idea under 1d as "platform-named moderators get study-wide codes by display name: Martin is m1 in every session, Mike m2", and §8 Q4 asks the owner which. Part 3 What we have now: the mechanism, the schema, and who wins

How a moderator's name gets to the screen

Seven hops, every one of them keyed by the bare speaker code. Read left to right: the pipeline mints codes, the people file keeps one entry per code, the serve importer fans that one entry out into one Person row per session, and the routes fold it back by code in three different ways.

Commentary — the three stores and their keys
people.yaml
PeopleFile.participants: dict[str, PersonEntry] keyed by code (models.py:476). compute_participant_stats overwrites stats[code] per session and logs one WARNING per run naming the sessions (people.py:194–225). merge_people keeps the editable block by key, so a typed name outlives the stats it was typed against.
bristlenose.db
session_speakers is unique on (session_id, speaker_code) and is the only foreign key to persons (server/models.py:286–311). The importer creates a new Person per (session, code) and seeds its name from the flat people[code] (importer.py:870–908). The join that "makes cross-session moderator linking possible" has never been written to by anything.
transcripts-raw/*.txt
Every line carries its code in brackets, [00:16] [m1] (Speaker B) …; the importer re-derives role from the prefix (importer.py:870–877). A recode that is not render-time has to rewrite these.
Not stored anywhere
The original speaker labels, the label→code map, name origin, "this guess was checked", and a cleared state. Absence is the only signal, and the pipeline refills absence (people.py:373–400).

The schema, as it stands

Commentary — why the schema can hold the collision, and why it cannot represent the fix yet

Nothing in the schema says a code names one person: the join key from a quote or a segment to a person is a string resolved by convention, so (s1, m1) and (s9, m1) are two session_speakers rows pointing at two persons rows that both read "Martin Storey". That is design-people §C4's point: the denormalisation is why renaming by code is free, and why the schema never objects to one code carrying two humans. The rows that could carry the fix exist (session_speakers.person_id could point two sessions at one person; a second moderator could be m2) and nothing writes them. There is no role endpoint, no rename-with-renumber endpoint, and no create-a-person endpoint (routes/data.py exposes GET/PUT /people only).

Part 8 The challenges — what makes this harder than it looks from the grid

Twelve things to design around

  1. Files in the field. Dissolved 1 Oct 2026 by retiring the file as a store (Part 5b, I5); the record stands. people.yaml is the one file researchers hand-edit, with copies in the field since the 14 Jul TestFlight. Any reshape needs a migration; any new block carries a downgrade hazard, because write_people_file does a model_dump() and an older binary silently drops what it does not know (§J2). The renumber is the design that needs neither, which is a large part of why it won.
  2. Three stores, one invariant, no transaction across them. Reduced to two on 1 Oct 2026: the database and the raw transcripts, whose bracket tokens are now within-session tags rather than identities (Part 5b). YAML, SQLite and transcripts-raw/ each hold the code, and a renumber must change all three or leave a reader that disagrees (D2). The DB half has an ordering constraint (free m1 before taking m2); the YAML half has no create path in the write-through; the file half is the open J4 question.
  3. The fixture that cannot exist. Until a second moderator can be m2, no test can express "two moderators across sessions", so the header, the sidebar and scope-at-rename have no red test to write first. The sequencing inverts the obvious order (TODO.md:583): the renumber lands before any of the surfaces it fixes can be gated.
  4. Tests that pin the limitation. test_multi_session_moderator_codes_collide_and_are_warned is a contract that the loss is announced; it must be re-homed, not deleted, when the loss stops happening. The sidebar's MULTI_MODERATOR fixture is the opposite problem: a passing test about a world the pipeline cannot produce.
  5. What counts as identity evidence. decision 1 forbids merging on name equality at every altitude, for good reason: two Marys are two people. A platform participant id is not a name; it is the platform asserting that one account spoke. Q4 must be answered with that distinction stated, or the first implementation will merge on the display string because that is what the VTT contract carries (G21, G22). Two "M. Alvarez" accounts in one tenant is rare and must still be two codes.
  6. The bank's store does not exist. "A pick, not a keystroke" needs rows that span projects, and every Person row lives in a per-project SQLite. The instance database is a prerequisite of the keystone, and it is a new database with its own migration story.
  7. Compound undo across a dead bridge. Rename-and-renumber, name-from-the-bank-and-link, re-attribute-and-fall-out-of-the-lens: each is one act to the researcher and two or three writes to the system, and the channel that would let ⌘Z span them is wired on the Swift side and not on the web side.
  8. Observers are the common case and the unnamed one. The extra person is an observer ~95% of the time; observers are never auto-named; their codes restart per session and fragment when someone else speaks first (F9). Auto-naming them before study-wide codes exist would spread the mislabel without a human in the loop (G4).
  9. The warning has no good home yet. A log line is read by nobody; a toast is banned; the popover vocabulary is a five-kind taxonomy with a flowchart for new messages. Until origin exists, the sentence can only be about sessions and codes, which is less than the researcher wants to hear and all the system can truthfully say.
  10. Localisation of a menu that does not exist. §I4 counts 141 seedable keys for the person menu across 21 full locales, with the label-plus-chooser contract (§B2) because Korean and Japanese cannot close an English cloze sentence; the fr moderator word is itself an open owner call. The sweep line in D1 is one more plural-bearing string in 21 files.
  11. The sealed renderer disagrees and will keep disagreeing. The static HTML byproduct groups by computed.session_id and drops moderators from rows; it is frozen by decision, so the two files in one output folder will describe the study's moderators differently until the byproduct is repurposed.
  12. The register that says it shipped. Two mockups are listed IMPLEMENTED for a lens that does not exist. The gate behind the register checks presence, not truth, by design; the truth has to be put there by hand, and a reader who trusts the register will skip this whole problem as solved.
