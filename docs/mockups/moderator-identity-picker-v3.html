Moderator identity — the picker, v3

The owner’s review of iteration 2, drawn (3 Oct 2026). In the grid a name the system is not sure of wears the dotted surround, as a proposed tag does; there are no ticks in the grid. Clicking a name opens the picker, where the green tick marks the current answer — the dotted most-likely name, or the name already chosen — and the selection starts on it, so Enter says yes. The other names are possibles. Typing m2 or a name jumps to it; Tab goes to the field to introduce someone new. A first line switches the role for a speaker the pipeline put in the wrong one. Each picker is drawn twice: in the web view, and as a native Mac popover.

Type-select, as in any Mac list. Codes and names both match: m2 or ker land on the same row. Nothing is filtered away — v1 lists are short (fewer than ten names, fewer than three moderators), so the list just moves the selection. Filtering a long list is the later search-as-you-type extension.

Selection is not choice. The highlight shows where Enter will land; the tick shows the current answer. They part company only while the researcher is deciding.

What is measured, and where it comes from. Type: the calibrated tokens-desktop.css ladder (Type Parity Inspector, macOS 26.4.1 @2x) — the probe confirms segmented controls, rows and fields all use the 13pt system font, which is --bn-text-label at --bn-text-label-lh. Selected-row blue: NSColor.selectedContentBackgroundColor, read from AppKit — #0064E1 light, #0059D1 dark, deliberately not the accent #007AFF the first draft used. Tick green: NSColor.systemGreen, #34C759 / #30D158. Placeholder and separator: the system's own alpha-black/white, which --bn-colour-muted and --bn-colour-border approximate.

What is sampled, so approximate. The segmented control has no named system colour, so its track and selected segment are pixel samples of the render (device RGB, window not key): the light track equals --bn-nav-selection-bg exactly; the dark one does not. On macOS 27 the selected segment is a grey pill, not the white raised one the first draft drew.

What is not measured at all. The popover’s own corner radius, arrow and material (a real NSPopover draws a translucent material the web cannot sample), the focus-halo width, and how the controls look in a key window rather than an inactive one. Those need a probe that presents a real popover in a key window.

Part 3 For discussion.

1. Web or native. The grid lives in the web view, so a web popover works in the browser, the export and the Mac app with one implementation. A native NSPopover feels more like the Mac and needs the bridge the search work just built. NSMenu is the wrong primitive: it does not host a field or a segmented control comfortably. Recommendation: the web popover first.

2. Fixing a spelling. Clicking a name now opens the picker, so the grid no longer edits names in place. Where does “Martin B Storey” become “Martin Storey”? Options: the pencil stays for spelling only; or the picker’s field edits the ticked person when one is selected.

3. Opening on an unknown slot (V6). Selection on the first known moderator (fast), or on nothing so Enter does nothing until the researcher moves (no accidental guess)?

4. “I don’t know who it was.” Is a row needed to put a slot back to m?, or is that too rare to earn one?

5. Role changes (V7). Ship the Participant and Observer segments with the first picker, or after, with the undo a recode needs?

6. Participant list scope. All study participants, this session’s first, or this session’s only?
