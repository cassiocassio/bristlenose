Redaction indicator — where the flag goes

There is no user-visible sign anywhere that a project was PII-redacted — verified 13 Sep 2026 across the SPA, the report, the export, the static renderer and the Mac. ProjectInfoResponse carries project_name, session_count, participant_count and nothing else.

Three routes below. The question underneath them is who the flag is for — the researcher confirming their setting took effect, or the colleague opening a report and needing to know names were stripped.

Route A — a badge in the report header

One neutral badge beside the project name. It rides in /info, which titles the codebook navigator and is baked into the offline export — so the same field lights the live report and the file a client opens. Silent when the project was not redacted.

Commentary

Grey, not green. Content owns colour here. Green reads as “passed a check”, and redaction is a processing state, not a success — a report without the badge is not a failed report. The house .badge atom, mono, neutral, is what the design system already has for this.

Nothing when off is the right asymmetry for the report. A “Not redacted” badge on every report is both noise and faintly alarming to a client who never asked the question. Absence is information.

The cost: the researcher only learns their setting took effect after a full analysis — and flipping the toggle costs a full LLM re-run ($0.67–$6.70 depending on size and model), because pii_enabled is in topic segmentation’s cache key. This route tells you late.

Route B — state it in the export dialog

Nothing in the report. Instead the fact is stated at the moment it matters most: handing the artefact over. Stated both ways here, because at this moment silence is the worst answer.

Commentary · hazard

This dialog now holds two privacy affordances that sound identical and are not. “Remove participant names from labels” is an export-time choice the researcher makes now, about speaker labels. “Personal details were removed before analysis” is a pipeline-time fact about the transcript text, decided runs ago and unchangeable here. Put them adjacent and undifferentiated and they will be read as one setting with a broken checkbox.

What separates them in the pixels above: the fact is a stated panel with no control; the choice is a checkbox. One is inert, one is operable, and the shapes say so before the words are read. The existing hint string already does the hardest disambiguating work — “Names spoken inside quotes are NOT removed” — which is precisely what redaction does do.

The “Not redacted” wording needs your ear. It states a fact neutrally, but on the way to a client it can read as an accusation. The alternative is to drop B2 and say nothing when off — at the cost of the one moment where the researcher would most want to be told.

Route C — both, asymmetrically

Badge in the report only when redacted; the export dialog states it either way. Same single /info field feeds both.

Commentary

The asymmetry is the argument. The report is read by people who did not choose the setting, so it should carry a positive fact and stay quiet otherwise. The export dialog is met only by the researcher, at the one moment the negative case is worth stating — so there, silence is the failure.

One field, two surfaces. Both read the same /info value, so they cannot disagree. The signal is already computed during import (transcripts-cooked/ presence) and — since 13 Sep — is trustworthy, because a run that does not redact now clears that directory instead of leaving a stale one behind.

Still open, and it is a wording call, not an engineering one: “Redacted” is short and slightly opaque — redacted of what? Alternatives that fit the badge: “PII removed”, “Names removed”, “Personal details removed”. The last is plainest and the least jargon, but it is wide for a header badge.
