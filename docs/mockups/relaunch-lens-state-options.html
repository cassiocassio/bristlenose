Mac app · relaunch · decision #182

What should the Mac app remember about each lens when it relaunches?

artefact — what would ship commentary — why, cost, risk

The question

The owner asked for “state for these and more, e.g. scroll depth, on all lenses” to be normal on relaunch. Zoom, quote grouping and panel sizes already are (R89). What is left is how fine a place each lens comes back to, and whether anything beyond the place — filters, search, the selected quote, open disclosures — comes back with it. The Mac norm is the place you were, not the filters (Finder restores a folder’s view and scroll; Mail clears search). This page lays out three widths of answer and what each costs when the content changed, when two windows show one study, in the HTML export, and in where the state has to live.

Commentary · what changes · consequences

S B2: six lines across two lists and the contract JSON, both sides already asserted. M B1: one selector per lens in ANCHOR_SELECTORS, one arm per lens in LensAnchor.action, and a new .session(id, moment) apply path (navigate, then scroll — WindowPlace already carries path + anchor, so the shape exists). Layers: frontend/src/hooks/useAnchorReporter.ts, LensAnchor.swift, ContentView.restoreAnchor, their tests. No new message, no new store, no new key in projects.json.

  • Nearest siblings: LensAnchor/useAnchorReporter (16 Aug), which already say “an id either resolves or falls back honestly”; the report’s Open … in New Window, which already lands a window on a transcript at a moment through WindowPlace. B1 reuses that arrival for a restore. B2’s sibling is R89 itself. Everything here follows; nothing invents.
  • Content changed overnight: a quote id q-p1-66 survives edits, stars, tags and renames. A hidden quote is out of the DOM → scrollToAnchor retries, gives up at the top. A re-analysis can renumber participants, so q-p1-66 could resolve to a different quote that looks right — the exact objection SessionsRouteMemory answers by clearing on run completion. Rule to carry over: clear last_anchor when a run completes, for every lens, as the route memory already does for Sessions. One line, and it is the thing that makes finer anchors safe.
  • Two windows on one study: still per study. Two Quotes windows land on the same quote; at quote granularity that is more visible than at heading granularity, but it is a tie, not an error. Per-window needs C’s store.
  • Export HTML: unchanged. The anchor reporter runs only when embedded; a browser keeps its own localStorage, so B2’s three toggles already persist there.
  • Risk: B1’s Signals and Discussion entries reverse a 16 Aug “top” decision. Signals rows are regenerated by elaboration; if their ids are not stable the restore falls to the top, which is where it is today. Low.
  • Rules out: nothing later. C is B plus a store.
Option C

The whole view: place plus search, filter, selection and disclosures, per window

Everything in B, and the window comes back with its search, tag filter, focused quote and pinned moderator questions as they were — per window, not per study, so two windows on one study each return to their own view.

Commentary · what changes · consequences

L A new bridge message both ways, a per-window store, and the SPA accepting initial search/filter/selection state at mount in QuotesContext, Toolbar and QuoteGroup (today they start empty by construction). Per-window selection is not even per-window in the SPA yet. Layers: Swift (@SceneStorage, BridgeHandler, ContentView), TypeScript (four stores and a seed), both test suites, and the LensMemory doc comment, which has to be rewritten because it argues the opposite.

  • Nearest sibling: none for the filter half — the shipped position is the carve-out. For the store half, WindowSeed is the per-window value macOS restores, but it is identity, not state; @SceneStorage is the right primitive and is unused. Departs from LensMemory’s stated rule; the departure clause would have to be “a filter restored is a filter the researcher set yesterday, so it is theirs” — which the right-hand frame answers.
  • Content changed overnight (right frame): the search and the filter return over re-analysed content: 0 of 312, a chip naming a tag that no longer exists, an empty centre. Nothing is lost, and it reads as if everything is. Mail clears search for this reason; so did we.
  • Two windows on one study: solved — each window carries its own view. This is the one thing only C buys, and only because the store moves per window; B1’s anchor could ride the same store without the filters.
  • Export HTML: unchanged (no bridge). The browser keeps search in React state only; a reload clears it there too, so the export and the Mac would now disagree about what a reopen does.
  • Rules out: the simple sentence “it opens where you were; what you were looking for is yours to type again”. Once filters restore, every later filter (the parked Quotes filter menu) inherits the question of whether it survives a relaunch.

Recommendation

Option B, in two commits: B2 first (three keys into the R89 contract — an afternoon), then B1 (finer anchors through the shipped LensAnchor table), with one rule carried over from Sessions: clear last_anchor when a run completes. Keep the search/filter carve-out exactly as written.

Why. The owner’s phrase is “scroll depth”, and the honest unit of scroll depth in this product is an element, not a pixel: the quote, the turn, the row. B gives the place at that unit on every lens that has one, through seams that already exist and are already tested on both sides, and it never restores anything that could make yesterday’s content look lost. C’s only unique gain is per-window views; the right-hand frame of C shows what its filter half costs, and the only researcher who meets the two-windows case gets a tie, not an error. A is what ships today and the owner has already said it is not enough.

Sequence. B2 → B1 (Quotes quote id, Sessions moment, Codebook code) → the Signals and Discussion entries once their row ids are confirmed stable across elaboration. Per-window state waits for a case that needs it; if one comes, the anchor moves into @SceneStorage without changing anything the SPA reports.

What the owner still has to settle

  • Per study or per window? Today the place is per study (projects.json). Two windows on one study land together. Accept the tie for now, or move the anchor into @SceneStorage as part of B1 (adds a day; no SPA change)?
  • The transcript’s moment: the turn you were reading, or the playhead if the video was playing? B1 proposes the turn in view; the player’s position is a different thing and already has its own memory in the popout.
  • Do Signals and Discussion get a place? 16 Aug said top. B1 says the row and the question. Cheap to reverse either way; the mockup recommends yes, after the id check.
  • Is “clear the place when a run completes” acceptable on Quotes? It means a re-analysis sends you to the top of Quotes once. The alternative is a quote that looks right and is not.
