Review Gallery, phases 2 and 3: does an “In the app” entry carry a door or a recipe, and where do the web specimens live?

Two owner choices. (i) Phase 2: an entry the gallery cannot fake honestly points at the real app — should it drive the app into the state (a baton: open the window, seed a fixture, land on the surface) or hand the reviewer a recipe to follow? (ii) Phase 3: the web states — do they ship as real React components inside the release bundle, as a page that exists only under serve --dev, or not at all in a release build? Both are judged on the same four consequences: the DEBUG-only gate, what check-release-binary.sh can and cannot see, maintenance per entry, and how a stale entry is caught.

Already built — Phase 2 is half there

  • ReviewGallerySpecimen.navigation(recipe:, open:) exists: every “In the app” entry carries recipe text and an optional door. 22 recipe entries; 3 have a door, all SettingsWindow.shared.show(pane:) (M04, M05, M10).
  • The canvas draws “Seen in the real app, not faked here.”, the recipe, and an Open It button when a door exists (ReviewGalleryCanvas).
  • Fixture seams already exist for a baton: DiagnosticFixture.load(name:) (the Diagnostics ▸ Diagnostic fixtures menu applies one to the selected project), PipelineRunner._debugSetState, ServeManager.debugMarkStartedByRetry, WhisperDownloadModel.debugApply.
  • Two gates: ReviewGalleryRegistryTests builds and draws every state at a real size; tests/test_review_gallery_registry.py resolves every commit hash in git (skips in a shallow clone, so CI never runs that one). “Mark Reviewed” is keyed to the commit list, so a grown list un-reviews.

Already built — Phase 3 is split in two places

  • Hand-written web specimens in a WKWebView inside the Mac gallery (ErrorPatternWebPreview.swift): HTML strings that describe RouteError.tsx and PanelErrorBoundary.tsx, not the components. A markup test checks their buttons. GA-2 (“hand-written versus the real view”) is held for this decision.
  • Two real specimen routes in the SPA, /report/specimen and /report/picker-specimen: always registered, lazy chunks of 7.5 KB and 2.5 KB, nav link only under IS_DEV, a door from the Diagnostics menu (openSpecimen). They ship in every release bundle (present in the signed sidecar’s static/assets).
  • The /report/dev/review page with a fault bar (§3 of the Phase 1 mockup) is not built; nothing in app.py or routes/dev.py mounts it.
  • check-release-binary.sh greps the Mach-O for "Review Gallery", BRISTLENOSE_DEBUG_ and two more literals. Nothing scans the sidecar’s static JS; a web fault injector in a release bundle would pass every gate.

2 · Choice (ii): where the web specimens live, and what “bundle-size budget” means here

The budget turns out not to be bytes. Today’s two real specimen routes add 10 KB to a 3.8 MB asset folder; a review page with a fault bar would add perhaps 40–60 KB. What differs between the options is whether a fault injector (crash this lens, fail this request) exists in a researcher’s binary at all, and whether any gate would notice if it did.

Commentary The Phase 1 mockup’s §3 described C and said “compiled out of release and export builds”; nobody built it, and A grew in its place because A needed no sidecar. A is the cheapest to look at and the most expensive to trust: it is a drawing of the component with the component’s name on it, which is the class of artefact this repo’s mockup register exists to warn about. B ships a review surface in a researcher’s binary for no researcher reason; harmless at 10 KB today, and a precedent that stops being harmless the day someone adds a fault switch to it “just for dev”. C is the only option where the fault bar can exist, because it is the only one where it cannot ship.

3 · The gate, drawn as it would run

# desktop/scripts/check-static-assets.sh — sibling of check-release-binary.sh, for the sidecar's JS
# Called from build-all.sh step 1d (after check-bundle-integrity.py). An assertion is `cmd || die`.
ASSETS="$APP/Contents/Resources/bristlenose-sidecar/_internal/bristlenose/server/static/assets"
hits=$(grep -l -F -e "bn-fault-bar" -e "/report/dev/review" "$ASSETS"/*.js || true)
[ -z "$hits" ] || die "dev-only review page reached the release bundle: $hits"

# tests/test_static_assets_dev_free.py — the same check against frontend/dist after `npm run build`,
# so CI fails before the Mac ever archives. Negative fixture: a build with DEV forced on must trip it.
Commentary Two places, one literal, and a negative fixture, because a gate that has never failed is not known to work (gate policy, root CLAUDE.md). The literal is a class name the fault bar must carry; the test asserts it is present in a dev build and absent in a production one, so the gate cannot pass by the fault bar being renamed.

Recommendation. (i) B: keep the recipe as the required field, make it say what to look at, and add an optional named seed beside the optional door; convert the six fixture-driven entries (M08, M09, M10, B03, the two Whisper rows) first, leave the Finder-drop and chord entries as recipes. (ii) C: build the dev-only review page with the fault bar under import.meta.env.DEV and serve --dev, add the static-asset scan with its negative fixture, and retire ErrorPatternWebPreview once the four states it draws exist there — its Mac entries become .navigation doors that open the dev URL in the report webview and dim when the window’s serve is not a dev serve.
  1. Registry: seed: on the navigation case; everySeedIsAScenario; rewrite six recipes. One Swift commit.
  2. SPA: /report/dev/review route and fault bar behind DEV; the list is review-gallery.json under frontend/src/data/, read by vitest and (later) by the Mac registry through the sidecar. Python: mount nothing new; --dev already serves the SPA from Vite.
  3. Gate: check-static-assets.sh + test_static_assets_dev_free.py with the forced-DEV negative fixture; wire the script into build-all.sh in the same commit, and list it in docs/testing/inventory.md’s source.
  4. Then GA-2 closes: delete ErrorPatternWebPreview.swift and its markup test; the Mac entries point at the real thing or dim.
Open for the owner
  • Is a dev-only web page acceptable as the only home for web states? It means a plain Debug build with the bundled sidecar cannot show them; the reviewer runs the External Server scheme. If the owner wants web states visible in every Debug build, (ii) A stays for those four, with its drift accepted and noted in each entry’s auditNote.
  • Undo Seed. The mockup draws it as a button beside Open It. The existing menu has no undo (a rescan restores the real state on the next poll). Whether the gallery should promise one is a small UX call; without it the footer line “Seeded project-ikea · stopped” is the only acknowledgement.
  • The default audit verdict (GA-4) is still held: an entry lands as .aligned unless the author says otherwise. Not drawn here; it is orthogonal to both choices and could be settled in the same sitting.
