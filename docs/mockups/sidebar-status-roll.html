One line, several jobs: when it holds, when it rolls

The sidebar row has one subtitle line. This page specifies a line that can roll between several things that are true at once, and lets you watch eight real situations play out. Nothing here is wired to the app.

Commentary · the rules

The idea in two tiers

Every state that can appear on the line is flagged holds or rolls. If anything that holds is true, it owns the line, exactly as today. If nothing holds, the line rolls between the states that roll.

  • Owner's rules (30 Oct 2026): the roll, 5 s dwell, pause on hover, shimmer kept, no count; errors displace everything; warnings and info may roll with progress; each state says whether it may be rolled away.
  • My recommendation is unchanged: the fixed order is the cheaper thing to ship and the overlap that prompted this is about 30 s. This page is the roll specified your way, so you can approve or reject it on what it does.
  • What changes from today: a persistent warning no longer hides progress for hours, since both are visible within one dwell. What does not change: errors, gesture acknowledgements and the run ladder.

When someone adds a new state, ask in this order. G1: does it make the project unusable or the report wrong? Holds. G2: did the researcher just press something and wait for an answer, or will it live under one cycle (about 15 s)? Holds. G3: does it carry a control on the row (a ring with cancel, a stop), or is it a run's verb ladder? Holds. Otherwise, if it is long-lived and ambient, it rolls. When unsure, it holds, because that is today's behaviour and cannot be worse than now. In code this is an exhaustive switch with no default, next to glyphKind, so a new variant cannot compile without the decision, and a table test pins every row.

What the repo already says

  • §5 of design-desktop-project-status.md says never two conditions on one line, with one sanctioned exception. This design keeps §5 for every holder and amends it only for rollers, where two conditions share a line in time, not in space.
  • The comment on SidebarSubtitleText.tooltip names "a cycling departure-board line" as the intended direction, with no design doc behind it. The project-icon split-flap (design-project-icons.md) is the nearest house motion vocabulary.
  • Shimmer is .running only today; readiness decision 5 extends it to Signals. About 22 characters fit at 240 pt.

Costs and a native version

  • Size: about 3 to 4 working days, a plausible range of 2.5 to 5, from reading the code, not from building it. The model and clock are easy; keeping an animation alive across outline reloads is the cost.
  • Model: SubtitleVariant.rollPolicy (exhaustive, no default, beside glyphKind), a resolveAll returning holders first then rollers, and a pure clock with an injected time source.
  • Reload churn (the main risk): update() calls a full reloadData(), which rebuilds cells. Keep the clock in the controller keyed by project and refresh a visible rollable row in place (refreshRowsAroundRename is the precedent). A throttle on count ticks is a reasonable add-on, not the fix. Measure how often update() fires while Screens reads before committing.
  • Accessibility tests: a pure "set before and after to announcement" function (a roll gives none); a seam on NSAccessibility.post counting posts over several cycles; the accessibility value byte-identical across a roll; then one by-hand VoiceOver pass.
  • Process: the R114 gate wants explicit owner approval of the mockup before any UX build, the beta policy says almost no new features (the board card says Could, post-launch), and the first merge would want a flag.

The owner decides.
