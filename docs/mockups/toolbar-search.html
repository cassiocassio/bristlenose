Search in the toolbar

Part 1 proposes a search for each lens. Part 2 merges them into one field that finds people, quotes, transcript lines, tags, themes, signals and sessions. It searches the current project, or every project in the current folder, and lists the results in a single view.

What exists today. Search only works in the Quotes lens. The SPA filters in the browser: a case-insensitive substring match from 3 characters, with a 150 ms debounce (utils/filter.ts). It checks the quote text, speaker name, tag names and sentiment. Matches are highlighted with .search-mark. On the Mac the field is a native capsule (QuotesToolbarControls.swift) and ⌘F focuses it. Sessions, Codebook and Signals show a disabled SearchComingSoonButton, and the Project lens shows no search control at all.

No search runs on the server. No route takes a q parameter, and nothing uses FTS5 or embeddings. MCP search_quotes loads every quote and runs the same substring match in Python. Stale claim: design-multi-project.md §3b says FTS5 is "already available in the per-project schema". It is not.

Part 1 — One search per lens

The per-lens searches come in two different shapes. A filter narrows a set: rows that don't match disappear. A find moves a cursor through a document: nothing disappears, and you step from hit to hit. Four lenses are filters and the transcript is a find. That is why ⌘G was withdrawn from the Quotes lens (a filter has no cursor to step), and why it comes back in the transcript.

Every hit is highlighted and one of them is the current hit (outlined). ⌘G and ⇧⌘G step forward and back, and the transcript scrolls to keep the current hit in view. This brings back the Find Next and Find Previous menu items that are commented out at MenuCommands.swift:751-791. It is also the condition the private notes set for restoring them.

When the playhead follows the current hit, a researcher can hear every mention of a word in about a minute. No other lens can do that. It is also the highest-value item on record (menu review, Finding 20). It needs no server work: the transcript is already loaded, so this is a DOM walk plus a cursor.

Part 2 — One field that finds everything

The merge keeps the per-lens field and adds suggestions as you type, in the way Mail does. Pressing ↩ does what it does today and filters the lens you are in. Choosing a suggestion turns the field's contents into a token (a person, a tag, a theme) or opens that item. ⌘↩ opens every result, grouped by type, in a single results view.

This is the pattern Mail and Finder already use. The first row, highlighted, is always the free-text match for the lens you are in, so pressing ↩ keeps today's behaviour exactly. Below it, one suggestion per type (people, tags, sections, signals, transcripts), with a count on every row so the menu also answers “how much is there?”. The menu is capped at about 8 rows, and the last one opens all results.

Keys. This follows Mail. ⌘F searches what you are looking at: Find in a transcript, the filter in any other lens. ⌥⌘F searches the whole project, as Mail's Mailbox Search does. ⌥⌘F currently belongs to Focus Mode, which gives it back and needs a new shortcut; ⌃⌘F is the system's Enter Full Screen, so it is not available. / keeps working on the web.

Choosing a person or a tag turns it into a token, the blue pill that Mail uses. Tokens combine with AND: here, p2 and the tag hidden costs. The token for a tag does the same job as the tag sidebar, and the two stay in sync: the sidebar shows the tag ticked. Backspace removes the last token.

Open decision: should tokens stay applied when you switch lens? My recommendation is yes, within a session. The query describes what you are looking at, and the lens is only how you view it. So p2 in Quotes becomes p2's sessions in Sessions and p2's cells in Signals. The query is still not restored after a relaunch.

The results view is a pseudo-lens. It uses the same window and the same sidebar geometry as the other lenses, and the sidebar's rows become result types, the way Mail's sidebar becomes mailboxes. Each group shows its first few rows, and “Show all in Quotes →” carries the query into the real lens, where it becomes a filter. The scope bar is Finder's (“Search: This Mac | ‘Folder’”).

In folder scope, the rules from design-multi-project.md §3c apply to how results are shown. The project name is the first thing on every row, above the quote and in bold, not in fine print (Finding 5). People appear as speaker codes only, because a participant who consented to one study may not have consented to being linked across studies. Showing names would need an explicit opt-in with a warning. Projects on unmounted volumes are named, not silently skipped (§3b constraints).

Part 3 — What you're deciding, and how it's built

Scope: you asked for all projects, but the design record says the folder is the boundary. design-multi-project.md §3b says: “Global — Not supported.” §3c Finding 1 says the folder is the confidentiality boundary between competing clients, “period”. The threat it names is a freelancer who shares their screen, types “onboarding”, and shows client A's participants to client B. The mockup therefore offers This project and this folder. Adding “All projects” later is one more item on the scope bar, and the provenance rules above already assume results come from more than one project. Your options:

  1. Keep folder scope (recommended). This follows the record and does not reopen it.
  2. Allow all projects, but only as an explicit choice. It is never the default and is not remembered after a relaunch, and people always appear as codes. If you pick this, it overturns §3b and needs a line in that doc.
  3. Allow all projects when there are no folders. A researcher with one client and loose projects has no boundary to protect.

Build order. Each step ships on its own.

  1. Find in the transcript with ⌘G. Client-side only. This is the highest-value step, and it is the condition for restoring the withdrawn menu items.
  2. Turn on the capsule in Sessions, Codebook and Signals. Client-side filters over data that is already loaded. Retire SearchComingSoonButton. The bridge message gains a lens field.
  3. Add a server search endpoint: GET /api/projects/{id}/search?q=&kinds=&limit=, returning a count per type plus the top N hits of each. Back it with an FTS5 table per project covering quote text and edits, transcript segments, people, tag names and definitions, and heading edits. Build the table after stage 12 and update it on edit. Signals are computed at request time, so the endpoint runs load_signals and matches labels and quote ids. MCP search_quotes should call the same core, following the grounding rule of one shared core and never a parallel sibling.
  4. Suggestions menu and results pseudo-lens for one project. The UI above.
  5. Folder scope, once the multi-project work in §7 is in place. The Mac already runs one sidecar per project (ServeFleet), so the natural fan-out is for each project's own sidecar to answer for its own database. That may also avoid the question of whether one sidecar can read another project's folder under the sandbox. Unverified: that last point needs measuring, not assuming.

New pieces this adds (the no-bespoke rule means they are flagged, not just drawn): the suggestions popover, search tokens in the field, the results pseudo-lens and its scope bar, the provenance pill, and the transcript's current-hit outline. Everything else reuses shipped parts: .search-mark, .badge with group tints, the quote card, the sidebar row, and the native capsule.

Native note: the capsule is a SwiftUI TextField, not an NSSearchField. Tokens (NSSearchField's token support, .searchable(tokens:)) are the one feature that argues for revisiting the choice left open in §4.4 of design-desktop-nav-toolbar-rearrangement.md. The popover can be a SwiftUI popover either way.
