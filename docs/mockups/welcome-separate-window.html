Welcome in its own window (Model 2)

Bristlenose for Mac. The Welcome spiral, as shipped, moves out of the main window into one app-wide window of its own. The window opens at the spiral's natural size and can be resized like any other window. The drop card stays behind: the main window's empty states become the drop card alone, centred. Seven panels. At its natural size the spiral is unchanged, apart from losing the drop card. Panel 4 proposes how it reflows when the window is made narrow. The Model 1 alternative, where Welcome stays in the main window, is in welcome-dismiss-options.html.

Artefact: pixels that would ship. No labels inside the frame. Commentary: tradeoffs and reasoning. Not the product. frame bar: state · NEW COPY = owner-written, not a shipped key

1First launch, no projects: Welcome beside the main window, not key

1 · main window key, Welcome open beside itNEW COPY: footer checkbox (see 3)

For: the task and the teaching sit side by side, and the teaching can be ignored at no cost. The research found this is the arrangement that helps without getting in the way. The drop card is live and is the only target in the key window, so a researcher with a folder ready can drop it straight away. The Welcome window is no longer tied to the main window's 700 pt minimum, which exists so a report can be shown. It opens at the spiral's natural size and handles narrow widths on its own terms, by reflowing (panel 4) rather than scaling content down. The scaling machinery (the shelf's 0.29 scale, WelcomeClauseFit) stops being the main way the spiral copes with width.

Against: "beside" needs room. At 1000 + 800 pt it fits only a display wider than about 1850 pt. That includes a 27″ at its default scale, but not a 13″–15″ laptop, where the two windows would overlap or the Welcome window would go off screen. A window that is not key is also easy to miss, and it is the first thing a new user sees of the app. Opening it without making it key is unusual on macOS: launch normally makes the newest window key. AppKit needs an explicit orderFront with no makeKey to do it, and the window falls behind on the next click anywhere.

2Same, Welcome centred over the main window, key for comparison

2 · Welcome key, centred over the main windowthe usual default for a launch window (Xcode, Pixelmator Pro)

For: this is what AppKit does by default, and it is the Xcode and Pixelmator Pro precedent. It cannot be missed, and it works on any screen size.

Against: the teaching stands between the researcher and the task. At 800 pt the Welcome window covers the whole centre of a 1000 pt main window, drop card included. The one action available is hidden behind a lesson the researcher has to close first. Xcode and Pixelmator get away with this because their launch window is the launcher: it has New and Open and a recents list. Bristlenose's launcher is the main window, so the Welcome window has nothing to offer the researcher's next step. It can only be dismissed. Dragging a folder from Finder onto the visible strip of sidebar is not a drop target either.

3The Welcome window, close up

3a · key, box ticked (default)NEW COPY: "Show this window when Bristlenose opens"
3b · not key, box untickedclick either box: it is live

The checkbox sits at bottom-leading with the label Xcode uses ("Show this window when Xcode launches"), and Pixelmator Pro's is in the same place. It closes like any other window: the red traffic light or ⌘W. There is no X inside the content and no Close button. It is an ordinary titled window. It can be resized, minimised and zoomed, because no part of it needs a fixed frame. Xcode's welcome window is fixed-size and has no title bar. That works because Xcode's window is a launcher, and this one is not.

Without the drop card, Study tools gains about 90 pt of height, which goes to the illustration. That is the only change to the spiral. Title is the shipped desktop.chrome.welcomeTitle ("Welcome to Bristlenose"), the same string as the Help menu item, so the menu item and the window it opens have the same name.

Opening size, derived rather than measured: 800 pt content width gives a 760 × 470 pt spiral. The Scientific background cell is then about 284 × 285 pt, enough for the 208 × 152 pt cover fan to draw at scale 1 with its caption and link. That is the reasoning from BookShelfView.coverFan's comments. Nobody has measured it yet. The Degradation Lab would confirm or move the number, and the spiral's φ geometry fixes everything else from that one width. Watch: the spiral's φ geometry means a wider window makes it taller as well. Above the natural size it needs a cap or it outgrows the screen, so the natural size works as a maximum as well as the opening size.

Rotators. Each cell currently advances "per visit", where a visit is an appearance in the main window. In Model 2 a visit has to mean opening the window. With the box unticked, a researcher who never reopens it never sees past the first slot in any cell, so the Tip curriculum stops at slot one.

4Resized narrow: the cells stack

4a · natural size (opening frame)as 3a
4b · dragged narrow (420 pt)proposal · scrolls

Below a breakpoint, the spiral gives up its φ geometry and the cells stack in spiral order: Study tools, Scientific background, Tip, AI, then the privacy card. Each cell keeps its tint and its large/small treatment and takes its natural height. The column scrolls, and the footer checkbox stays pinned at the bottom. Fonts stay at their semantic sizes. Nothing scales down. This is the same rule the spec already sets ("never squish the architecture"), applied by switching the layout instead of shrinking it.

For: the window behaves like a normal Mac window: it is resizable and has a sensible minimum (about 360 pt is enough for one cell's copy), and it never shrinks content below its designed size. A researcher can park it as a narrow strip beside the main window on a laptop, which makes panel 1's "beside" placement work on a 13″ screen as well.

Against: two layouts to build and test instead of one. The baton, which passes the animation along the spiral, now needs an order for the stack too. Reading top to bottom is the obvious one. Where the breakpoint goes, and whether there is an in-between step (two columns), is undecided. Also: this is the first change to the spiral's own layout that the mockup proposes, and only below the natural size.

5Main window empty states, Welcome window closed

5a · no projects yetshipped keys only
5b · projects exist, none selectedshipped keys only

The two states are drawn the same: the existing drop card, unchanged, centred. The lens group stays dimmed because there is no project to apply it to. This is the one point where Model 2 and Model 1's "Welcome off" state (panel 3 of the sibling mockup) produce identical pixels. Model 2 makes this the only no-selection state, so the main window never shows teaching. ⌥⌘N windows open into this state as well, and none of them brings its own copy of Welcome.

For: every no-selection moment, whether it comes from deselecting, deleting the selected project or opening a new window, is now calm and shows one action. The main window's empty state no longer depends on window width.

Against: in 5a the main window alone is very bare: an empty sidebar and one card. If the researcher closed Welcome a moment ago, it is no longer there to say what the app is for. Also: this window is titled "Welcome" today (desktop.welcome.windowTitle, ContentView.swift:427). That made sense while it showed the Welcome content. In Model 2 it no longer does, and it shares a name with the Welcome window. See panel 6.

6a. Xcode keeps "Welcome to Xcode" in its Window menu. In Model 2 Welcome is a window, so the Window menu is a natural home for it. It has no shortcut, for the reason already in MenuCommands.swift: it is opened rarely, so a shortcut would not be remembered. 6b. The Help item stays where it is, and what it does changes. Today it clears the selection to show the Welcome pane. In Model 2 it opens or focuses the Welcome window and leaves the main window's selection alone, so it stops being destructive to what the researcher was looking at. The research's "easy to find in a help area" argues for keeping Help. Whether Window should also have it, or whether one menu is enough, is open.

The window list in 6a shows the naming collision: "✓ Welcome" is the main window with no project selected, under its shipped title, and "Welcome to Bristlenose" is the new window. Nobody can tell them apart from the menu. A shipped alternative for the main window's empty title already exists: desktop.chrome.noProjectSelected ("No Project Selected"). Using it is a one-line change, but it is a decision for the owner, so it is not drawn here.

A third option, not drawn, is to open the window only at launch and never into a full-screen Space. That relies on the "launch only" answer to the first open question below.

?Open questions (surfaced, not answered)

1. When does it appear? Only at launch, if the box is ticked? Or also when the main window has no selection, for example after deleting the last project? Launch-only follows Xcode and keeps every deselect calm. Showing it on deselect brings back Model 1's behaviour in a second window.

2. Reopen at the last frame, or always at the natural size? The Mac convention is to restore a window's last frame, and a researcher who parked it as a narrow strip (panel 4b) would expect it back there. Always opening at the natural size guarantees the designed first impression every time, at the cost of discarding the user's choice.

3. Beside or over, and which window is key? Panel 1 helps but needs a wide display. Panel 2 works everywhere but covers the drop card. Possible middle ground: beside the main window when there is room, otherwise offset so the drop card stays visible. That gives two behaviours to explain and test.

4. Sheets on the main window. If the AI-consent sheet, or any first-run sheet, is attached to the main window at launch, the Welcome window either competes with it for key or waits until it is dismissed. A Welcome window that is key and sitting over a window with a modal sheet is the worst case. Order of operations: sheet first, Welcome after?

5. What counts as a "visit" for the rotators, now that opening the window is the only way to see one (panel 3 commentary). Should each cell advance per opening, per launch, or on a timer while the window is open?

6. The main window's empty-state title ("Welcome" vs "No Project Selected"), and whether the Window menu gets the item as well as Help (panel 6).

7. Drop on the Welcome window? With no drop card it has no drop target. A folder dropped on it does nothing. Should the whole window accept the drop and pass it to the main window, or should it refuse visibly?
