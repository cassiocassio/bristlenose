Performance field notebook

What we measured, changed, declined and learned making Bristlenose open faster. Two days of work (4 to 5 November 2026), written so it can be distilled later into a long-form piece on how to do performance work without fooling yourself.

Source of truth for every number: docs/design-perf-ledger.md and docs/design-standby-sidecar.md. App timings are from a Debug build of the macOS app, sandboxed, on one Apple Silicon Mac; a Release re-run at the end showed no difference to the web-side numbers (see "The biggest caveat, and the check we then ran").

Summary

−0.6 soff every study opened from the Welcome screen: standby sidecar, measured in the app (1,824 → 1,238 ms click to report)
−30%sidecar start from one lazy import (inflect): 3.19 → 2.24 s cold, in the app
−30%spawn to first health check from loading the MCP endpoint on first use: 1,454 → 1,005 ms
75%off the first click on Sessions: 361 → 86 ms (preload the chunk when idle)

The shape of the result: the big wins were not tuning. They were finding work that did not depend on the thing the researcher had just asked for (importing a plural library, building an agent endpoint nobody had called, starting a Python process that could have been started earlier) and moving it out of the click. What is left is smaller, harder, and mostly in two places we have deliberately not touched yet: the server's bind step and the web view's own startup.

Two things also went wrong in instructive ways. A fix to return the window to its lens after an analysis passed its unit tests and did nothing in the real app (a run replaces the page and records the wrong lens). And a "regression" in the standby turned out to be a changed macOS setting under the test harness. Both are in What we learned.

Method

The loop, every time: instrument, change one thing, re-measure, stop at a number you wrote down before you started. The rest is discipline about not fooling ourselves.

Rules we held to

  1. Label every number: measured a repeatable run; estimate reasoned from a measured part, with the reasoning shown; unmeasured no number, and none guessed.
  2. Interleave A/B. Alternate the arms (off, on, on, off…) so drift in machine load hits both. Report the spread, not just the median.
  3. Same binary, one switch. The standby was toggled by an environment variable on one app build, never by comparing two builds.
  4. Measure in the real thing. A dev-server number is a hypothesis. The sandboxed app's own signposts decide.
  5. Write the stop number first. "Good enough" is a figure, so a pass can end by succeeding or by declining.
  6. Declined is a result. A change that does not pay is recorded with its number, so nobody re-proposes it.

Instruments we built

  • Signposts in the Mac app (os_signpost): launch, project select, serve ready, and one named step per stage between the click and the report being ready.
  • Server stamps: BRISTLENOSE_STARTUP_TRACE and Server-Timing on routes.
  • Harness scripts: a launcher that drives the real app through Accessibility, an interleaved A/B runner, a bare WKWebView loader, a Chromium timeline script.
  • A spend guard: the harness aborts if the study's LLM call log grows, because some trial launches start a paid job.
  • Isolated Swift verification: build in a throwaway worktree with only your own files, so a concurrent session's half-saved edit cannot flip your result.
  • Mutation proof: revert the fix and see that exactly the new test fails. A test you have not seen fail is a guess.

A restored launch

Why the standby cannot help a relaunch. macOS restores windows by default, so most relaunches skip the Welcome screen. The standby earns its 0.6 s on the first study opened from Welcome and on every later open in the session (a replacement spare is started after each claim).

The thing that looked like a regression was this: the harness had been written while the system switch for restoring windows was off, so every launch landed on Welcome and then clicked. With the switch back at its factory default, every launch restored the study at once and no spare existed in time. The build was fine. The test had changed under us.

What we learned

About the product

  • Find work that does not depend on the click. 47% of a cold start was Python importing things unrelated to which study was opened. The three largest wins were all of this kind.
  • The platform default decides who benefits. Window restoration is on by default, so the thing we optimised (open from Welcome) is the minority path on a relaunch and the common path within a session.
  • A restored window is a different product moment, and it hid a real bug: on macOS 27 the restored scene value arrives after the view appears, so every relaunch used to come back empty.
  • Bind is the floor we have not touched. About 440 ms of the 1.2 s after a click is the server building the study's app. Lowering it means a per-study warm worker, which is an architecture decision, not a patch.

About doing the work

  • The first measurement is usually of the wrong scenario. Three times in two days a harness measured something other than what we thought: a changed system setting, a pgrep pattern that matched nothing, and a clock that started a second early. Check what the run actually did before reading its numbers.
  • Unit tests do not see the product. The lens-after-analysis fix held the lens the window was on at reload time. In the real app that lens was always Project, because a run replaces the report with its own page. Only running an analysis, with a harness reading the window, showed it. The corrected version captures the lens when the run starts, and was checked live on two lenses.
  • Reviews find a different class of bug. An independent review found the standby process was freed immediately after being claimed (nothing owned it). Every unit test had passed.
  • An honest "not measured" beats a confident guess. Several rows in the ledger say so, and two of our own earlier claims were corrected after a review: a lazy-loading change that still loaded the SDK on its first health call, and a standby "cost" that did not reproduce.
  • Verification costs something. Trial launches spent real LLM calls (five early, then about seventy on a scratch study for the lens check). The spend guard exists because of the first five.
  • Shared working trees bite. One commit swept in another session's uncommitted edit. Stage by explicit path, read git diff for hunks you did not write, and never rewrite another session's work to tidy up.

The biggest caveat, and the check we then ran

Every app number above is from a Debug build, and the in-app web side runs about 230 ms slower than bare WebKit. The obvious suspect was Debug (unoptimised SwiftUI drives the web view). We re-ran the whole click-to-ready harness on a Release build, built with the same signing and sandbox entitlements as Debug so that optimisation was the only change.

Result: it does not close the gap. View made to ready was 596 ms (standby off) and 567 ms (on), against 604 ms in Debug. The mount phase may be about 40 ms faster (104 against 148 ms), which is inside the spread. Click to report ready was 1,747 and 1,757 ms. Debug is not the cause. What is left is the sandboxed network path and contention, and neither is something we would change cheaply. (Neither arm claimed a standby: the study was restored at launch, as the earlier section explains.)

The Release app here is a measurement build only: Debug entitlements, no hardened runtime. It says nothing about an App Store build's signing cost.

Value against cost

Sequencing

  1. Now (measure only): the Release-build re-run (#1) is done and ruled Debug out. Idle energy (#2) is next: it changes nothing in the product and can kill or confirm other items.
  2. Next (small, contained): web view start-up re-test (#3). The in-app gap (#4) is parked: Release did not close it, and what is left is the sandbox. Memoisation and selectors (#5) when the display-preferences work has landed.
  3. After launch: lens revisit from last-known data together with per-lens scroll position (#6), since they share the same state model; then the regression gate (#8) once the numbers have stopped moving.
  4. As a designed project: the warm worker (#7). It deserves its own design note first, and its decision rule is the standby's law: it must beat bind (440 ms) by more than it costs in memory and lifecycle complexity.

Notes for the essay

Angles that came out of the work and could carry a piece on their own:

  • "Find the work that does not depend on the click." The three biggest wins, with the 47% figure for how much of a cold start was independent of the study.
  • "The test changed under us." How a macOS default turned a working optimisation into an apparent regression, and what a harness should assert before it measures.
  • "It passed its tests and did nothing." The lens fix: why a live run found what unit tests could not, and why a review found what the live run could not (the freed standby).
  • "The stop number." Writing the good-enough figure first, and treating declined changes as results with a recorded number.
  • "Label your numbers." Measured, estimate, unmeasured, and the discipline of saying which.
  • "Everything here is a Debug number." The honest caveat, and then the check that showed it did not matter (Release changed nothing). A caveat is only worth stating if you then go and test it.
