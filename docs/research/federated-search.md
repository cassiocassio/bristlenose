# Grow federated search from one shared core

Bristlenose should build **one search core in its own Python and SQLite stack**. Every surface (the toolbar field, each lens, the CLI, the MCP tool and the offline export) should query it through a small contract that returns plain data. The first two sources should be quotes and people, because they are the least alike. The remaining lenses then join one per release. Do not build a separate v1 search in each lens and merge them later, and do not build infrastructure with nothing in it. The engine is SQLite FTS5 with two indexes, one for words and one for substrings and CJK text. On top of it sit a folding layer, an in-memory fuzzy matcher for short names, and a "did you mean" that reads the index's own vocabulary. It stays well inside a keystroke budget at 100,000 transcript segments, and it runs identically on the Mac, Linux and in a browser. Core Spotlight is the wrong engine for this content. It has no typo tolerance, no snippet API and ranking you cannot control. Worse, anything indexed appears in the system ⌘Space window, which is how one client's participant surfaces while the researcher is screen-sharing with another. The per-lens searchers should run concurrently in code. Inside one project the UI should still paint the results once, when they are complete, because an index removes the latency spread that streaming exists to hide. Streaming earns its complexity only for the folder-wide fan-out. The user's working assumption holds as a recall policy: offer every data type a chance to answer. As a presentation policy it fails. It needs query understanding that *proposes* tokens rather than silently reinterpreting what was typed, per-type caps, and guardrails where scope or participant identity is at stake.

## Today's Quotes filter is a sound seed with five fixable flaws

The baseline is `matchesSearch` in `frontend/src/utils/filter.ts`. It lowercases the whole query and runs `includes()` against four fields: the quote text (edited if edited), the speaker's display name, the tag names and the sentiment value. It needs 3 or more characters and is debounced by 150 ms. That is a respectable v1, since it covers the fields a researcher actually remembers. Five weaknesses would each show up in daily use, and all five are cheap to fix before any server work.

First, the whole query is a single substring, so "delivery price" misses "price of delivery". Apple's own apps match **each word independently as a prefix and AND the words together**. Photos does this: "bury st" matched a place through "bury" and several people through "st" (observed in the user's Photos screenshot; no Apple document states the rule). Second, there is no diacritic folding, so "cafe" never finds "Café". Third, the 3-character floor is wrong for Chinese and Japanese, where two-character words such as 東京 or 設計 are common. Fourth, the sentiment comparison runs against the stored value. A researcher in a translated UI who types the sentiment label she sees on the card gets nothing unless the stored value happens to be spelled the same way. Fifth, the Quotes lens no longer shows a match count; the mockup notes that the vanilla report had one and the SPA dropped it.

The same substring logic lives a second time on the server. MCP `search_quotes` (`bristlenose/server/mcp_server.py:523`) loads every visible quote and filters in Python. The project already has a rule for this: the chat lens and the MCP endpoint ground in one shared core, "never a parallel sibling". Two ad-hoc substring matchers already break that rule for search. One design-record claim is also stale. `docs/design-multi-project.md` §3b says quote search "uses SQLite FTS5 (already available in the per-project schema)". There is no FTS5 table anywhere in `bristlenose/`, and no server route takes a query parameter.

The baseline also sets a constraint that the rest of this report keeps: **the offline HTML export has no server**. It is a single-file React bundle with embedded JSON, opened from `file://`. Whatever the server learns to do, some client-side matcher must survive for that artefact. That argues for keeping a TypeScript matcher, bound to the Python one by a shared contract. The repo already runs this pattern for formats, in `tests/fixtures/shared-format-contract.json`, which is asserted from both pytest and vitest.

## Researchers want a finder that turns words into evidence

Two families of prior art pull in different directions, and Bristlenose sits between them.

General desktop tools have converged on **one ranked list with type filters beside it**. Spotlight in macOS 26 dropped its per-type sections: all result types are "now listed together and ranked intelligently based on relevance" ([AppleInsider](https://appleinsider.com/inside/macos-tahoe)). Browse filters on ⌘1–⌘4 bring the type back when type is the intent ([Six Colors](https://sixcolors.com/post/2025/09/macos-26-tahoe-review-power-under-glass/)). No vendor publishes a cross-type ranking formula. In practice ranking is **match quality on names first, frecency second**. Raycast ranks exact alias, then alias prefix, then fuzzy title, then subtitle, and uses frecency only below all of those ([Raycast Manual](https://manual.raycast.com/search-bar)). Joplin places any title match above every body-only match "regardless of weight" ([Joplin spec](https://joplinapp.org/help/dev/spec/search_sorting)). Things shows the cheapest tier first: it searches names only, "so suggestions can be shown as soon as you start typing", and a **"Continue Search"** row widens to notes and the Logbook ([Things Support](https://culturedcode.com/things/support/articles/2803584/)). Slack's switcher reaches a 7 ms median by prefetching when the switcher opens, not on each keystroke ([Slack Engineering](https://slack.engineering/a-faster-smarter-quick-switcher/)).

Qualitative-research tools split into two traditions. **CAQDAS desktop tools treat search as an analytic instrument.** MAXQDA's results table has a Context column; clicking a hit "opens the document and positions exactly where the reference is located", and the hits can be **autocoded** in bulk ([MAXQDA manual](https://www.maxqda.com/help-mx22/lexical-search/search-results)). NVivo's Find slider runs from exact matching to stemmed forms, synonyms, specialisations and generalisations, and results can be saved as codes ([NVivo 15 help](https://help-nv.qsrinternational.com/15/win/Content/queries/text-search-query.htm)). ATLAS.ti shows each hit alongside **the codes it already carries**, and a bulk action codes all results at once ([ATLAS.ti manual](https://manuals.atlasti.com/Win/en/manual/SearchAndCode/SearchAndCodeTextSearch.html)). **Repository SaaS tools treat search as navigation plus AI retrieval.** Their answers carry cited verbatim quotes that "jump directly to that moment in the recording" ([Great Question](https://greatquestion.co/support/repository/ask-ai)). The most instructive recent move is Dovetail's February 2026 change. Its default search now **excludes contacts, tags, highlights and themes** "to keep results focused on core content" ([Dovetail changelog](https://dovetail.com/changelog/faster-simpler-search-in-dovetail)). The lesson is that high-volume evidence types swamp navigation results. For Bristlenose the volume problem is transcript segments, and the mockup's answer is correct: transcripts appear in the menu as a count row ("41 lines in 6 sessions"), not as 41 rows.

The researcher complaints on record are thin but consistent. One Dovetail reviewer wanted to "search keywords within a specific project. Right now, I can only search site-wide", and others called results "unstructured" with "limited options for quickly filtering down" ([AWS Marketplace reviews](https://aws.amazon.com/marketplace/reviews/reviews-list/prodview-ckaqbf4iqi5mi?page=1)). Delve users, by contrast, praise the ability to "instantly find the perfect quote" ([Capterra](https://www.capterra.com/p/196428/Delve/)). The job to optimise is therefore narrow: find the exact quote fast, see it in context, jump to the moment, and act on the hits. Nothing in this prior art suggests that researchers want wider or cleverer search. They want faster narrowing.

### The macOS conventions to copy, and the ones only observed

The HIG's search guidance is short and sets principles rather than mechanics. Start the search as the person types, show recents before typing, "default to a broader scope and let people refine it", and pair tokens with suggestions because "people may not know which tokens are available" ([HIG: Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields)). Search history must be clearable ([HIG: Searching](https://developer.apple.com/design/human-interface-guidelines/searching)). Most of the micro-interactions the user named appear in Apple's apps but in no Apple document, so they are specifications to imitate and verify by hand, not rules.

| Convention | Evidence | Bristlenose adaptation |
|---|---|---|
| Leading type glyph, label, trailing count on each suggestion row | Observed in Photos; `NSSuggestionItem` has an image slot but **no count slot** ([Apple docs](https://developer.apple.com/documentation/appkit/nssuggestionitem)) | Glyphs for person, quote, transcript line, tag, section/theme, signal, session; count right-aligned in secondary colour |
| Typed text in primary colour, completion in secondary | Observed in Photos ("**Bury St**" dark, "Edmunds" grey) | Apply to entity names only; body-text hits use the existing `.search-mark` highlight instead |
| Each word matched as its own prefix, words ANDed | Observed in Photos; Photos support confirms space-separated multi-criteria search ([Apple Support](https://support.apple.com/guide/photos/search-for-photos-and-videos-pht64de33e5a/mac)) | Rewrite the query as quoted tokens with `*` on the last; same rule in TS and Python |
| Counts capped, e.g. "280+", while 927 stays exact | Observed; the rule is undocumented | Use "N+" only when a count stopped at a limit or the index is still building. Never show a count that later drops |
| "Indexing…" footer row, not selectable | Observed in Photos | Shown while a project's index builds on first serve; suggestions still appear from the tiers that are ready |
| Picks become tokens; a chevron menu changes the token's meaning | Mail: "If a search filter contains a down arrow, you can click it to change the filter" ([Apple Support](https://support.apple.com/en-gb/guide/mail/mlhlp1003/mac)) | Person token: *said by p3* / *mentions p3*. Tag token: *tagged* / *text contains*. Any token: *exclude* |
| Tokens ANDed with free text; field scrolls as tokens are added | Mail support page ([Apple Support](https://support.apple.com/en-gb/guide/mail/mlhlp1003/mac)) | Identical |
| Backspace selects a token, second Backspace deletes it | Observed/unverified; matches `NSTokenField` | Copy it, because it protects a token that took effort to build |
| Grouped sections with "Top Hits" first | Mail: suggestions "organized into categories", "Top Hits" first ([Apple Support](https://support.apple.com/guide/mail/search-for-emails-mlhlp1003/mac)) | Mail-style sections suit a query that resolves to several kinds at once, which is Bristlenose's normal case |
| ↑↓ rows, ⌘↑⌘↓ sections, Return / ⌘Return, Esc clears then closes | Raycast, documented ([Raycast Manual](https://manual.raycast.com/search-bar)) | ↩ keeps today's behaviour (filter the current lens); ⌘↩ opens the full results view |
| Scope bar under the toolbar, current scope named | Finder and DEVONthink ([DEVONtechnologies](https://www.devontechnologies.com/blog/20231107-narrow-search-devonthink)); SwiftUI puts scopes "in a scope bar beneath the toolbar on macOS" ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10052/)) | "Search: This project · ‹Folder›" at the top of the results view only |
| Async suggestions appended after immediate ones | WWDC24: "place those after the immediate suggestions you already provided" ([WWDC24 10124](https://developer.apple.com/videos/play/wwdc2024/10124/)) | Short-entity matches first (instant), text-index rows after |

One platform fact changes the native-versus-web question. The system-standard suggestions menu (`NSTextField.suggestionsDelegate`, with sections, images, secondary titles, highlight-time completion and `.intermediate`/`.final` async phases) arrived in **macOS 15** ([WWDC24 10124](https://developer.apple.com/videos/play/wwdc2024/10124/); [NSTextSuggestionsDelegate](https://developer.apple.com/documentation/appkit/nstextsuggestionsdelegate)). That is exactly Bristlenose's deployment floor, so a native menu costs no availability gating. It would bring the system's keyboard handling and VoiceOver behaviour for free. The price is a second renderer, because the browser SPA still needs a web menu. That is affordable only if each suggestion row is plain data. The mockup notes that the toolbar capsule is a SwiftUI `TextField`, not an `NSSearchField`, and that tokens are the one feature arguing for revisiting that choice. The suggestions API is a second argument for revisiting it.

Keyboard assignments follow Apple's pattern: ⌘F finds within what you are looking at, and ⌥⌘F searches the collection. Mail's Mailbox Search is ⌥⌘F, and Notes uses ⌥⌘F for all notes (unverified on macOS 27 menus). In Bristlenose ⌥⌘F currently belongs to Focus Mode, but the maintainer has said search takes it back when it needs it. So **⌘F searches the current lens (Find in a transcript, the filter elsewhere), and ⌥⌘F focuses the project-wide search** with the results view as its scope. Focus Mode then needs a new shortcut, which is a separate decision. ⇧⌘F becomes free, but check it against Apple's own apps before assigning it; ⌃⌘F is the system's Enter Full Screen and is not available.

## Every query should reach every source, but through tokens and tiers

The user's assumption is that anything a researcher can type should be mapped to every data type that could answer it meaningfully. It is right about *recall* and wrong about *presentation*. Every source should get the chance to answer, because the researcher usually does not know which lens holds the thing she half-remembers; that is what makes a toolbar search worth having. Answering with everything at once, or quietly turning "s3" into a session filter, breaks two things. It breaks the researcher's model of what she typed, and it breaks the NN/g rule that every suggestion must lead to real results. NN/g also found that users picked suggested queries in only **23%** of cases where they were offered ([NN/g: Site Search Suggestions](https://www.nngroup.com/articles/site-search-suggestions/)). Free text therefore has to remain the default action, with interpretations *offered* as suggestion rows that become tokens only when chosen.

The practical model is **intent recognisers that propose, sources that answer, and tiers that cap**. Each recogniser inspects the raw string and offers zero or more interpretations. Each source (quotes, transcript segments, people, sessions, tags and codebook entries, sections and themes, signals) searches the free text independently. The menu shows the free-text row first, then one row per recognised interpretation, then one count row per source with hits.

| Intent | Typed example | How it is recognised | Sources it should reach | Guardrail |
|---|---|---|---|---|
| Remembered phrase | *more than the shelf* | Default for any text | Quotes (original and edited), transcript segments, per-session mention counts | Search the text the report displays (post-redaction), never a pre-redaction source |
| Topic word | *delivery* | Default | Quotes, segments, tag names **and definitions**, section/theme labels, signal cards | Transcripts as a count row, not a list; moderator turns grouped apart |
| Participant code | *p3*, *m1* | Pattern `[pm]\d+` | Person, their quotes, their sessions, their turns, signals they contribute to | Offer as a token, never auto-apply; the only identity allowed cross-project |
| Participant name | *Tom* | Fuzzy match over the project's people | The same as the code, resolved to the code | In-project only. In folder scope, codes only, per §3c Finding 5 |
| Session | *s3*, *interview_03.mp4* | Pattern `s\d+`, filename match | Session row, transcript, its quotes | None |
| Timecode | *12:04*, *1:12:45* | The shared `timecode` format (minutes padded, hours never) | The segment at that time in the current session; with a session token, that session; otherwise one row per session | Ambiguous without a session, so suggest, don't jump |
| Date | *12 Sep*, *Tuesday* | Locale-aware date parse | Sessions recorded then | Parse in the UI locale; keep relative dates simple |
| Tag or code | *hidden costs* | Fuzzy match over tag names | Tag token (tagged quotes), codebook entry, definition snippets | Token menu separates *tagged* from *text contains* |
| Section or theme | *checkout* | Name match | The section/theme, its quotes, its signal cards | None |
| Sentiment word | *frustration*, *frustración* | Lookup against **UI-language labels** mapped to canonical values | Sentiment token; signal cards | Match the label the researcher sees, not the stored enum |
| Curation state | *starred*, *hidden*, *edited* | Keyword list, as Mail's "flag" suggests "Message is flagged" ([Apple Support](https://support.apple.com/en-gb/guide/mail/mlhlp1003/mac)) | Curation filters | Hidden quotes are excluded by default and reachable only via a token |
| Signal combination | *frustration checkout* | Two recognised tokens together | The section × sentiment card | None |
| Question | *why did people abandon checkout?* | Question shape (wh-word or "?") | An **"Ask the report…"** row that hands off to the chat lens | Explicit only. It is an outbound LLM call with a cost |
| Framework term | *affordance* | Match over installed and library codebooks | Codebook entries, including uninstalled library tags | Label library hits as "not in this project" |

Three rows carry most of the design risk. The **question** row follows Dovetail, where question-shaped queries trigger an AI summary inside the same box ([Dovetail help](https://docs.dovetail.com/help/search)). Bristlenose should offer that path, not take it. The chat lens is a cloud LLM call, which is normal and fine for this product but still spends money and sends text outbound. Nobody should trigger one by pressing Return on a keyword. The **sentiment** row exposes a locale gap. Bristlenose ships 22 UI locales, so every recogniser that matches enum-like vocabulary (sentiment, curation states, lens names) must match the translated label in the current UI language and map it back to the canonical value. The **participant name** row is where the assumption meets the consent model. Inside a project, typing "Tom" to reach p2 is plainly useful, and the baseline already does it. Across projects, §3c Finding 5 of the design record rules it out. A participant who consented to one study may not have consented to being linked to another, so cross-project results use speaker codes and full-name search needs an explicit opt-in with a warning.

Several guardrails sit outside the table. **Scope must never widen silently.** HIG and NN/g both say default to the broad scope ([NN/g: Scoped Search](https://www.nngroup.com/articles/scoped-search/)), while Dovetail's users ask for the narrow one. These reconcile once "broad" is read as *every lens of this project*, with the folder as an explicit escalation row in the Things "Continue Search" style. **The moderator problem is specific to interviews.** A moderator who asks "so tell me about delivery" plants the topic word in the question turn. Moderator segments should form their own group, or rank below participant speech, so the evidence is what surfaces first. **Very short queries** (one Latin character, a bare "p") should drive the entity recognisers but not full-text search. The exception is a one- or two-character CJK run, which is a complete word. **The query itself is sensitive.** Uvicorn's access log is enabled under `-v` (`bristlenose/cli.py:1695`), so a `GET /search?q=Sarah` would write a participant's name into the terminal and possibly the log. Send the query in a POST body or scrub it from logging.

There is also a finding about the design record itself. §3c Finding 6.3 says cross-project views of *linked-person* data are "only accessible from the home screen / project library, never from within an open project's UI". The mockup's folder scope runs from inside a project's toolbar. Folder-scoped quote results shown as codes are not linked-person data, so the two can coexist. The line should still be drawn explicitly in the doc before the folder scope ships, because a later "People in this folder" group would cross it.

## SQLite FTS5 plus Python beats Spotlight on every axis that matters

FTS5 already offers everything a search that is "fuzzy enough" needs. It has a `unicode61` word tokenizer with `remove_diacritics 2` ("correctly removes diacritics from all Latin characters"), a `trigram` tokenizer for substring matching, per-column weighted `bm25()`, and `snippet()`/`highlight()` for keyword-in-context display. External-content tables are kept in sync by AFTER INSERT/UPDATE/DELETE triggers ([SQLite FTS5](https://sqlite.org/fts5.html)). Triggers matter here because researchers edit quotes and headings constantly. With triggers, an edit is searchable in the same transaction, with no background re-index to fall behind. That is the house pattern across the SQLite ecosystem, and sqlite-utils generates exactly those triggers.

The recommended shape uses **two indexes per project plus two Python layers**. A `unicode61 remove_diacritics 2` table is the *word* index; it handles ranking, snippets and prefix search, and it supplies the vocabulary for "did you mean". A `trigram remove_diacritics 1` table is the *substring and CJK* index. Both cover only the long text: quote text and edits, transcript segments, tag definitions, and heading edits. The short entities (people, tags, sections, themes, sessions, a few hundred rows) never touch FTS. They are held in memory per project and scored with `rapidfuzz`, which handles typos and transpositions without an index. Typo tolerance for body text belongs on the query side. When a MATCH returns few or no hits, `fts5vocab` lists the corpus's own terms and `rapidfuzz` proposes the nearest. That works in every language the corpus contains, and it needs no loadable extension. This matters because `spellfix1` is not compiled into any measured Python build, and `sqlean.py`, which bundled a fuzzy extension, was archived in February 2026 ([sqlean.py](https://github.com/nalgeon/sqlean.py)).

Measured on the maintainer's Mac on 27 Sep 2026, a synthetic corpus of **100,000 segments (about 7M words)** gave these results. The word index built in about 3.5 s, occupied about 29 MB, and answered in about 1 ms for an exact term and 2.6 ms for a prefix. The trigram index took about 27 s to build and occupied about **202 MB, roughly 3.4× the text**. It answered in 4–6 ms. Adding `prefix='2 3'` quadrupled build time for no meaningful speed-up, so skip prefix indexes. Every number is comfortably interactive. The trigram index's size is the figure to watch, and it argues for indexing only searchable text columns and for testing `detail=column`. The first build on a pre-existing project is the one visible cost. That is the moment for Photos' "Indexing…" footer: suggestions from the ready tiers keep flowing, and a `LIKE` fallback covers the gap.

CJK and some non-Latin scripts need deliberate handling, and the measurements are blunt. `unicode61` **does not segment CJK at all**: a sentence of Japanese becomes one token, so 地下鉄 finds nothing. Trigram fixes queries of three or more CJK characters, but two-character words (東京, 設計) match in neither index. A plain `instr()` scan over 100,000 rows of CJK text took about 15 ms, so the query router should send 1–2-character CJK runs to a scan. If that ever proves too slow, the next step is a bigram shadow column built in pure Python. Folding also has gaps that the tokenizers do not cover. Russian `ё`→`е` is not folded by `unicode61`, the Turkish dotted `İ` fails under plain trigram, and German `ü`↔`ue` transliteration is met by no tokenizer. Apply `casefold()` plus a small replacement table in Python on both the indexing side and the query side. Stemming in FTS5 is English-only (`porter`). Because Bristlenose transcribes in the language spoken and serves 22 UI locales, prefix matching should be the baseline. Snowball pre-stemming into a shadow column is an optional later step, not a foundation.

The deployment floor is set by Linux, not the Mac. Every measured Mac interpreter, including the bundled sidecar's `libsqlite3`, is at SQLite 3.53. The snap on core24 links Ubuntu 24.04's **3.45.1**, and Ubuntu 22.04 ships 3.37.2 ([packages.ubuntu.com](https://packages.ubuntu.com/noble/sqlite3)). Trigram `remove_diacritics` needs 3.45, and FTS5's `locale=1` plus the v2 tokenizer API need 3.47 ([SQLite changes](https://sqlite.org/changes.html)). Design against 3.45, probe features at startup rather than sniffing version numbers, and let an older pip install fall back to correct, slower `LIKE` search instead of an error. Alternatives were considered and set aside. tantivy-py has real fuzzy term queries and Snowball stemmers, but it is a second store outside SQLite transactions, with a single-writer lock and 23 MB of native code to sign. Whoosh last released in 2016. Semantic search is feasible later in Bristlenose's own stack: a static multilingual model such as potion-multilingual-128M covers 101 languages without a transformer runtime ([Hugging Face](https://huggingface.co/minishlab/potion-multilingual-128M)), fused with keyword results by reciprocal rank ([Simon Willison](https://simonwillison.net/2024/Oct/4/hybrid-full-text-search-and-vector-search-with-sqlite/)). It is not needed now. Researchers search for words they remember, and "things about X" is the chat lens's job.

### Core Spotlight fails the product on matching, parity and privacy

Core Spotlight looks attractive because it is on-device and native. It fails Bristlenose three ways. On **matching**, its predicate language offers case, diacritic, word and wildcard modifiers but **no edit distance** ([Apple docs](https://developer.apple.com/documentation/corespotlight/searching-for-information-in-your-app)). Its semantic path, `CSUserQuery`, has been reported through 2025–26 as returning results identical to having it disabled, with embedding timeouts in the logs ([Apple Developer Forums 793867](https://developer.apple.com/forums/thread/793867)). Apple's own documentation suggests disabling semantic search "when looking for a proper name" ([disableSemanticSearch](https://developer.apple.com/documentation/corespotlight/csuserquerycontext/disablesemanticsearch)), and proper names (participants, clients, products) are what researchers type most. No API returns match offsets or snippets, so Bristlenose would need its own matcher anyway to highlight a hit. On **parity**, none of it exists on Linux or in a browser. The CLI and SPA still need the SQLite engine, so a native engine would give the Mac different results from the CLI for the same query on the same project. NetNewsWire, a native Mac app, still uses SQLite full-text search for in-app search ([NetNewsWire source](https://github.com/Ranchero-Software/NetNewsWire/blob/main/Modules/ArticlesDatabase/Sources/ArticlesDatabase/ArticlesDatabase.swift)).

On **privacy** the verdict is decisive. Content indexed through Core Spotlight appears in the system Spotlight window: Eclectic Light searched a unique word and "at the top of the list of hits is my test note" ([Eclectic Light, Jul 2026](https://eclecticlight.co/2026/07/08/core-spotlight-in-action-notes-and-contacts/)). Picture a freelancer presenting to Client B who presses ⌘Space to find a slide and sees Client A's participant quote. That is exactly the threat §3c of the design record names. Indexed entities are, in Apple's words, "discoverable by Apple Intelligence" ([IndexedEntity](https://developer.apple.com/documentation/appintents/indexedentity)). The per-user store sits outside the project folder the researcher owns and deletes, and forensic tools parse it ([Swift Forensics](http://www.swiftforensics.com/2018/10/the-user-spotlight-database.html)). A GDPR erasure would then have to reach a copy Bristlenose cannot inspect. Apple itself keeps Contacts search out of Core Spotlight ([Eclectic Light](https://eclecticlight.co/2026/07/08/core-spotlight-in-action-notes-and-contacts/)). Only two native hybrids are defensible. The first is App Intents search routed *into Bristlenose's own engine* (`ShowInAppSearchResultsIntent`, macOS 14.2+ ([Apple docs](https://developer.apple.com/documentation/appintents/showinappsearchresultsintent)); `.system.searchInApp` in macOS 27 ([WWDC26 343](https://developer.apple.com/videos/play/wwdc2026/343/))), which puts nothing into any system index. The second is an opt-in donation of project names only, off by default, because a project name like "Acme checkout study" can itself identify a client.

## Run searchers in parallel, but paint once inside a project

The user's third question has two separable answers, and conflating them is the main risk. As a **code architecture**, one searcher per lens is right. JetBrains' Search Everywhere is built from contributors. Each has a static sort weight that fixes group order regardless of arrival time, an element limit with a "has more" signal, and cancellation through a progress indicator ([SearchEverywhereContributor.java](https://raw.githubusercontent.com/JetBrains/intellij-community/master/platform/lang-api/src/com/intellij/ide/actions/searcheverywhere/SearchEverywhereContributor.java)). JetBrains' 2025 rewrite separated data from presentation. The old API "coupled the search result data with the UI renderer", which made results impossible to serialise between a backend and a thin frontend ([JetBrains Platform Blog](https://blog.jetbrains.com/platform/2025/12/major-architectural-update-introducing-the-new-search-everywhere-api-built-for-remote-development/)). Bristlenose has the same shape three times over: Python to React, Python to the Swift host, and Python to an MCP client. Each searcher should therefore return plain rows: kind, id, title, snippet, highlight ranges, deep-link route, rank, why-matched, `has_more`, and count.

As a **UI behaviour**, progressive painting should be kept for the case that needs it. Algolia Autocomplete runs its sources concurrently but updates the panel **once, after `Promise.all`**, and shows a loading state only after a 300 ms stall threshold ([onInput.ts](https://raw.githubusercontent.com/algolia/autocomplete/next/packages/autocomplete-core/src/onInput.ts)). With FTS5 every in-project searcher answers in single-digit milliseconds, so the latency spread is noise. Painting progressively would buy selection jumps, climbing counts and screen-reader chatter to hide a delay nobody perceives. NN/g's thresholds give the frame: under 0.1 s needs no feedback, under 1 s keeps flow unbroken, and beyond that needs "running feedback of completed work" and a way out ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). In-project search should aim for the first threshold and paint atomically. Measure per-lens latency on the largest real project before deciding otherwise; that measurement does not exist yet.

The **folder fan-out** is where streaming earns its keep. Project databases can sit on a sleeping or unmounted drive, and WAL "does not work over a network filesystem" ([SQLite WAL](https://www.sqlite.org/wal.html)). A single streaming endpoint suits this. FastAPI has had native SSE since 0.135.0, including POST bodies and automatic keep-alives ([FastAPI docs](https://fastapi.tiangolo.com/tutorial/server-sent-events/)). Each project emits `{project, status, groups, elapsed}` as it completes, under a per-project deadline of roughly 2–3 s, and the stream ends with an explicit account such as "searched 3 of 4 projects; IKEA kitchen planner is on an unmounted volume". Results from different projects must not be interleaved by raw score. BM25 is corpus-relative: a term present in half the documents scored about zero in one database and far higher in another (measured). ATTACH is also capped at 10 databases by default. So fan out on separate read connections, take each project's top K, and either group by project or merge by rank position with RRF. One placement question needs measurement before any code is written. One Python process opening every project in the folder read-only is simpler. Asking each open project's own sidecar (the existing `ServeFleet`) may be the only option under the sandbox, if one sidecar cannot read a sibling project's folder. The mockup marks this unverified, and it should stay so until tested.

Three client disciplines apply however results arrive, and each prevents a bug that has shipped elsewhere. **Drop stale responses by request id and abort superseded requests.** Algolia shipped the out-of-order overwrite and fixed it with a `latestResolvedId` guard ([algolia/autocomplete d15c404](https://github.com/algolia/autocomplete/commit/d15c404845a1446ad2cc8673c44be4dbfa68723f)); on the server, `Connection.interrupt()` stops an abandoned query ([Python docs](https://docs.python.org/3/library/sqlite3.html)). **Hold selection by identity, not index**, and freeze any top hit once chosen, so Return opens the row the eye was on. **Render deferred, not debounced.** React's `useDeferredValue` keeps the previous results visible, dimmed via an `isStale` flag, while new ones compute, with no fixed delay ([react.dev](https://react.dev/reference/react/useDeferredValue)). The network request is still debounced by 100–150 ms.

## Build a thin contract first, then add one source per release

Strategy (a) ships a v1 search in each lens and then combines them. It delivers visible progress soonest, but it would produce five matchers with five sets of semantics. The TypeScript lens filters would fold diacritics differently from each other and from the MCP tool. Per-lens syntax (`p3`, `#trust`, `is:starred` typed into the Quotes capsule) would be invented before tokens exist, and the combine step would inherit the job of reconciling them. Sessions shows the problem clearly: the mockup's mention counts need every transcript loaded in the client or a server endpoint, so Sessions' "v1" is really the server core. Strategy (b) builds the contract, the menu and the results view first, then adds sources. It gets the architecture right but delivers nothing a researcher can use for weeks. It also designs the contract in a vacuum, which is the usual way contracts end up fitting their first real source badly.

The recommendation is a hybrid: **contract-first, proven on two dissimilar sources, with each lens's local search falling out as "the global field scoped to this lens"**. The mockup already states the key invariant, that ↩ keeps today's behaviour and filters the current lens. A per-lens search is therefore not a separate feature; it is the shared core with a lens scope. The sequence below keeps every step independently shippable, and it keeps the mockup's first step because it depends on nothing.

The first release is **Find in the transcript** (⌘G / ⇧⌘G), done entirely client-side. It is a *find*, not a filter: a cursor moves through hits that stay in place, and the playhead can follow it. The menu review ranks it as the highest-value search item on record, and it is the condition for restoring the Find Next and Find Previous items that are commented out at `MenuCommands.swift:751-791`. The second release **upgrades the baseline matcher in place**. It adds per-word prefix AND, casefold and diacritic folding, a lower minimum length for CJK, localised enum labels, and a match count in the capsule. All of this is written against a **shared normalisation contract fixture** asserted from both vitest and pytest, so that the export's offline matcher and the server can never drift. The third release is **the core**. It adds FTS5 external-content tables through an Alembic migration with triggers, built at the end of stage 12 or lazily on first serve; the capability probe; and the searcher contract with two implementations, quotes (long text, BM25, snippets) and people (short entity, rapidfuzz). A `POST /api/projects/{id}/search` endpoint returns per-kind counts and top-N rows. MCP `search_quotes` is rerouted through it, and a `bristlenose search` CLI command gains `--json` in the same row schema. The fourth release is **the suggestion menu and tokens** fed by those two sources, with Sessions, Codebook and Signals lens capsules turned on as scoped views of the same query. Later releases **add sources one at a time**: tags and codebook definitions, sections and themes, sessions, transcript count rows, and signals (computed per request by matching labels and the quote ids behind each card). Then comes the **results pseudo-lens**, and last the **folder scope** over the streaming endpoint, once the sandbox question is answered.

The hybrid does ask for one discipline that neither pure strategy needs. The first contract must survive the second source unchanged, or it is not yet a contract. Quotes and people differ on almost every axis: long text against short names, BM25 against fuzzy scoring, snippets against none, thousands of rows against dozens. If one row schema and one ranking rule serve both, the remaining five sources are additions rather than redesigns.

## Thirteen practices that turn search into a research instrument

The user asked for best practices beyond those already named. These are the ones the evidence supports, each tied to a concrete researcher benefit.

| Practice | What it does | Why a researcher cares |
|---|---|---|
| **Search and code** | Select all hits (or a subset) and apply a tag in one action, as MAXQDA autocodes and ATLAS.ti codes all results ([MAXQDA](https://www.maxqda.com/help-mx22/lexical-search/search-results); [ATLAS.ti](https://manuals.atlasti.com/Win/en/manual/SearchAndCode/SearchAndCodeTextSearch.html)) | Turns "find every mention of price" into coded evidence in one step; the CAQDAS expectation most UXR repositories miss |
| **Existing codes shown on each hit** | Tags and sentiment render beside the matched quote, as in ATLAS.ti's Quotation Reader | She sees at a glance which hits are already coded, so the bulk action lands on the right rows |
| **Keyword in context** | `snippet()` gives sentence-level context with the term highlighted | Judging relevance without opening each hit is the core speed-up in every CAQDAS tool |
| **Why it matched** | A caption such as "in edited text", "in tag definition" or "said by moderator" | Trust in a result that doesn't visibly contain the word; the mockup's codebook snippet is the same idea |
| **Jump to the moment, and play from it** | Every quote or segment hit deep-links to its timecode; transcript Find moves the playhead | Hearing every mention of a word in a minute; the repository standard since 2024 ([Great Question](https://greatquestion.co/support/repository/ask-ai)) |
| **The codebook as thesaurus** | Tag definitions and codebook terms expand a query ("hidden costs" also finds quotes coded with it) | Synonyms grounded in her own coding, not a generic thesaurus that returns "related-but-off-point" hits ([Great Question](https://greatquestion.co/support/repository/ask-ai)) |
| **Zero-result recovery** | Offer a did-you-mean from the corpus vocabulary, then "include hidden quotes", "search transcripts too", and "search ‹folder›" rows | A no-result screen becomes a next step instead of a dead end |
| **Recents, clearable, session-scoped** | Empty-focus shows this project's recent token sets; "Clear Recents" as the HIG requires ([HIG](https://developer.apple.com/design/human-interface-guidelines/searching)) | Re-running yesterday's query is common. Recents are kept per project and in memory, so they cannot show a name from another client's study |
| **Save search as a view** | An explicit act, stored in the project, the Mac's Smart Mailbox idiom | A recurring question ("pricing, frustrated, p1–p6") stays one click away. Being explicit, it doesn't overturn LensMemory's no-restore rule |
| **Stable results under editing** | A quote edited or untagged from the results view stays in place until the next search, as Mail keeps a message that no longer matches | Coding from search results without rows vanishing under the cursor |
| **Honest counts** | Exact counts for complete groups, "N+" only when capped or indexing, a total only once every source has reported | A count she can quote in a readout. A number that drops as sources arrive teaches distrust |
| **Relevance tuning without analytics** | A golden-query fixture per locale (expected top hits for real queries), gated in CI like the codebook golden fixtures; frecency computed locally, never sent | Ranking improves by evidence without telemetry leaving the machine, consistent with the project's data-governance stance |
| **Accessible by construction** | WAI-ARIA combobox with `aria-activedescendant`, groups as labelled `role="group"`, and one debounced polite announcement per settled query (GOV.UK uses 1.4 s) ([APG](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/); [GOV.UK source](https://raw.githubusercontent.com/alphagov/accessible-autocomplete/main/src/status.js)) | A VoiceOver user hears "23 results in 4 groups" once, not a burst of chatter as each lens lands |

Two of these need a decision rather than an implementation. The first is whether recents persist at all, given that search is deliberately not restored across launches. The recommendation is in-memory recents per project, which honours that decision, plus explicit saved searches as the only persistent form. The second is whether tokens survive a lens switch. The mockup recommends yes, within a session, on the reasoning that "the query describes what you are looking at, and the lens is only how you view it". That is the right call, and it is also what makes per-lens search and global search one feature rather than two.

## Conclusion

Federated search here is less an engine problem than a *vocabulary* problem. SQLite can already answer any single query in milliseconds. The hard work is agreeing, once and in a fixture, what a query *means*: which characters fold, what a word boundary is in Japanese, which label counts as "frustration" in Catalan, when "p3" is a participant and when it is text, and which identities may cross a folder boundary. Build that agreement first and every surface inherits it, including the offline export that has no server. Build five lens searches first and each will answer the question differently, which is the one failure a researcher quoting evidence to a client cannot tolerate.

The other shift is from *retrieval* to *action*. The repositories added AI answers; the CAQDAS tools added "code all hits". For a researcher working to a deadline, the second matters more: a search that ends in a tagged set of quotes has produced analysis, while a search that ends in a list has only produced reading. The privacy argument points the same way. By keeping search inside the project's own database, Bristlenose can promise that a hit never appears anywhere the researcher did not put it. Spotlight cannot promise that, and for people juggling competing clients the promise is part of the product.

## UX ideas worth mocking up

1. **Typed suggestion menu (Photos row anatomy)**: type glyph, primary/secondary completion text, trailing counts, free-text row first. Shows the researcher what exists and how much before she commits to a search.
2. **Intent rows that propose, never presume**: "p3 — participant", "12:04 — timecode in s2", "frustración — sentiment" as offered interpretations below the free-text row. She gets structured precision without the search guessing wrong on her behalf.
3. **Tokens with role menus**: a person token toggling *said by* / *mentions* / *exclude*, and a tag token toggling *tagged* / *text contains*. Distinctions that matter analytically become one click.
4. **Results pseudo-lens with a scope bar**: groups in fixed order, "Show all in Quotes →" carrying the query into the lens, and "Search: This project · ‹Folder›". One place to see everything, with an obvious route into each lens.
5. **Search-and-code action bar**: select hits, then apply a tag or star, with the existing codes shown on each row. Search results become coded evidence in one step.
6. **Transcript Find with a playhead that follows**: current-hit outline, ⌘G stepping, audio jumping to each hit. She can hear every mention of a word in a minute.
7. **Why-it-matched captions and KWIC snippets**: "in edited text", "in tag definition", a sentence of context. She can judge relevance without opening each hit.
8. **Moderator-aware transcript grouping**: participant speech first, moderator turns in their own collapsible group. The evidence surfaces before the interviewer's question does.
9. **Zero-result recovery panel**: did-you-mean, "include hidden quotes", "search transcripts too", "search ‹folder›". A dead end becomes a next step.
10. **Folder results with unmissable provenance**: project name first in bold on every row, speaker codes only, and a closing "3 of 4 projects searched — 1 on an unmounted drive" account. Cross-study patterns without cross-client leaks or silent gaps.
11. **Empty-focus state**: this project's recent searches with Clear, plus saved searches. Yesterday's question is one keystroke away and nothing from another client appears.
12. **"Indexing…" and honest-count states**: footer row during the first index build, "N+" only while capped, a total only when complete. She can trust the numbers she reports.
13. **"Ask the report…" handoff row** for question-shaped queries, visibly marked as a cloud AI step. A synthesis path that never fires by accident.
14. **Lens capsules as scoped views**: the same field in Sessions (mention counts), Codebook (definition snippets) and Signals (dimmed heatmap cells), with tokens carried across lens switches. One mental model of search across the whole app.
15. **Save search as view**: turning a token set into a named, project-local view in the sidebar. A recurring research question becomes a permanent lens on the data.
