# Extend Playwright first, make Storybook earn its place

Bristlenose should start by adding self-hosted Playwright screenshot assertions to the E2E suite it already has, rendered in a version-pinned Linux Docker image on Chromium and WebKit, with baselines committed as WebP. Storybook should be a bounded second contender, tried on a handful of components, and kept only if it reaches states the page suite cannot reach more cheaply. A hosted service should be considered only if reviewing intentional changes turns out to be the bottleneck, and then Argos rather than Chromatic, because Argos diffs screenshots your own CI takes, WebKit included. Chromatic's free tier is Chrome-only and stops testing at 5,000 snapshots a month. The reason is a matter of layers. The nightly guest walk already owns real-WKWebView fidelity, and no option here can reproduce that, because Playwright's WebKit is a patched trunk build, not Safari. What is missing is a cheap, deterministic pixel tripwire on every push, plus a way into the odd states (empty, error, long German labels, every colour theme) that the walk cannot reach. Playwright covers most of that with no new tool. Storybook adds isolated states and conventional documentation, but it costs mocking against 41 files that import `utils/api.ts` directly, plus a Storybook 11 migration already in beta whose notes run to about 2,200 lines. Two of the owner's three goals, token coverage and the component inventory, are not visual-testing problems at all. They are better answered by a stylelint ratchet and an import-graph script than by any of these tools. The spike below runs about six working days and tests each contender at its smallest useful size against numeric kill criteria. Most of those criteria are this report's own proposals, because the sources offered no published framework for one.

## Each option adds a different layer, and only one duplicates the guest walk

The question is easiest to settle by asking which layer each tool adds to the four Bristlenose already runs. Vitest under jsdom tests logic and computes no layout. The Playwright E2E suite on Linux Chromium and WebKit checks that the real SPA mounts against a committed fixture without console errors, broken links, clipped labels or overflow, but it asserts nothing about pixels. The guest walk drives the signed app in a clean macOS 27 VM and pixel-diffs the real WKWebView nightly. It is the only layer with true platform fidelity, and it reaches only the states a scripted walk through a real project produces. Its noise floor is already known: between two unchanged nights, 5 of 26 screens differed, four from model output and one from the Welcome animation. That shows determinism, not capture, is the hard part of any screenshot layer.

| Option | Layer it adds | What it duplicates | States it reaches | Platform fidelity |
|---|---|---|---|---|
| A. Playwright `toHaveScreenshot` in the E2E suite | Per-push pixel diff of the real composed SPA | The guest walk's report-lens screenshots, at lower fidelity | Whatever the fixture and routes produce, plus `page.route()` stubs | Linux WebKit and Chromium: a tripwire, not WKWebView |
| B. Storybook + addon-vitest (+ screenshots) | Isolated component states; render smoke test per story; a catalogue | Some jsdom RTL tests, if `play` functions are written wholesale | Any state a mock can express | Chromium by default; WebKit off the documented path |
| C. Hosted diff (Argos, Chromatic, Percy, Happo) | Baseline storage and a review UI | Nothing new about rendering if fed by A or B | Same as its feeder | Argos: whatever you render. Chromatic and Percy: their cloud browsers |
| D. Vitest browser mode alone, no Storybook | Real layout for component tests in Chromium and WebKit | jsdom tests it is ported from | Whatever the test mounts | Playwright WebKit |

Option A extends the layer nearest to the guest walk. That near-duplication is a strength, not waste: the walk runs once a night on one machine, and a Linux tripwire runs on every push and narrows the walk's job to WKWebView-specific checks. Options B and D add a genuinely new layer, a component rendered in a real browser with layout that jsdom cannot compute. Storybook's own framing puts its testing story "around component tests" in a real browser and sends full workflows to Playwright, and its docs say nothing about overlap with an existing Testing Library suite ([Storybook docs, Writing tests](https://storybook.js.org/docs/writing-tests)). For a project with about 1,700 jsdom tests, converting them into `play` functions would duplicate the suite. The new value is the free per-story render test and the layout-dependent checks hung on it.

## Playwright's own screenshots beat the baseline test, with Docker as the tax

Playwright's position is blunt: rendering "can vary based on the host OS, version, settings, hardware, power source", so a baseline is valid only in the environment that made it. Baseline filenames carry the platform (`-chromium-darwin.png` against `-linux.png`), which means a Mac-made baseline is never even compared on Linux CI ([Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)). The standard fix is to render inside the official image, pinned to the same version as the npm package, currently `mcr.microsoft.com/playwright:v1.64.1-noble`. Playwright warns that a mismatch leaves it "unable to locate browser executables" ([Playwright: Docker](https://playwright.dev/docs/docker)). For a developer on Apple silicon, the useful detail is **remote-server mode**. The browser runs in the container behind `run-server`, while the tests run on the Mac through `PW_TEST_CONNECT_WS_ENDPOINT`, and `--add-host=hostmachine:host-gateway` lets the container reach the host's `bristlenose serve` ([Playwright: Docker](https://playwright.dev/docs/docker)). The alternative is to regenerate baselines only in CI, through a `workflow_dispatch` job that commits changed screenshots. Vitest's docs give that workflow almost verbatim, and warn that local updates "may not match the CI environment" ([Vitest: Visual Regression Testing](https://main.vitest.dev/guide/browser/visual-regression-testing)). Practitioner guides agree that this update loop is the ongoing tax: "Forget once, and the PR turns red with diffs that have nothing to do with the change" ([TestQuality guide](https://testquality.com/?p=7894); [adequatica, Apr 2025](https://adequatica.github.io/2025/04/10/operating-system-independent-screenshot-testing-with-playwright-and-docker.html)). It is unverified whether an arm64 container on the Mac renders pixel-identically to GitHub's x86_64 runner. The spike has to measure that, not assume it.

Flake control is mostly done for you. `toHaveScreenshot` defaults to `animations: "disabled"` and `caret: "hide"`, retries until **two consecutive captures match**, and offers `mask` and `stylePath`, a CSS file applied only during capture, for volatile regions ([Playwright API: toHaveScreenshot](https://playwright.dev/docs/api/class-pageassertions#page-assertions-to-have-screenshot-1)). The default per-pixel `threshold` is 0.2. Sources agree that tolerances should be loosened only after instability is removed ([TestQuality guide](https://testquality.com/?p=7894)). What remains is app-side determinism. Freeze the clock with `page.clock.setFixedTime()`, stub polling endpoints, wait for `document.fonts.ready`, move the mouse to `-1,-1`, and set `colorScheme` and locale explicitly ([Diffy blog](https://diffy.website/blog/playwright-screenshots-ci-docker/); [Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)). That checklist is identical for every option, hosted ones included. A region that keeps changing produces a timeout rather than a silent pass. That fits the house rule that a gate must be able to fail.

The fidelity ceiling is real and should be stated in the suite's own docs. Playwright's WebKit is "derived from the latest WebKit main branch sources", it does not work with branded Safari, and the docs point to macOS for the closest-to-Safari behaviour ([Playwright: Browsers](https://playwright.dev/docs/browsers)). One public PR notes that Linux WebKit uses a different network stack and compositor, "so screenshots do not match" macOS ([storybranch PR #40](https://github.com/adriangohjw/storybranch/pull/40), search snippet). A WebKit-on-Ubuntu font-weight bug was fixed in Playwright 1.33, but similar reports kept arriving on Windows through late 2024 ([microsoft/playwright #22429](https://github.com/microsoft/playwright/issues/22429)). Linux WebKit screenshots therefore catch layout and token regressions, and leave native scrollbars, form controls, Core Text rasterisation and colour management to the guest walk. A `-darwin` set on a GitHub macOS runner would come closer. That runner costs **$0.062/min against $0.006/min on Linux**, and the fetched page confirms only that *larger* runners are not free for public repos, so whether a standard macOS runner bills this repo is unconfirmed ([GitHub runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)).

Committing baselines is Playwright's official model ("commit this directory ... and review any changes to it"), and WebP is supported to cut size ([Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)). The objections in the literature are mostly team-scale: merge conflicts, review across people, and comparing against the last push. Their loudest source is the Argos author on Hacker News, whose thread drew one comment ([HN 43653464](https://news.ycombinator.com/item?id=43653464)), and Argos's own blog, which sells hosted baselines ([Argos: Playwright VRT in CI](https://argos-ci.com/blog/playwright-visual-regression-testing-ci)). For one developer, conflicts largely vanish. Two costs remain: permanent git-history growth, and reviewing dozens of intentional diffs after a token edit. The matrix is what makes either cost blow up. Light and dark on two browsers multiplies every shot by four, and all 21 locales and every colour theme multiply it into the thousands. The workable scope is every page in one locale and theme, a German long-string run on key components, and colour themes on a swatch page or one representative screen. Neither the notes nor any source found offers a non-vendor 2024–2026 case study of a team keeping or abandoning self-hosted Playwright screenshots. The case for option A rests on mechanism and fit, not on testimony.

## Storybook 10 fits the stack today, and the bill arrives with 11

Storybook 10.6.8 (20 Nov 2026) declares peers that cover every Bristlenose pin: `vite ^5–^8`, React up to 19, and TypeScript 4.9+. It has supported Vite 8 officially since 10.3 (18 Mar 2026), and Node 24 clears its ESM-only floor ([npm registry, @storybook/react-vite](https://registry.npmjs.org/@storybook%2Freact-vite); [Storybook 10.3 blog](https://storybook.js.org/blog/storybook-10-3/); [Storybook 10 blog](https://storybook.js.org/blog/storybook-10/)). Vite 8 brings frictions that are open rather than fatal. In dev, the preview runtime is served at 1.3 MB with an inline sourcemap against 383 kB on Vite 7, pending an upstream Vite fix ([storybookjs/storybook#36228](https://github.com/storybookjs/storybook/issues/36228)). A static build warns about a 1,119 KiB preview chunk ([#37495](https://github.com/storybookjs/storybook/issues/37495)). And dev can fail to resolve tsconfig `paths` that the build resolves, so a green build can sit beside a broken dev server ([#36005](https://github.com/storybookjs/storybook/issues/36005)). The timing is the decisive fact. **Storybook 11 is at 11.0.0-beta.5 (23 Nov 2026)**, and its 10→11 migration section runs about 2,188 lines with 87 headings, against about 150 for 9→10 ([npm registry, storybook](https://registry.npmjs.org/storybook); [MIGRATION.md, next](https://github.com/storybookjs/storybook/blob/next/MIGRATION.md)). Most items target addon authors and other frameworks. Ordinary projects still feel several: `@storybook/test-runner` is removed, `globalTypes` loses `defaultValue`, `fn()` typing changes under CSF Next, and `typescript` becomes a required peer ([MIGRATION.md, next](https://github.com/storybookjs/storybook/blob/next/MIGRATION.md)). A setup built on 10.6 today faces that migration within months. No date has been published for 11.0 stable.

Theming is cheap if hand-rolled. Import the SPA's own CSS entry in `.storybook/preview.ts`. Declare two `globalTypes`, scheme and colour theme. Write one decorator that sets `color-scheme` on `<html>` (what `light-dark()` follows) and `data-color-theme`, ideally by calling the same boot function the SPA uses so the two cannot drift. The official `addon-themes` owns a single `theme` global, and Bristlenose has two independent axes ([Storybook docs: Themes](https://storybook.js.org/docs/essentials/themes); [Toolbars & globals](https://storybook.js.org/docs/essentials/toolbars-and-globals); [Mozilla bug 1858998](https://bugzilla.mozilla.org/show_bug.cgi?id=1858998)). A third global plus `i18n.changeLanguage` covers locale. That avoids `storybook-react-i18next`, which needs a separate release line for each Storybook major ([npm registry, storybook-react-i18next](https://registry.npmjs.org/storybook-react-i18next)). "Modes", the multiplication of stories across theme and locale, is a Chromatic feature layered on globals, not something Storybook core does by itself ([Chromatic docs: Modes](https://www.chromatic.com/docs/modes/)).

Mocking is where the cost concentrates, because Bristlenose's components are connected by design. A survey of the repo found 34 files using `useSyncExternalStore`, 24 store modules in `contexts/`, and 41 non-test files importing `utils/api.ts`, which has 77 exports. The least invasive route is `sb.mock(import('../src/utils/api.ts'))` in `preview.ts`, which automocks every export with no change to app code. Stories then set `mocked(fn).mockResolvedValue(fixture)` per state, and a never-resolving promise or a rejection gives the loading and error states for free ([Storybook docs: Mocking modules](https://storybook.js.org/docs/writing-stories/mocking-data-and-modules/mocking-modules)). The sharp edges are documented. Mocks are registered globally only, with no factory and no unmock, and the module is still evaluated, so import-time side effects run ([Storybook docs: Mocking modules](https://storybook.js.org/docs/writing-stories/mocking-data-and-modules/mocking-modules)). An open bug empties arrays and breaks `new` on classes in spy mode under dev and build but not under the Vitest addon, "so CI is green while dev and the deployed Storybook are broken" ([#37040](https://github.com/storybookjs/storybook/issues/37040)). Another open bug breaks mocking of files that export a TypeScript `enum` ([#32336](https://github.com/storybookjs/storybook/issues/32336)). The stores themselves must not be automocked. An automocked `subscribe` or `getSnapshot` returns `undefined`. They are module singletons that leak state between stories, so each store wants a reset hook called in a global `beforeEach`. That small app-side change is the main defence against order-dependent stories. MSW (`msw-storybook-addon` 3.0.3) is the higher-fidelity alternative, keeping the real `api.ts` code path, at more cost per story ([npm registry, msw-storybook-addon](https://registry.npmjs.org/msw-storybook-addon)). Storybook's own guidance concedes that the clean fix, restructuring into presentational and container components, "may be difficult" in an existing app ([Storybook docs: Build pages](https://storybook.js.org/docs/writing-stories/build-pages-with-storybook)). No source quantifies hours per connected story. The spike must measure that number before any other.

As a test harness, `@storybook/addon-vitest` turns every story into a browser-mode render test, sits beside the jsdom suite as a separate Vitest project, and needs no running Storybook. It is documented and configured for Playwright's Chromium only ([Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)). Vitest's Playwright provider supports WebKit, so a `webkit` instance is a config change ([Vitest: Browser Mode](https://vitest.dev/guide/browser/)), but the only field example found is one project's CI jobs, not a stability report ([geul-web PR #248](https://github.com/echovisionlab/geul-web/pull/248)). Screenshots are a gap. The addon's comparison table says it does not do snapshot tests. Calling Vitest's native `toMatchScreenshot` inside a story test threw `Invalid Chai property`, and the reply (from a bot, not a maintainer) was that "Storybook continues to recommend Chromatic for visual regression testing" ([discussion #32930](https://github.com/storybookjs/storybook/discussions/32930)). The workarounds are a hand-written `composeStories` test calling `toMatchScreenshot`, a third-party addon, or a Playwright loop over Storybook's `index.json`. Every one of them inherits the same Docker and platform-suffix discipline as option A. Storybook does not remove that work. It adds a second server and a fixture layer on top of it.

The case for "embrace the React tooling" deserves its strongest form. Stories are the convention a future contributor will look for. They give an isolated development surface for states that are tedious to reach in the app. Storybook now ships agent-facing features, including Storybook MCP for React in 10.3 and an AI setup in 10.4 that generates a provider tree, MSW mocks and stories ([Storybook 10.3 blog](https://storybook.js.org/blog/storybook-10-3/); [Storybook 10.4 blog](https://storybook.js.org/blog/storybook-10-4/)). The counter-evidence is opinion rather than data, but it is consistent: stories rot within months unless writing them is part of "done", and they pay off mainly for larger teams whose designers or clients actually look at them ([Yashveer Labs, 2026, opinion](https://yashveerlabs.vercel.app/blog/storybook-in-2026-still-worth-it); [Atomic Object, older](https://spin.atomicobject.com/using-storybook-reconsider/)). Running stories as tests catches the story that breaks. It cannot catch the story that renders fine and no longer resembles the app, through stale fixtures or a missing provider or stylesheet. That drift silently weakens any visual baseline taken from stories, whereas a page-level baseline cannot drift from the app by construction. The resolution is a matter of scope. Storybook's natural territory is the **16-primitive library**: leaf components that need args and no mocks, where a catalogue doubles as documentation. Its worst territory is the **~25 page-local connected components**, exactly where the owner most wants visibility.

Two warnings apply to the whole category. First, nearly every 2026 comparison that search surfaced was **written by Argos, a competitor**, and its figures for rivals disagree with the rivals' own pages. Chromatic's entry tier appears there at $149, while Chromatic's page says $179 today ([Chromatic pricing](https://www.chromatic.com/pricing); [Argos comparison, search result](https://argos-ci.com/blog/percy-vs-chromatic-vs-argos)). Chromatic's and Argos's claims about each other, and about Playwright, should be read as marketing ([Chromatic: Playwright comparison](https://www.chromatic.com/compare/playwright); [Argos: best VRT tools 2026](https://argos-ci.com/blog/best-visual-regression-testing-tools)). No independent first-hand 2026 user report was found. Second, Lost Pixel's shutdown, announced with no shutdown date or data guidance, is a live example of hosted-baseline risk ([Lost Pixel blog](https://www.lost-pixel.com/blog/lost-pixel-team-is-joining-figma)). No hosted service removes the determinism work, and none renders WKWebView. What they sell is a review UI and somewhere other than git to keep baselines. For a solo developer, those are worth paying for only once the spike shows that review time, not capture, is the bottleneck.

## Token coverage and the component inventory need a linter and a script

Goal (a) is a source-code property, and Storybook's token tooling only **displays** tokens. `storybook-design-token` renders swatches from `@tokens` comments and can label a token "global or unused" only from a usage map you generate yourself. It computes no coverage metric ([storybook-design-token README](https://github.com/UX-and-I/storybook-design-token)). The direct tool is a stylelint gate. `stylelint-declaration-strict-value` requires listed properties to use a variable, function or keyword, with an `ignoreValues` escape hatch ([README v1.11.1](https://unpkg.com/stylelint-declaration-strict-value@1.11.1/README.md)). Core stylelint can restrict which custom-property families each property may use ([stylelint.io, Customize](https://stylelint.io/user-guide/customize)). `stylelint-value-no-unknown-custom-properties` catches a typo'd `var(--bn-colr-…)` that falls back silently, a failure neither `audit-css.py` nor the live scan can tell apart from a deliberate value ([csstools](https://github.com/csstools/stylelint-value-no-unknown-custom-properties/)). Mozilla's `use-design-tokens` rule is prior art at scale for exactly this ([Firefox source docs](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens.html)). The shape that fits Bristlenose's gate policy is a ratchet. Start with colour, background and border on a baselined violation count, widen one property family at a time, and keep `audit-css.py` as the trend line and `live-scan.mjs` as the only check on computed style. The sanctioned exception, a researchers' proposal rather than sourced practice, is a stylelint disable comment that must carry a written reason, so every exception is greppable and reviewable. `ignoreValues` covers keyword-level exceptions such as `initial`.

Goal (b) is an import-graph question. react-scanner's `raw-report` processor emits every component instance with its file location ([moroshko/react-scanner](https://github.com/moroshko/react-scanner)). A small script can classify each component by where it is defined (the primitives directory or a page file) and how many distinct files import it (one means a one-off, two or more means shared). That gives a re-runnable answer derived from the running code, which matches the repo's "derived from the running thing" seam rule. react-scanner's handling of components defined locally, rather than imported, is undocumented. A TypeScript-compiler AST walk may be needed for the page-local one-offs, which are precisely the ones that matter. Omlet, the hosted dashboard, announced on 28 Apr 2026 that it is going fully open source under MIT, and a fork carries a guide for migrating off the hosted service ([Omlet blog](https://omlet.dev/blog/); [drianoaz/omlet](https://github.com/drianoaz/omlet)). That reads as a wind-down of the hosted product, but the post body could not be read, so this is inference. "Has a story" as the definition of "in the design system" is a team convention, not a tool feature. It would tie the inventory to the most rot-prone artefact in the stack. Accessibility follows the same logic. `@axe-core/playwright` drops into the existing suite on both browsers, and its documented fingerprint-snapshot pattern for known issues is a ratchet ([Playwright docs, accessibility](https://playwright.dev/docs/accessibility-testing)). Storybook's `addon-a11y` uses the same axe-core, and in its `'todo'` mode it reports "nothing at all in CI", which the gate policy would treat as a soft gate with no disposition ([Storybook docs, accessibility testing](https://storybook.js.org/docs/writing-tests/accessibility-testing)).

## A six-day spike, ordered so the cheapest option sets the bar

The spike builds the smallest version of each contender that can answer a decision, in an order where each step reuses the last. No criterion below comes from published practice: the sources offered no VRT spike framework, so every threshold is marked **[proposal]** unless a source fixes the mechanism. Where a criterion rests on a sourced mechanism (`--repeat-each`, platform-suffixed baselines, runner pricing), that is noted as **[mechanism sourced]**.

| Order | Contender | Smallest version worth comparing | Time box |
|---|---|---|---|
| 0 | Shared harness | Determinism kit: pinned `@playwright/test` and Docker tag, `page.clock` frozen, polling stubbed, `document.fonts.ready`, mouse reset, one `stylePath` file killing transitions, spinners and video. A seeded-regression branch with six deliberate breaks | 0.5 day |
| 1 | A: Playwright screenshots | About 10 viewport-level page shots and 10 locator shots across existing routes on the committed fixture; light and dark; one non-default colour theme; German on 5 key components; Chromium and WebKit; WebP baselines; remote-server mode on the Mac and a `workflow_dispatch` update job | 2 days |
| 2 | Goals (a) and (b) side track | stylelint with `declaration-strict-value` on colour families plus `value-no-unknown-custom-properties`, violations baselined; inventory script over `frontend/src` | 0.5 day |
| 3 | B: Storybook | Storybook 10.6.8, hand-rolled scheme, theme and locale decorators, `sb.mock` on `api.ts`, store resets. Stories for 3 primitives, 2 connected components (one API-driven, one store-driven), and 1 page-local one-off, each with Empty, Error, Long German and Dark stories. addon-vitest with `chromium` and `webkit` instances; screenshots through a `composeStories` + `toMatchScreenshot` file. One timed upgrade of the branch to the 11.0 beta | 2 days |
| 4 | C: Hosted review | Upload option A's screenshots to Argos Hobby; optionally publish B's stories to Chromatic free to judge its review UI (Chrome only) | 0.5 day |
| 5 | Decision | Score against the table below; write the outcome into the design doc | 0.5 day |

The six seeded regressions are chosen to show where the layers overlap and where they leave gaps: a 1px padding token change; a colour token changed in dark mode only within a non-default colour theme (a state the guest walk does not visit); a font-weight change; a hidden icon; a German label that overflows its button; and a change to a native control or scrollbar style that only WKWebView renders faithfully. The last records whether Linux WebKit sees it, or whether it stays the guest walk's job.

| Criterion | How measured | Success | Kill | Basis |
|---|---|---|---|---|
| Flake rate | `--repeat-each=20` locally in Docker plus 5 consecutive CI runs, `threshold` 0.2, `maxDiffPixels` fixed before the run | 0 screenshot failures | More than 1 flaky shot in 100 runs after the determinism kit | [mechanism sourced](https://playwright.dev/docs/test-cli); thresholds [proposal] |

The decision rule follows from the layer argument, and it too is a proposal. If A passes its flake, cross-OS and seeded-regression criteria, it becomes the visual-regression layer, with a soft-gate disposition (ratchet or conditional) recorded in `docs/testing/soft-gates.json` before it ships. The stylelint ratchet and the inventory script go ahead regardless, because they answer goals (a) and (b) whatever happens to the visual tooling. Storybook is adopted only if its connected-component cost lands under the kill line, it reaches states that A could reach only through stubs costing more, and the owner values the catalogue as documentation. It should then be scoped to the primitives plus a few named connected states, and installed on 11.0 stable rather than on 10.6. A hosted service is trialled only if review time, not capture, breaks its line. Throughout, the guest walk stays the arbiter of what the Mac app actually looks like.

## Conclusion

The research shifts the question. It is less "which tool" than "which layer is actually missing". Real-WebKit fidelity, the property the owner prizes most, already has an owner in the guest walk, and none of these tools can take it over: Linux WebKit, Chromatic's Safari and Percy's Safari are all approximations of WKWebView. What is missing is cheap per-push determinism and reach into odd states. Determinism is the same work whichever tool captures the pixels, and Playwright is the cheapest place to do it. That makes the owner's two leanings complementary rather than opposed. Extending Playwright is the floor that every other option must clear. React-ecosystem tooling should be embraced where it is strongest, the primitive catalogue, and not where it is weakest, the connected one-offs.

One implication reaches beyond tooling. The connected one-offs are expensive to put in Storybook and are the ones goal (b) wants surfaced, and both facts point to the same design debt: components that fetch and subscribe for themselves. If the inventory script shows many one-offs duplicating a primitive's role, pulling them into presentational primitives would at once raise token consistency, shrink the inventory and make Storybook cheap. The spike should therefore record its mocking cost per component as a measure of that coupling, not only as a verdict on Storybook.
