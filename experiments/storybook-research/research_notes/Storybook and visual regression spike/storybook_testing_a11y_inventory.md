# Storybook as a testing and design-system tool: Test addon, a11y, tokens, component inventory, maintenance

Researched 24 Nov 2026. Storybook docs read were labelled **version 10.6**; Vitest docs read were **v5.1.1**. Version claims below are dated to those pages unless flagged. 21 tool calls; several questions have thin public evidence and are marked as gaps rather than filled.

## 1. `@storybook/addon-vitest` (Storybook Test): mechanics, browsers, CI, coverage, coexistence with a jsdom Vitest config

### Takeaway
The addon compiles every story file into Vitest tests (via portable stories) and runs them in **Vitest browser mode, Playwright provider, Chromium by default**. Every story becomes a render smoke test, and a story with a `play` function also becomes an interaction test. It sits beside an existing jsdom setup as a **separate Vitest project** (Vitest 4+) and needs no running Storybook. WebKit is a supported Playwright browser in Vitest browser mode, so a `webkit` instance is a config change. But Storybook's docs only document and recommend Chromium, and I found no first-party statement or field report that Storybook Test is exercised on WebKit.

### Cited Findings
- The addon "uses a Vitest plugin to turn stories into tests built on portable stories" and runs them in browser mode. It requires a Vite-based Storybook framework (`react-vite` and others). Every story gets a smoke test that checks it renders, and a `play` function is executed with its assertions checked. No running Storybook is needed for the tests. — [Storybook docs, Vitest addon (v10.6)](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- Default and recommended browser: "We recommend (and configure, by default) running Vitest in browser mode, using Playwright's Chromium browser." Other browsers go through Vitest's browser instance option, and WebDriverIO can replace Playwright. The page does not list WebKit explicitly. — [Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- The generated config extends the Vite config and adds a `storybook` project with `browser: { enabled: true, provider: playwright({}), headless: true, instances: [{ browser: 'chromium' }] }`. On **Vitest 4.x** the docs recommend a separate test project; on 3.x a workspace file. **Unit-only settings such as `setupFiles` and `environment` should move into the unit project** so they don't leak into stories. Requirements: Vitest ≥ 3.0, MSW ≥ 2.0 if used. — [Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- CI: the suggested script is `vitest --project=storybook`. Set `storybookUrl` so failures link to a published Storybook. For "Cannot connect to the iframe" resource errors, the docs suggest `isolate: false` or sharding (`vitest run --shard=1/3`). — [Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- Coverage: the addon can compute coverage from stories, but **coverage is a global Vitest option**, so `vitest --project=storybook --coverage` uses the root `test.coverage` config even with `extends: false`. — [Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- The addon's comparison table says it does **not** support snapshot tests. — [Storybook docs, Vitest addon](https://storybook.js.org/docs/writing-tests/integrations/vitest-addon)
- Vitest browser mode: providers are `preview`, `playwright` and `webdriverio`. **Playwright supports firefox, webkit and chromium**; WebdriverIO supports firefox, chrome, edge and safari. CI needs playwright or webdriverio, and `headless` defaults to true in CI. Known browser-mode limits: native `alert`/`confirm` are mocked, and `vi.spyOn` on an ES module namespace throws (use `vi.mock(path, { spy: true })`). The page shows a mixed `projects` setup of a Node unit project plus a browser project. — [Vitest docs, Browser Mode (v5.1.1)](https://vitest.dev/guide/browser/)
- Vitest 4 (released late 2025) made Browser Mode stable and added visual regression (`toMatchScreenshot`). Provider packages are now separate (`@vitest/browser-playwright` and others). — [InfoQ, Vitest 4 browser mode (Dec 2025)](https://www.infoq.com/news/2025/12/vitest-4-browser-mode); [heise, Vitest 4.0](https://heise.de/-10814342); [Vitest 4 blog](https://main.vitest.dev/blog/vitest-4)
- WebKit usage in the wild: one public project (echovisionlab/geul-web PR #248) moved to the Storybook Vitest addon and ran stories in separate Chromium, Firefox and WebKit CI jobs. This is a single usage example, not a stability report. — [GitHub PR #248, geul-web](https://github.com/echovisionlab/geul-web/pull/248)
- Open bug, about two months old: addon-vitest sets Vitest's `include` to every stories glob, so every story file is imported even when its tag filter excludes all its stories. The reporter still reproduced it on the latest versions. — [storybookjs/storybook #36386](https://github.com/storybookjs/storybook/issues/36386)
- Version-coupling bugs from the 9.x era: the addon failed to start from Storybook 9's UI on old Vite (fixed by Vite 6.2.4) and failed on Vite 5. Stories importing from `vitest` crashed Storybook after Vitest 4 (reported on Safari 26.1). — [#31619](https://github.com/storybookjs/storybook/issues/31619); [#31624](https://github.com/storybookjs/storybook/issues/31624); [#33215](https://github.com/storybookjs/storybook/issues/33215); also [#32444, tests fail in non-browser mode in v9](https://github.com/storybookjs/storybook/issues/32444)
- Storybook's own a11y page warns that results "can vary across environments because axe-core output can differ by browser version or configuration", and it says tests run with Playwright's Chromium. — [Storybook docs, accessibility testing (v10.6)](https://storybook.js.org/docs/writing-tests/accessibility-testing)

### Inferences
- **WebKit:** mechanically, adding `{ browser: 'webkit' }` to the storybook project's `instances` should work, because Vitest's Playwright provider supports it. But it is off the documented path, so a WebKit-only breakage is the project's own to debug. For a WKWebView-primary product this is the main open risk of the addon. It deserves one empirical spike: a handful of stories under a `webkit` instance, on macOS and on GitHub Actions `ubuntu-latest`.
- **Coexistence with ~1,700 jsdom tests** is clean in shape: two Vitest projects in one config, with jsdom-specific `environment`/`setupFiles` scoped to the unit project. The one coupling is coverage, which is global. A merged coverage figure would blend jsdom and browser runs unless they run as separate invocations.
- **Overlap with the existing Playwright E2E:** the addon's free render smoke test per story overlaps the E2E "each page mounts / no console errors" check only at page granularity. Stories render a component in isolation with fixture props, so they catch prop combinations the E2E server data never produces, but they do not exercise the real API, router or `--bn-*` theme wiring unless the Storybook preview loads the same global CSS.
- The bugs found are version-coupling bugs (Vite, Vitest and Storybook majors moving together). Expect this to recur at each Vite or Vitest major. The repo runs Vite 8; I found no report confirming Storybook 10.x support for Vite 8 specifically (see Gaps).

### Gaps
- **No first-party statement or field report of Storybook Test running reliably on WebKit**, on macOS or on Linux CI. The searches turned up nothing either way.
- **No published run times or flakiness rates** for addon-vitest suites of a given size, beyond the docs' sharding and `isolate: false` advice. I found no engineering blog with numbers.
- **Vite 8 compatibility** of Storybook 10.x / addon-vitest was not confirmed in any source read.
- I found no report on how Vitest browser-mode coverage (istanbul or v8 in a browser) merges with jsdom coverage in practice.

## 2. Interaction tests (`play`) vs Testing Library component tests vs Playwright E2E: where each belongs, and duplication

### Takeaway
Storybook frames its whole test story around **component tests in a real browser**: render, smoke, interaction (`play`), a11y and visual. It sends full-workflow tests to Playwright or Cypress. It does not address overlap with existing Testing Library/jsdom tests at all. For a project with 1,700 jsdom tests, a `play` function would mostly duplicate an RTL test, run in a real browser instead of jsdom. The new thing it adds is real layout and CSS, which jsdom cannot provide.

### Cited Findings
- "In Storybook, the entire testing experience is built around component tests": a component rendered in a real browser, with simulated interaction, testing one unit of UI, with mocking available. A story alone is a render test that "passes when the story renders successfully and fails when it errors." Interaction tests are `play` functions for stateful components and user behaviour. — [Storybook docs, Writing tests](https://storybook.js.org/docs/writing-tests)
- Snapshot tests: "In most cases, the other testing types will provide more coverage with less effort." On coverage, the goal "is not to get 100% coverage and fill every gap." — [Storybook docs, Writing tests](https://storybook.js.org/docs/writing-tests)
- Stories can be reused in Vitest/Jest unit tests and imported into Playwright/Cypress E2E. E2E is for when "you need to test a full workflow, with the full running stack." **The page has no comparison table and does not mention Testing Library, jsdom, or duplication.** — [Storybook docs, Writing tests](https://storybook.js.org/docs/writing-tests)

### Inferences
- A defensible split for this codebase:
  - **jsdom RTL**: logic, state, store wiring, and anything not needing layout. Keep these as they are.
  - **Story + `play` in browser mode**: only behaviour that depends on real layout or CSS (overflow, focus rings, clipped labels, scroll containers, popover positioning). jsdom computes no layout, and the E2E already asserts no clipping or overflow on whole pages.
  - **Playwright E2E**: the whole stack and composed pages.
- Converting RTL tests into `play` functions wholesale would duplicate the suite and slow it down for no gain. The marginal value is the render-per-story smoke test at no extra cost, plus a11y and visual checks hung on the same stories.
- An alternative with less tooling: Vitest browser mode on its own (no Storybook), as a second Vitest project, running a few existing RTL-style tests in real Chromium and WebKit. That gets real layout without authoring stories. This follows from the Vitest docs, not from any team report found.

### Gaps
- I found no 2024–2026 engineering blog that reports measured duplication between Storybook interaction tests and an existing RTL suite, or a migration away from one.

## 3. `@storybook/addon-a11y` vs `@axe-core/playwright` in the existing E2E

### Takeaway
Both are axe-core. The Storybook addon checks each story, which covers states that are hard to reach on a page. It becomes a CI gate only when `parameters.a11y.test: 'error'` is set and the Vitest addon runs, and that run is documented on Chromium. `@axe-core/playwright` drops into the existing Playwright suite, so it runs on **Chromium and WebKit pages already being crawled** and needs no new infrastructure. For this project that is the cheaper first gate. Story-level a11y adds value only once stories exist for other reasons.

### Cited Findings
- The addon is built on Deque's axe-core and "automatically catches up to 57% of WCAG issues". Results show as Violations, Passes and Incomplete (needs manual review). — [Storybook docs, accessibility testing (v10.6)](https://storybook.js.org/docs/writing-tests/accessibility-testing)
- `parameters.a11y.test` values: `'off'` (no run), `'todo'` (warnings in the UI, **nothing at all in CI**), and `'error'` (fails in the UI and in CLI/CI). Failures block CI only on `'error'`. With the Vitest addon, `'error'` stories run their a11y checks automatically in CI. — [Storybook docs, accessibility testing](https://storybook.js.org/docs/writing-tests/accessibility-testing)
- Rule control: `parameters.a11y.config.rules` (enable, or limit a rule by selector), `parameters.a11y.options` (`runOnly`, for example to add AAA), `parameters.a11y.context` (exclude elements), settable per project, component or story. The `region` rule is off by default. There is no explicit false-positive workflow. Async rendering (Suspense) can produce **false negatives** because checks run too early, and the documented mitigation is `features.developmentModeForBuild: true`. A11y tests must run together with component tests in the testing widget. — [Storybook docs, accessibility testing](https://storybook.js.org/docs/writing-tests/accessibility-testing)
- `@axe-core/playwright`: `new AxeBuilder({ page }).analyze()`, plus `.include()`, `.exclude()` (use sparingly, since it disables every rule on that subtree), `.withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa'])` and `.disableRules([...])`. For known issues, **snapshot a fingerprint (rule id plus `node.target` selectors), not the volatile violations array**. Share configuration through a `base.extend` fixture. The page gives no WebKit-specific notes. — [Playwright docs, accessibility testing](https://playwright.dev/docs/accessibility-testing)
- Before the Vitest addon, Storybook's suggested whole-catalogue CI scan used the Jest+Playwright test runner with `axe-playwright`, a different package. — [Storybook blog, automate accessibility tests](https://storybook.js.org/blog/automate-accessibility-tests-with-storybook); [GitLab UI MR using the test runner](https://gitlab.com/gitlab-org/gitlab-ui/-/merge_requests/4720/commits)

### Inferences
- **Duplication:** the same engine and rule set either way, so running both duplicates the work for any state visible on a crawled page. Story-level a11y earns its place only for states E2E can't easily reach (error, empty, loading, disabled variants), and only if those stories exist anyway.
- The fingerprint-snapshot pattern in the Playwright docs is a ratchet, which fits the project's existing gate policy (a number that may not rise). The Storybook `'todo'` mode is silent in CI, which the project's gate policy would treat as a soft gate with no disposition.
- axe colour-contrast results depend on computed styles. Running it on the real WebKit page under the real `--bn-*` theme (light and dark) is closer to what users see than a story whose preview may not load the full global CSS.

### Gaps
- I found no quantified false-positive rates for addon-a11y or for axe on WebKit vs Chromium. The "results vary by browser" warning is the only first-party statement.
- I found no source comparing `@axe-core/playwright` and `addon-a11y` head to head.

## 4. Design-token tooling around Storybook vs linting the CSS

### Takeaway
Storybook token tooling **documents** tokens: swatches, type specimens, token tables. It does not **measure or enforce** their use. `storybook-design-token` can show "global or unused" tokens only from a usage map you generate yourself. For goal (a), raising token coverage, a **stylelint gate on the CSS source** is the direct tool. It fails per declaration, in the editor and in CI, which a coverage percentage cannot do, and it complements the existing Python scorer and rendered-style scan.

### Cited Findings
- `storybook-design-token` reads annotation comments in the stylesheets themselves (`/** @tokens Colors */`, optional `@presenter`, ended by `@tokens-end`). It parses css/scss/less/svg/images, with the glob set by `DESIGN_TOKEN_GLOB` or a `main.js` option. **v5 targets Storybook 10+ (ESM-only)**, the v4 branch Storybook 9, and v3 Storybook 7/8. It does not detect usage. You supply a `usageMap` (token to components) from your own prebuild script, and tokens missing from it show "This token appears to be global or unused." It has no coverage metric. — [UX-and-I/storybook-design-token README](https://github.com/UX-and-I/storybook-design-token)
- `ColorPalette` and `Typeset` are Storybook's built-in doc blocks, used in MDX, and placing doc blocks inside stories breaks Storybook. `swatchbook` is a Storybook 10 / Vite addon with DTCG token doc blocks (`<TokenTable/>`, `<ColorPalette/>`, `<TokenDetail/>`). — [Storybook docs, doc blocks](https://storybook.js.org/docs/writing-docs/doc-blocks); [swatchbook addon](https://storybook.js.org/addons/@unpunnyfuns/swatchbook-addon); [swatchbook quickstart](https://unpunnyfuns.github.io/swatchbook/quickstart)
- `stylelint-declaration-strict-value` enforces that listed properties (strings or regexes) use a variable, function or allowed keyword instead of a raw value, with an `ignoreValues` escape hatch (for example `initial`). About 429k weekly downloads per Snyk. — [npm](https://npmjs.com/package/stylelint-declaration-strict-value); [README v1.11.1](https://unpkg.com/stylelint-declaration-strict-value@1.11.1/README.md); [Snyk](https://security.snyk.io/package/npm/stylelint-declaration-strict-value)
- Stylelint core can do token enforcement without plugins: `referenceFiles` plus `value-type-custom-property-required-list` and `declaration-property-custom-property-allowed-list`, which point at a `tokens.css` and restrict which token families each property may use. — [stylelint.io, Customize](https://stylelint.io/user-guide/customize)
- `stylelint-value-no-unknown-custom-properties` (csstools) flags `var(--x)` where `--x` is never defined. `importFrom` takes CSS or JSON sources of definitions. v6.0.0 requires stylelint ≥ 16, and the latest found is 6.1.1. — [GitHub csstools](https://github.com/csstools/stylelint-value-no-unknown-custom-properties/); [jsDelivr](https://www.jsdelivr.com/package/npm/stylelint-value-no-unknown-custom-properties). Project Wallace's stylelint plugin has an equivalent `no-unknown-custom-properties` rule. — [projectwallace README](https://raw.githubusercontent.com/projectwallace/stylelint-plugin/HEAD/src/rules/no-unknown-custom-properties/README.md)
- Prior art at scale: Mozilla ships a `use-design-tokens` stylelint rule ("checks that CSS declarations use design token variables instead of hardcoded values", per property family, e.g. colour) and has an open bug to drive token adoption with custom stylelint rules. — [Firefox source docs, use-design-tokens](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens.html); [colour sub-rule](https://firefox-source-docs.mozilla.org/code-quality/lint/linters/stylelint-plugin-mozilla/rules/use-design-tokens/color.html); [Bugzilla 1979098](https://bugzilla.mozilla.org/show_bug.cgi?id=1979098)
- `stylelint-plugin-rhythmguard` positions itself as token governance (require tokens, catch arbitrary values). — [Socket](https://socket.dev/npm/package/stylelint-plugin-rhythmguard)

### Inferences
- **Lint is the better coverage gate.** It names the file and line, it runs in the editor, and it can be ratcheted: start with `declaration-strict-value` on colour, background and border-colour (the high-value families) with the current violations baselined, then widen it. The existing Python 81% scorer becomes the trend metric and stylelint the enforcement. Storybook adds nothing on the source side.
- `value-no-unknown-custom-properties` catches a typo'd `var(--bn-colr-…)`, which silently falls back. Neither the Python coverage score nor (likely) the rendered-style scan distinguishes that from a deliberate value. It costs almost nothing to adopt.
- The rendered-style Playwright scan remains the only check on what the browser actually computed (cascade, inline styles, JS-set styles). Lint and that scan cover different failure classes. Storybook token pages would be a *view* of `--bn-*`, useful to a designer, and would require adding `@tokens` annotations to the theme CSS.

### Gaps
- I found no source measuring how a stylelint strict-value gate changed token adoption over time on a real project (Mozilla's bug is open, with no outcome data read).
- Whether `storybook-design-token` v5 handles a large flat set of `--bn-*` custom properties well (performance, presenter mapping) is not documented.

## 5. Component inventory: shared component vs page-local one-off; "has a story" as the definition of "in the design system"

### Takeaway
Off-the-shelf inventory tools are static analysers of JSX usage. **react-scanner** (MIT, config-driven, counts instances and props) is the lightweight option. **Omlet** (by the Zeplin team) is the hosted dashboard, and as of **28 Apr 2026 it announced it is going open source under MIT**, with a guide for migrating from omlet.dev to a self-hosted instance. Both are oriented to *imported* components (`importedFrom`), so "used once, defined in a page file" one-offs need a small AST script or a `raw-report` post-process. Storybook offers no component-coverage report. "Has a story" as the definition of "in the design system" is a team convention, not a tool feature, and I found no well-sourced account of it.

### Cited Findings
- react-scanner statically analyses JS/TS and outputs a JSON report of component and prop usage. Config: `crawlFrom`, `includeSubComponents` (default false), `importedFrom` (string or regex, report only components imported from a matching module). Processors: `count-components`, `count-components-and-props` (the default), and `raw-report` (every instance with props and **file location**). MIT, about 665 stars, 22 open issues and 7 open PRs at capture. The README doesn't say whether locally defined components are detected, and the page showed no last-release date. — [moroshko/react-scanner](https://github.com/moroshko/react-scanner)
- A conference talk ("Measuring Coverage of React Design System") presents react-scanner as the DIY route and Omlet as the all-in-one alternative. — [GitNation, Karan Kiri](https://gitnation.com/contents/measuring-coverage-of-react-design-system-1590)
- Omlet: "Built by your friends at @Zeplin". It has a CLI (`omlet login/init/analyze`) that scans React code locally to detect components, props and usage and uploads metadata (names, paths, prop usage, dependency relationships) to a web dashboard. Supports React and React Native. — [Omlet on X](https://x.com/omlet_dev); [Announcing Omlet](https://omlet.dev/blog/announcing-omlet/); [Product Hunt](https://www.producthunt.com/products/omlet)
- Omlet blog: "**Omlet is going open source**", dated **Apr 28, 2026**: "We're open sourcing Omlet — all of it, under an MIT license." The previous post was Mar 10, 2025 (VS Code extension). The homepage banner links to it, and the docs point at the `zeplin/omlet` GitHub repo. No pricing tiers were visible on the homepage. — [Omlet blog index](https://omlet.dev/blog/); [omlet.dev](https://omlet.dev/)
- A fork of `zeplin/omlet` (MIT) shows a "Migrating from the hosted version" guide covering moving "from omlet.dev to your own instance". It lists Omlet answering which non-design-system components are "heavily used" and "which props are unused". — [GitHub drianoaz/omlet (fork of zeplin/omlet)](https://github.com/drianoaz/omlet)
- React Scanner Studio: an interactive dashboard over react-scanner output, with CODEOWNERS mapping. — [reactscanner.studio](https://reactscanner.studio/)

### Inferences
- Open-sourcing plus a "migrate from hosted" guide, with the blog quiet for 13 months before it, reads as **wind-down of the hosted product and community maintenance after that**. That is inference: the post body (which would state the hosted service's fate) returned 404 at its guessed URL. For a solo developer, a self-hosted dashboard is more infrastructure than the question needs.
- For goal (b), the cheapest reliable answer is a script in the style the project already uses: run react-scanner with `raw-report` (or a TS-compiler/Babel AST walk) over `frontend/src`, and classify each component by **definition location** (a shared components directory vs a page/feature file) × **number of distinct importing files** (1 = one-off, ≥2 = shared). That answers "shared vs one-off" directly, needs no stories, and can be ratcheted ("one-offs that duplicate a shared component's role" as a reviewed list).
- "Has a story" works as the design-system definition only if stories are kept current. On a one-person team that makes the inventory depend on the most rot-prone artefact (section 6). The import-graph classification is derived from the running code, which matches the project's "derived from the running thing" seam rule.

### Gaps
- I could not read the Omlet open-source post body. Whether omlet.dev's hosted service continues, when it ends, and current pricing are **unconfirmed**.
- react-scanner's last release date and current maintenance activity were not visible. Its handling of locally defined (non-imported) components is undocumented.
- I found no Storybook-native "component coverage" (components without stories) feature in the docs read. Any such report would be custom.
- I found no well-sourced 2024–2026 write-up of teams formally using "has a story" as the design-system membership rule.

## 6. Maintenance reality: story rot, stories that pass but no longer match the app, one-person teams

### Takeaway
The evidence is practitioner opinion, not data, but it is consistent. Stories decay within months unless writing them is part of "done". Storybook pays off for larger teams with a shared library and audiences (designers, clients) who look at it. Upgrades and addon breakage are a recurring cost. Turning stories into tests (addon-vitest) makes *broken* stories fail loudly, but it does not catch stories that render fine and no longer resemble the app.

### Cited Findings
- Stories rot without a team norm: one write-up describes teams letting stories sit about three months until they no longer matched the components, and calls culture ("story-writing as part of the definition of done") the biggest predictor of success. It names the conditions where Storybook pays off: more than eight frontend engineers, a component library shared across teams, and stories treated as first-class. It also says stories go stale, addons break between majors, and upgrades take longer than estimated. — [Yashveer Labs, "Storybook in 2026: Still Worth It?" (blog, opinion)](https://yashveerlabs.vercel.app/blog/storybook-in-2026-still-worth-it)
- "Each new component needs a story, and whenever the API for that component changes, you will also need to update the associated Storybook files." If designers and clients don't regularly look at the stories, there is little value against the maintenance cost. — [Atomic Object, "Reconsider Using Storybook"](https://spin.atomicobject.com/using-storybook-reconsider/) (undated in the snippet; treat as older)
- Counterpoint: building bottom-up means working on components in isolation all the way up. — [Hacker News thread (2021, older)](https://news.ycombinator.com/item?id=28493328)
- An example of the cleanup cost: an issue to "group by product area, remove dead stories, add per-situation stories". — [SlashieApp/web #374](https://github.com/SlashieApp/web/issues/374)
- Version-coupling breakage in the 9.x line (Vite 5 and old-Vite failures, a vitest-import crash after Vitest 4) shows the upgrade cost in practice. — [#31624](https://github.com/storybookjs/storybook/issues/31624); [#31619](https://github.com/storybookjs/storybook/issues/31619); [#33215](https://github.com/storybookjs/storybook/issues/33215)

### Inferences
- **Two kinds of rot:** (1) a story that breaks, which addon-vitest's per-story smoke test now catches in CI; and (2) a story that renders but has drifted from the real app (stale fixture props, a missing provider or theme, CSS the app no longer loads). Type-checking story `args` against component props catches part of (2), when props change shape. Nothing catches drift in *context* (theme, global CSS, data shapes from the API), and that drift silently weakens any visual baseline taken from stories.
- On a one-person team the maintainer and the only audience are the same person. The documentation value is small, and the test value has to justify the cost alone. That argues for **a few stories**, limited to the components whose look matters and that E2E can't easily drive into every state, not a catalogue.
- A visual baseline on the **real pages** (Playwright `toHaveScreenshot` against the running server, Chromium plus WebKit) cannot drift from the app by construction. A story-based baseline can. Vitest's own guidance applies to both: generate references in CI or a pinned container, because "references generated on one machine will often fail on another", and baselines are stored per browser and platform (`…-webkit-darwin.png` vs `…-linux.png`). — [Vitest docs, visual regression testing](https://vitest.dev/guide/browser/visual-regression-testing)

### Gaps
- I found no survey or measured data (2024–2026) on story-rot rates or abandonment on small or solo teams. The "decays within months" claim rests on blog opinion.
- I found no case study of a solo developer running Storybook as a test harness long-term.
